<layering_rules>
src/loop.ts is the ONLY file in the repo that may call `requestAnimationFrame`.
`src/loop.ts` and `src/debug/**` are the ONLY places that may read wall time
(`performance.now()` / `Date.now()`). Elapsed run time is `clock.simTimeSec`
everywhere else, per RESEARCH.md "Pattern 2" - a wall-clock run timer makes medal
times framerate-dependent, which is the exact thing VEH-03 exists to prevent.

`renderer.render()` is called exactly once per animation frame, OUTSIDE the fixed
step loop. Rendering per tick collapses the architecture back into variable-rate
rendering. `renderer.info` is read only after that call returns.
</layering_rules>

    Create `src/loop.ts` following RESEARCH.md "Code Examples > Example 1" structurally. PATTERNS.md lists the conventions this file establishes for every later phase, so get the shape right, not just the behaviour.

    Structural conventions to establish:
    - Dependency injection through a single `deps` object literal rather than constructor parameters or module singletons. Later phases add fields to this object; keep it an object.
    - `scheduler` is optional and defaults to a browser implementation wrapping `requestAnimationFrame`, `cancelAnimationFrame`, `performance.now` and a `document` `visibilitychange` listener that fires the callback only on the hidden-to-visible transition. Injecting it is what makes this file testable in Node without jsdom - build the default lazily inside `startLoop` so importing the module in Node does not touch `document`.
    - Reschedule the next frame at the TOP of the frame callback, before any work, so a throw does not kill the loop.
    - First frame only calls `clock.start(nowMs)` and returns.
    - Compute `steps = clock.stepsFor(nowMs)`, then loop `s` from 0 to `steps - 1` with `tickIndex = clock.tick - steps + s`, because `stepsFor` has already advanced `clock.tick` past all of them.
    - Inside each tick, in this exact order: `deps.transforms.captureAsPrevious()`, `deps.onTickBegin?.(tickIndex)`, `deps.applyInput(deps.input.sampleForTick(tickIndex))`, `deps.world.step()`, `deps.onTickEnd?.(tickIndex, null)`, `deps.transforms.captureAsCurrent()`. Swapping the two capture calls inverts interpolation.
    - `onTickEnd` takes an event-queue parameter that is `null` in Phase 1. RESEARCH.md is explicit that the tick callback signature must PERMIT per-tick event draining now, or Phase 5's checkpoint detection will silently miss crossings on multi-step frames. Do not omit the parameter because it is unused today.
    - Measure `physicsMs` with the scheduler's `now()` around the whole step loop, and `renderMs` around the single `deps.render(clock.alpha(nowMs))` call. These wall-clock reads are legal here and only here.
    - `deps.render(alpha)` is called exactly once per frame, outside the step loop.
    - `deps.hud?.(stats, dtMs)` is called last, after render, so the HUD's `renderer.info` read happens after `renderer.render()` returned.

    Stall handling, both halves - RESEARCH.md measured that the clamp alone fails SC3:
    - Register a visibility listener; on the hidden-to-visible transition call `clock.rebaseline(now)`.
    - Track consecutive saturated frames: when `steps === MAX_STEPS_PER_FRAME` increment a counter and call `clock.rebaseline(nowMs)` once it exceeds 30, then reset it; otherwise reset it to 0. This catches stalls that never fire `visibilitychange` - debugger pause, long GC, OS sleep with the tab still nominally visible.

    Return a `LoopHandle` exposing the `clock` and a `stop()` that cancels the pending frame and unregisters the visibility listener.

Do not use jsdom and do not construct a renderer; `render` and `hud` are plain spy functions and `world` is a real Rapier world from `createWorld()` and `createDebugScene()`.
