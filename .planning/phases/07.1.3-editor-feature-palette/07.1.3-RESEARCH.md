## Summary

The two briefs are accurate in their broad shape and the file/function names they cite all exist. Line numbers drifted by small amounts (listed in the verification table). However, I found **eight claims that are wrong, stale or internally inconsistent** and that would cause rework if the planner trusted them. The most consequential: (1) solo `p2p`/`circuit` race modes start at `scene.defaultSpawnPose`, which is the same value `spawnOverride` replaces, so a sidecar default start point WOULD change race starts (the brief says race modes "take their start from the course"; that is only true of `circuit-race`); (2) the AI forward-avoidance ray is an allow-list of car colliders, so AI cars do not "avoid trees" today and will not unless new code is added; (3) the brief's "at most 12 draw calls" and "up to 150 individually fading building meshes" cannot both hold, and the camera fade is off by default anyway (`main.ts` starts occlusion in `"off"`); (4) `P` is taken (Terrain), so the brief's proposed Start-point hotkey clashes; (5) `Delete` is already bound to Delete road and wheel is already bound to zoom, so two of the brief's interactions need different inputs; (6) "coordinates within `MAX_AREA_SIZE_M`" would reject valid Juliette coordinates (x spans -3760..1745); (7) `nextStartId` computed as max-in-list does reuse ids after deleting the last entry; (8) `loadTerrainArea` rebuilds the area field by field, so new sidecar fields are silently dropped on load unless it is edited too.

The undo mechanism is simple and extends cleanly: a `StrokeDiff` carries optional parts, each `{ before, after }` snapshots; `applyStrokeDiff` writes the chosen side onto the live area object. New parts for `startPoints`, `features`, `buildings` and `objects` should be whole-array snapshots (arrays are replaced, never mutated, so snapshots can share element objects). Five functions enumerate diff parts and each needs the new parts (list in Architecture Patterns).

No new npm packages are needed. Everything uses `three@0.185.1` (incl. `three/addons/utils/BufferGeometryUtils.js`) and `@dimforge/rapier3d@0.20.0`, both already installed.

**Primary recommendation:** Build in the briefs' order (start points, then scenery), keep all logic in pure modules (`src/core/*`, `tools/terrain-editor/*.ts`) with tests first, route every edit through new `StrokeDiff` parts committed by dispatcher methods, put scenery colliders on ONE shared fixed body, and resolve Open Questions 1 and 2 with the user before planning the render and spawn plans.

### Pattern 1: Undo diff part (follow `graph`/`lock` exactly)
**What:** `StrokeDiff` (`src/core/terrain-brush.ts:52`) is a bag of optional parts. `heights`/`paint` are index+before+after typed arrays; `graph` is `{before: string, after: string, nextEdgeIdBefore/After}` serialized JSON; `lock` is `{before, after}` number arrays. `applyStrokeDiff(area, diff, side)` (`terrain-undo.ts:37`) writes `diff.x[side]` onto the mutable `UndoTarget` and sets a result flag. The editor's `area` is a `TerrainArea` whose fields are `readonly` in the type; it is mutated through `area as unknown as EditArea` (`editor.ts:488`), where `EditArea = RoadEditTarget & UndoTarget` (`tool-dispatch.ts:146`). So new fields go on `UndoTarget` as optional mutable arrays, like `unlockedEdgeIds`.
**Recorded how:** graph/lock changes are recorded through `StrokeRecorder.recordGraph/recordLock` ("first `before` wins, latest `after` wins"), then `commit()` drops no-op parts. Pure graph changes are pushed by `commitGraphChange` (`tool-dispatch.ts:568`) -> `commitLockDiff` (:552) -> `stack.push(diff)` and a `ToolResult` flag.
**Recommendation for new parts:** build the `StrokeDiff` directly (`{ startPoints: { before, after } }`), skipping the recorder, and push it through a new `commitSceneryDiff(area, diff)` modelled on `commitLockDiff`. Skip the push when `before === after` or arrays are deep-equal (no empty undo steps). Snapshots are whole arrays; because every pure op returns a NEW array and never mutates elements, snapshots can share element objects (50 undo steps x 4,000 pointers is about 3 MB). Apply with `area.features = diff.features[side]` (no re-parse needed: in-memory arrays were valid when pushed; `graph` is re-parsed only because it crosses a JSON string).
**Places that enumerate diff parts and MUST learn the new parts** (missing any one silently drops the part from one path):
1. `applyStrokeDiff` and `ApplyResult` (`terrain-undo.ts:29,37`)
2. `windowsOfDiff` (`tool-dispatch.ts:253`) - returns `{heights?, paint?, graph, lock}`
3. `mergeDiffs` (`tool-dispatch.ts:294`) - erase strokes merge diffs; copies only graph/lock/paint/heights
4. `ToolResult`, `UndoRedoResult`, `emptyResult` (:190), `mergeInto` (:211), `toUndoResult` (:495) and the editor's `applyResult` (:1509) / `undoRedo` (:1685) which decide `edited`, `setDirty(true)`, and refreshes
5. `createStrokeRecorder.commit()` only if you route through the recorder (not recommended)
**Drag = one step:** moving a marker/feature fires many pointer-moves. Keep the working copy in the place-tool state; call the dispatcher commit once on pointer-up with `before` captured at pointer-down.
**Tests to extend:** `tests/terrain-undo.test.ts` (undo stack, `makeArea` helper returns an `UndoTarget`), `tools/terrain-editor/tool-dispatch.test.ts` (uses `createEmptyTerrainArea` + `createToolDispatcher(() => area as unknown as EditArea)`; lock tests at lines ~370-420, ~976 are the closest analogues).

### Pattern 4: Spawn resolution (pure, tested)
`resolveStartPose(search, grid, graph, startPoints, opts)` in `terrain-drive-setup.ts`; `parseDriveHeading` (degrees -> radians; strict decimal, <=8 chars, 0..360) and `parseStartId` (`/^start-\d{1,3}$/`) in `map-select.ts`. ### Pattern 5: Shared scenery view
`createSceneryView(features, buildings, heightAt, opts)` returns `{ group, buildingMeshes, dispose, ... }`. `MeshStandardMaterial` only. Per-kind `InstancedMesh`: set matrices with `setMatrixAt`, then `instanceMatrix.needsUpdate = true`, then `computeBoundingSphere()`. For the editor, expose incremental rebuild by kind (`update(kind, ...)`) rather than rebuilding everything. `dispose()` must dispose geometries, materials AND `InstancedMesh.dispose()` (releases the instance buffer; geometry/material are separate). Rotation convention: three's `mesh.rotation.y = r` maps local +X to (cos r, 0, -sin r), the same as `yRotationQuat(r)` used for building colliders (`map-scene.ts:143`), so `rotationY` means the same thing in view and physics. Use it for features too.

### Anti-Patterns to Avoid
- **Second write path to the area.** All edits go through dispatcher commit -> undo stack -> `applyStrokeDiff`. Do not assign `area.features = ...` anywhere except the undo applier and the commit helper.
- **Mutating arrays in place** in pure ops (breaks snapshot sharing).
- **Raw URL strings as object keys.** Use allowlist regex and array `find` (existing convention; `map-select.ts:29-34`).
- **Wall-clock or randomness in `src/core`.** The Scatter feature needs a seeded PRNG (an LCG like `tests/terrain-scene.test.ts:lcg` is fine); no `Math.random`.
- **One physics body per scenery piece.** Use one shared fixed body.
- **Changing `vehicle.ts` to filter wheel rays** (violates medal rule 8). See Pitfall 6.

## Common Pitfalls

### Pitfall 1: New sidecar field lost on load
**What goes wrong:** `loadTerrainArea` (`terrain-format.ts:654`) returns a hand-built object. Parser and serializer handle `startPoints`/`features`, but the area handed to the editor/game lacks them.
**Why:** field-by-field rebuild is deliberate hardening; `unlockedEdgeIds` is copied there conditionally.
**Avoid:** edit `loadTerrainArea` in the same task as the parser; add a test: load -> area has `startPoints` -> serialize -> text equal.
**Warning sign:** start point visible after placement, gone after reload.

### Pitfall 2: Undo part missing from one enumeration
**What goes wrong:** undo works for startPoints but `mergeDiffs`, `windowsOfDiff`, `toUndoResult` or the editor's refresh flags ignore it, so the UI does not update or the dirty flag is not set.
**Avoid:** the five-place checklist in Pattern 1; one dispatcher test per part: commit -> undo -> state == before -> redo -> state == after, plus assert the result flag is set.

### Pitfall 3: Spawn change silently alters race starts
**What goes wrong:** `spawnOverride` becomes the scene's `defaultSpawnPose`, which solo p2p/circuit restart and respawn-fallback use (`race-coordinator.ts:147,165`) and pursuers/stations derive from. A map with routes plus a start point would move the race start.
**Avoid:** gate the sidecar default and `?start=` (see Open Question 2). Keep `?at=`/`?heading=` behaviour as today (explicit URL intent applies in every mode). Test with `?mode=circuit` and no params that `defaultSpawnPose` equals the graph spawn on a map WITH a start point.

### Pitfall 4: Palette building invisible on legacy-GLB maps
**What goes wrong:** `legacyGlbBuildings: true` maps (juliette-ga, grid-test) only draw the glb; a newly placed building has a collider and no mesh.
**Avoid:** per-building rule (style present = always drawn by the scenery view; style-less = drawn only if `!legacyGlbBuildings`). In the editor (no glb loaded) draw ALL sidecar buildings so the author sees what exists; decide whether style-less legacy ones are drawn as grey blocks (recommended, cheap, labelled as legacy).

### Pitfall 5: Per-mesh fade vs draw budget
See Open Question 1. Also: fade materials need `transparent: true`; `buildingMeshes[i].id` is the occluder key; `createOcclusionProbe(mapView.buildingMeshes)` and `createOcclusionController(...)` each get the array reference at creation (`main.ts:1201,1209`), so `mapView.buildingMeshes` must be final BEFORE that point.

### Pitfall 6: Wheel rays treat scenery as ground
**What goes wrong:** `vc.updateVehicle(DT)` is called with no filter (`vehicle.ts:1053`), so suspension rays hit EVERY collider, including fence/hedge cuboids and building tops. A 0.3-0.5 m fence (brief allows `heightM` from 0.3) behaves like a kerb the car climbs; the surface under such a hit is the map default (tarmac) unless registered.
**Avoid:** do not modify `vehicle.ts` (medal rule 8). Raise the catalog minimum heights for solid linear features (hedge/fence minimum about 1.0 m to be decided by a headless drop/drive test), and add a physics test: drive/drop a chassis at speed into a 0.5 m and a 1.0 m fence cuboid and record whether it climbs. Register scenery colliders with `input.groundSurface` in `surfaceMap` (as the berm does) so a wheel on top of one reads grass not tarmac. This is the only item here that may force a catalog-number change; mark MEDIUM until measured.

### Pitfall 7: Stale instanced bounding sphere
r185 computes `InstancedMesh.boundingSphere` lazily when null, then caches it. After editor re-seating or any matrix change, call `computeBoundingSphere()` (or null it) or instances pop in/out at screen edges.

### Pitfall 8: Shadows are nearly irrelevant and cost draw calls
The game's only shadow-casting light is the sun in `vehicle-view.ts:492-503` with a fixed 60 m x 60 m shadow box (`SHADOW_AREA_HALF = 30`) at the origin; the sun does not follow the car and the car uses a blob shadow (`car-shadow.ts`). So `castShadow = true` on trees/buildings does nothing useful away from world origin while adding shadow-pass draws: `WebGLInfo.update` increments `render.calls` for every `renderBufferDirect` including the shadow pass, and an InstancedMesh with a whole-map bounding sphere is always drawn into the shadow map `[CITED: node_modules/three/src/renderers/webgl/WebGLInfo.js]` (MEDIUM: shadow-pass counting inferred from source, not measured). Recommend `castShadow = false` for all scenery in v1 and `receiveShadow` only if it is free; revisit with the lighting work in Phase 11. This overrides brief 02 stage 4's "castShadow true for buildings and tree canopies" (planner should confirm with the user if they care about the look).
Also note: `renderer.shadowMap.type = THREE.PCFSoftShadowMap` (`renderer.ts:64`) is logged as deprecated in r185 (`WebGLShadowMap.js:101`, falls back to PCFShadowMap). Pre-existing, not this phase's problem.

### Pitfall 9: Editor and game heights differ slightly
Editor `area.grid` vs game `physicsGridForArea` (Catmull-Rom 2x upsample). Pass `heightAt` explicitly into every geometry function so each consumer uses its own grid; do not hide the grid inside the view. Buildings store `center.y` baked at editor placement, so they are exact for neither; extend the box downward by the footprint height range (brief step 3) so no corner floats on either grid.

### Pitfall 10: `driveHere()` reads state before `await save()`
Capture the spot at the instant of the hotkey (`lastHit` at keydown time is valid because the pointer is over the canvas) and pass it into the async function. Menu invocation has no cursor: use the camera target and say so in the info bar, as the brief says. Also remember `save()` can refuse (returns `false`); `driveHere` already returns in that case.

### Pitfall 11: ids and counters
Start point id counter lives outside the list (see verification table). Feature ids: `nextFeatureId` has the same issue; crest ids for ramps must be unique within `objects` (parser rejects duplicates, `terrain-format.ts:613-619`; existing ids are free-form strings, e.g. juliette names). Generate `ramp-N` and check collisions against existing crest ids.

### Pitfall 12: Existing assertions that must change
`tests/terrain-scene.test.ts:219` ("throws naming the area when there is no default spawn and no override") becomes the new fallback test. `rail-tools.test.ts` expected code set and "TERRAIN_BAR order" tests change when Place is added. `toolbar-state.test.ts` input literals (`ToolbarInput`) gain a field; update the `sel`/`brush` helpers.

### Spawn parse helpers (strict, allowlist)
```ts
// src/core/map-select.ts, same DECIMAL regex as parseDriveAt
export function parseDriveHeading(search: string): number | undefined {
  const raw = new URLSearchParams(search).get("heading");
  if (raw === null || raw.length === 0 || raw.length > 8 || !DECIMAL.test(raw.trim())) return undefined;
  const deg = Number(raw);
  return Number.isFinite(deg) && deg >= 0 && deg <= 360 ? (deg * Math.PI) / 180 : undefined;
}
```
Note: URL degrees need a defined mapping to `headingRad` (VehiclePose yaw). Test both ends together so a compass-flip bug shows up.

| Pattern | STRIDE | Standard Mitigation |
|---------|--------|---------------------|
| Hostile/oversized sidecar (huge arrays, NaN, huge sizes feeding allocation/Rapier) | Tampering / DoS | caps (32 start points, 4,000 point features, 500 lines, 64 points per line, 2,000 buildings), `reqRange` on every size, finite checks (WR-08 precedent) |

| Path in server error text | Info disclosure | existing `safeMessage` redaction; no change |

## Constraints for the UI-SPEC (do not design the layout here)

The UI design contract (`/gsd-ui-phase`) must respect:
- **Shared shell components available:** `createTopBar` spec model (tool, stack, menu, slot, divider; one menu open at a time; menu closes on pick/Esc/outside), `menuFace` (icon + word + optional swatch), `createSection/Field/Stepper/Select/Toggle/Button`, `openDialog/confirmDialog`, info bar (`setStatus` kinds info/ok/error, `info.set(key, text)` fields: area, size, cell, cursor, surface, roads, change; adding a field is just an `infoFields` entry), tooltips (`data-tip` on every control, `tipLong` for the long-hover tier), sidebar with title/subtitle and a persistent "View" section.
- **07.1.2 conventions (CONTEXT D-32..D-38 and memory editor-ui-principles):** one slim top bar over the canvas; related tools behind ONE button with a drop-down (Place ▾, like Road ▾ and Terrain ▾); option values in the LEFT sidebar, never floating on the canvas; controls next to what they affect; swatch grids in even rows (Terrain uses `ceil(n/2)` columns of 32 px); sidebar content rebuilt per mode/armed tool; Undo/Redo are in the top bar; Clear selection beside Select.
- **Button text rules:** label <=12 chars, tip format `Word: what it does`, no trailing period, <=60 chars including the key label; unique glyphs; `tipLong` for how-to text.
- **Hotkeys:** free codes only (table above); Delete and wheel are taken; Esc has a priority chain.
- **Sidebar list for start points** (name editable, Make default, Go to, Delete) sits in the sidebar, which is currently built per mode/armed tool and replaced wholesale; the Start-points list must survive sidebar rebuilds (render from area state each time) and refresh after undo/redo/place/delete.
- **Show the user a layout sketch before building** (rule 11 and memory); the sketch is the UI-SPEC deliverable.
- **No jsdom:** UI behaviour beyond pure state is manual-check only; keep visual logic data-driven where possible (e.g. palette entries as data, `validateBarSpec`-style checks).

## Open Questions

1. **Per-building camera fade vs the 12-draw-call budget (needs user decision)**
   - Known: brief 02 stage 4 says build one `Mesh` per building (<=150, each with its own material, listed in `buildingMeshes`) so the camera can fade them, and merge above 150. D-09 locks <=12 scenery draw calls. 150 meshes is 150 draws (live target `< 80` total, Juliette peaks at 63). Fade is OFF by default (`main.ts:1215`, `"off"` with car x-ray); `O` cycles it in debug only.
   - Unclear: whether the user expects palette buildings to fade.
   - Recommendation: honour D-09. Draw buildings as one merged mesh per style (<=5 draws), leave them OUT of `buildingMeshes`, and rely on the default x-ray ghost. If fade for palette buildings is wanted later, add it for small counts only (for example <=24 buildings as individual transparent meshes, gated by the draw budget) or via a per-instance approach. Record the decision; adjust the brief's human check #4 ("camera still fades a building") to "x-ray ghost shows the car behind a building".

2. **Where the sidecar default start point and `?start=` may apply (needs user decision)**
   - Known: solo p2p/circuit and free drive all spawn/restart at `scene.defaultSpawnPose` (see Pitfall 3). Existing maps have no start points, so nothing changes until an author adds one.
   - Recommendation: apply `?at=` (+`?heading=`) and an explicit `?start=` in every mode (explicit URL intent, matches today's `?at=`); apply the SIDECAR DEFAULT only when the run is free-drive (no routes file or no course mode), so authoring a start point on juliette-ga can never silently move a medal-time race start. The editor's "Drive from" always passes explicit `&start=`. Brief human check #5 stays valid.

3. **Catalog minimum heights for hedges/fences (needs a headless measurement)**
   - Known: wheel rays treat any collider as ground (Pitfall 6); brief allows `heightM` 0.3-6.
   - Recommendation: measure with a Rapier test, then set minimums in the catalog and sidebar steppers. Do not edit `vehicle.ts`.

4. **Scenery in the shadow pass**
   - Recommendation: `castShadow = false` everywhere in v1 (Pitfall 8); confirm the user does not expect tree/building shadows.

5. **Ramp editing UI needs crest mesh extraction**
   - `terrain-view.ts` builds crest meshes privately. Recommendation: extract `buildCrestMeshes(crests, heightAt)` (and `faceWeightedNormals`) to a shared render module used by both `terrain-view.ts` (output unchanged, `tests/terrain-view.test.ts` must stay green) and the editor, then rebuild after `objects` changes and sculpts. Also export `MAX_CREST_HEIGHT_M` (currently module-private in `terrain-format.ts:459`).

6. **AI cars do not avoid scenery (accepted limitation)**
   - Not in scope to add. Record in docs so nobody expects it; pursuers snagging on trunks is consistent with the "hung-up pursuers are an intended escape" memory.

7. **Editor drawing of legacy buildings**
   - Editor has no glb. Recommend drawing ALL sidecar buildings (style-less ones as neutral blocks) so authors can see and delete them; confirm.
