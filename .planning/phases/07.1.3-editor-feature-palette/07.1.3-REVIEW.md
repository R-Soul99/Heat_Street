# Phase 07.1.3: Code Review Report

**Reviewed:** 2026-11-16T01:16:48Z
**Depth:** standard
**Files Reviewed:** 22
**Status:** issues_found

## Summary

Reviewed the changes since `30b868b` in the 22 listed files (start points, Place menu, scenery
catalog / format / geometry / physics / view, editor palette, select / move / delete, arrow-key
rotate, ramp editing, ray picking). The large pre-existing files (`editor.ts`, `tool-dispatch.ts`,
`terrain-format.ts`, `main.ts`) were reviewed through their diff plus the surrounding code the
diff calls into.

The pure modules (`features.ts`, `scenery-guards.ts`, `scenery-geometry.ts`, `start-points.ts`,
`place-tool.ts`, `drive-url.ts`, the sidecar parser) are sound: rotation conventions agree between
footprint, pick, render and collider code; the parser caps and validates every new field; URL
parameters are validated; names from files reach the DOM through `textContent` / `value` only.
No security findings.

The defects are in the wiring: one data-consistency blocker on legacy-GLB maps, and several editor
integration bugs (stale building meshes after a sculpt, an arrow-key fall-through that silently
changes the Raise/Lower step, undo history flooding from the ramp steppers, index-based building
selection that shifts under undo).

## Answer to the specific question: what wrote the ~80 degree slope into demo-hills?

**Short answer: no phase-07.1.3 code path writes terrain heights. The steep step was produced by
the existing box-selection Raise/Lower (or Alt-drag push/pull) sculpt with the sidebar "Slope
limit" set to its maximum of 80 degrees.**

### Evidence from the code

- None of the phase's files writes `grid.heights`. A search for height writes across
  `editor.ts`, `features.ts`, `scenery-guards.ts`, `place-tool.ts`, `start-points.ts`,
  `tool-dispatch.ts`, `scenery-geometry.ts`, `scenery-view.ts` and `crest-view.ts` finds none.
  The sculpt, road and slope modules (`terrain-slope.ts`, `terrain-road.ts`,
  `terrain-road-lock.ts`, `terrain-grid.ts`, `terrain-limits.ts`, `crest-geometry.ts`) have no
  changes since `30b868b`; `terrain-brush.ts` gained type fields only.
- `withBuildingReseat` / `pushDiff` (`tool-dispatch.ts:575-605`) read heights only. The "before"
  grid is a copy (`Float32Array.from(g.heights)`, line 582); the live grid is never written. The
  only thing it changes is `area.buildings` (centre y and half-height of styled buildings).
- `reseatBuildingsAfterSculpt`, `moveSceneryItem`, `rotateSceneryItem`, `seatBuilding`
  (`scenery-guards.ts`, `features.ts`) take a height sampler and return new building objects.
- `commitScenery` / `commitStartPoints` (`tool-dispatch.ts:797-839`) build diffs with no `heights`
  part, so `withBuildingReseat` returns early (line 578) and undo/redo touches arrays only.
- Ramps are crest objects in `area.objects`, drawn by `buildCrestMeshes` and collided as their own
  mesh. Editing ramp height / angle / width (`updateRamp`) never touches the grid.
- Lock / re-grade interplay: `commitLockDiff` is now an alias of `commitSceneryDiff`. A re-grade
  diff does carry heights, but those come from the unchanged `regradeRoads` / `setRoadLock`; the
  phase only appends a `buildings` part to that diff.

### Evidence from the saved map (working copy vs HEAD, read-only analysis)

- 11,856 of 40,401 vertices differ. The changed vertices form axis-aligned rectangles, which is
  the footprint of box-selection operations, not of buildings, ramps or roads.
- 6,516 vertices changed by exactly +4.0 m (one large rectangle raised).
- 650 vertices changed by exactly -50.0 m. 50 m is `PUSH_PULL_MAX_M` (`tool-dispatch.ts:172`),
  the clamp shared by hold-to-repeat Raise/Lower and push/pull. This is a rectangular pit about
  rows 15-40, columns 142-170.
- The pit wall is a straight line along column 141 to 142 (x = 123 to 126), with heights
  -17.01 then -34.03. Each step is 17.02 m over a 3 m cell, and tan(80 deg) x 3 m = 17.01 m. That
  is the slope limiter (`limitSlope`) terracing at exactly 80 degrees, which is
  `SLOPE_LIMIT_MAX_DEG` (`tool-dispatch.ts:171`).
- All 3,423 over-limit vertex pairs have at least one end on a changed vertex. None is near any of
  the four placed buildings (they sit on unchanged ground at height 0, around x -30..40,
  z 90..119). Only 67 are near road paint.

So the limiter was running at 80 degrees while a box selection was lowered to the -50 m clamp. The
only code that sets `slopeLimitDeg` is the "Slope limit" stepper in the Select and Brush sidebars
(`editor.ts:4719-4727`), which is pre-existing and not persisted between sessions.

### How the phase may have contributed indirectly (not confirmed, worth a look)

These do not write heights, but they make an unintended sculpt more likely or harder to recover:

1. The selected-ramp panel puts a ramp "Angle" stepper (degrees, max 80) in the same Select
   sidebar as the "Slope limit" stepper (degrees, max 80), a few rows apart. ramp-5 in the saved
   map has angle 80, and the slope limit was at 80. Whether the wrong stepper was used is not
   something the code can show.
2. WR-02 below: holding Left/Right to rotate a selected item steps the Select "Step" value on every
   key repeat, up to 5 m per tick. With Step at 5, ten ticks of Lower reach the -50 m clamp.
3. WR-03 below: holding a ramp stepper pushes one undo entry per tick into a 50-entry stack, so
   earlier sculpt steps drop out of undo history. Three ramps were raised from 2 m to 50 m and
   110 m.
4. WR-08 below: Esc from a Place tool returns to whatever brush was armed before.
5. IN-04 below: the editor saves a map whose slopes exceed `MAX_SLOPE_DEG` (35) without any
   warning, so the failing test is the first signal.

## Critical Issues

### CR-01: Legacy GLB buildings can be moved, rotated or bulk-deleted, desynchronising collision from the baked visuals

**File:** `tools/terrain-editor/editor.ts:3004`, `tools/terrain-editor/editor.ts:2699-2739`, `tools/terrain-editor/features.ts:447-462`, `tools/terrain-editor/features.ts:684-697`
**Issue:** On maps with `legacyGlbBuildings: true` (`grid-test` has 124 buildings, `juliette-ga`
has 85) the style-less entries in `area.buildings` are collision boxes for meshes baked into the
map GLB. The editor draws them (`installArea` passes `drawStyleless: true`), `pickFeatureByRay` /
`pickFeatureAt` select them, `moveSceneryItem` and `rotateSceneryItem` move and turn them, the
Delete key removes them, and "Delete scenery in selection" (`removeInMask`) removes every building
whose centre is in the box. The game still draws the building from the GLB
(`main.ts:431-437, 454`) because `drawStyleless` there is `!legacyGlbBuildings`. After a save the
car drives through a visible building, or hits an invisible box where a building was moved to, and
pursuit line of sight no longer matches what is drawn. Nothing in the editor signals this.
**Fix:** Treat style-less buildings on legacy maps as read-only in every scenery edit path:
```ts
// features.ts
const editable = (b: TerrainBuilding, legacyGlb: boolean) => !(legacyGlb && b.style === undefined);
// removeInMask: keepB = buildings.filter((b) => !editable(b, legacyGlb) || !inMask(b.center.x, b.center.z));
// pickFeatureAt / pickFeatureByRay: skip buildings where !editable(b, legacyGlb)
```
Pass `area.legacyGlbBuildings` through `SceneryArea` (already present) into the pick and remove
functions, and add a test on a legacy area.

## Warnings

### WR-01: Building meshes are not refreshed after most sculpt paths re-seat the buildings

**File:** `tools/terrain-editor/tool-dispatch.ts:539-542`, `:1109-1112`, `:1374`, `:1399-1402`, `:1422`; `tools/terrain-editor/editor.ts:5223-5235`, `:790-812`
**Issue:** `pushDiff` re-seats styled buildings and replaces `area.buildings`, but only
`endOpRepeat`, `endPushPull` and `commitSceneryDiff` report `buildingsChanged`. These paths drop
it:
- brush stroke release (`pointerUp` -> `finish(s.recorder.commit())`), erase, and road stroke
  (`finish(r.diff)`): `finish` ignores the pushed diff, the returned result has no
  `buildingsChanged`.
- Flatten on a selection (`applyOperation`, line 1111) and `smoothAll` (line 1422).
- Keyboard / pointer hold of Raise, Lower, Smooth: `stopOpHold` calls `dispatcher.endOpRepeat()`
  and discards the result (`editor.ts:5230`).

`sceneryChanged` therefore never calls `sceneryView.setBuildings`. The view keeps the old array,
and `reseatScenery` only calls `sceneryView.reseat` when a feature is in the window, which rebuilds
from that same stale array. The building is drawn floating or buried until some later building
edit, while the saved data and the selection box use the new seat. The toolbar text "sculpting
under an item re-seats it" is false for these paths as far as the view goes.
**Fix:** Have `finish` return the pushed diff and set the flag at each call site, and apply the
hold result:
```ts
function finish(diff: StrokeDiff | undefined): StrokeDiff | undefined {
  const pushed = diff ? pushDiff(getArea(), diff) : undefined;
  stroke = null;
  return pushed;
}
// pointerUp / smoothAll / applyOperation: res.buildingsChanged = pushed?.buildings !== undefined;
// editor.ts stopOpHold: sceneryChanged(dispatcher.endOpRepeat());
```

### WR-02: Holding Left/Right (or Shift+Left/Right) on a selected item silently changes the Raise/Lower step

**File:** `tools/terrain-editor/editor.ts:5580-5609`
**Issue:** The rotate branch requires `!e.shiftKey && !e.repeat`. When the key auto-repeats, or
Shift is held, the branch is skipped and the event falls through to `adjustDirection`, where
ArrowRight is +1 and ArrowLeft is -1 on `activeValue`. In Select mode `activeValue` is the "Step"
stepper (`selectStepM`, 0.25 to 5 m). Holding Right to turn a building rotates it once, then walks
Step up to 5 m per tick; holding Left walks it down to 0.25. The next Raise/Lower on a box
selection uses that value. The same fall-through happens when the selected item is a hedge or
fence (`rotateSelectedScenery` returns false for lines).
**Fix:** Consume the arrow keys whenever a placed item is selected:
```ts
if ((e.code === "ArrowLeft" || e.code === "ArrowRight") && selectedScenery && selectableNow()) {
  e.preventDefault();
  if (!e.shiftKey && !e.repeat) rotateSelectedScenery(e.code === "ArrowLeft" ? 1 : -1);
  return;
}
```

### WR-03: Ramp panel steppers push one undo entry per tick and evict the rest of the history

**File:** `tools/terrain-editor/editor.ts:2799-2812`, `:2836-2860`; `tools/terrain-editor/tool-dispatch.ts:435`
**Issue:** Each `onChange` of the selected-ramp Height / Angle / Width steppers calls
`editSelectedRamp`, which commits one undo entry. The stepper buttons auto-repeat while held. The
stack holds 50 entries (`createUndoStack(50)`) and drops the oldest. Taking a ramp from 2 m to
50 m at 0.5 m per tick is 96 entries, so one held button removes every earlier sculpt, road and
placement step from undo.
**Fix:** Coalesce consecutive edits of the same ramp into one entry, for example commit on stepper
release / blur, or let the dispatcher replace the top entry when it is an `objects`-only diff for
the same ramp id made within a short window.

### WR-04: Building selection is an array index and silently retargets after undo or redo

**File:** `tools/terrain-editor/features.ts:33-36`, `tools/terrain-editor/editor.ts:2397-2402`, `:2456-2467`, `:2673-2697`
**Issue:** `ScenerySelection` for a building is `{ kind: "building", index }`. `sceneryExists`
only checks the index is in range. Delete building 1, select what is now index 2, press Ctrl+Z:
building 1 returns and index 2 is a different building. The selection box jumps to it, and Delete,
the arrow keys or a drag then act on the wrong building.
**Fix:** Clear the building selection (and hover) whenever `buildingsChanged` arrives from undo or
redo, or key the selection on object identity (`area.buildings.indexOf(selectedBuildingRef)`) and
drop it when the reference is gone.

### WR-05: Building footprint road check samples only the centre and four corners

**File:** `tools/terrain-editor/editor.ts:1518-1530`, `tools/terrain-editor/scenery-guards.ts:161-168`, `:307-316`
**Issue:** Place, move and rotate refuse a building only when its centre or a corner is on road
paint or outside the area. Footprints go up to 100 m per side and roads are 3 to 20 m wide, so a
road that passes between the sample points is not seen. A 16 m "block" can be dropped across an
8 m street with its centre just off the paint; the result is a solid collider across the road.
Lines already sample every 0.5 m (`canPlaceLine`).
**Fix:** Sample the footprint on a grid no coarser than the paint resolution (edges and interior),
for example by reusing the `rectPoint` walk with a step of `paint.metresPerPixel`, in one shared
helper used by all three call sites.

### WR-06: Hedge and fence segments are level slabs at the average ground height, so they float on slopes

**File:** `src/core/scenery-geometry.ts:134-171`, `:214-228`
**Issue:** Each segment (up to `MAX_SEGMENT_M` = 8 m) gets one `y`, the mean of its two end
heights, and both the collider and the drawn box are axis-level. `LINE_SINK_M` = 0.3 only covers
a 0.6 m end-to-end height difference, about 4 degrees over 8 m. On a 20 degree slope an 8 m
segment has ends 2.9 m apart, so the low end of a 1.2 m fence collider sits about 1.2 m above the
ground and the high end is buried. A car can pass under it, and the rails float away from the
posts (which are seated per point).
**Fix:** Shorten segments by height difference as well as length (split until
`|y1 - y0| <= 2 * LINE_SINK_M`), or pitch each box along its slope and give the collider the same
rotation.

### WR-07: Ramp checks validate only the foot start point

**File:** `tools/terrain-editor/scenery-guards.ts:92-99`, `:188-200`, `:336-342`; `tools/terrain-editor/editor.ts:2288-2331`; `tools/terrain-editor/features.ts:369-387`
**Issue:** `canPlaceRampAt` tests one point. A ramp runs `rampLengthM` along its heading from that
point; the saved map has ramps over 100 m long. Placing, moving, rotating, or raising the height
of a ramp near the edge leaves most of its body outside the area and through the edge berm, seated
on clamped out-of-grid heights. `updateRamp` and `rotateSceneryItem` do no area check at all.
**Fix:** Check the four corners of `rampFootprint(crest)` with `insideArea` in one helper, and call
it from place, move, rotate and `updateRamp` (pass the area in).

### WR-08: Leaving a Place tool with Esc silently returns to the previously armed brush

**File:** `tools/terrain-editor/tool-dispatch.ts:791-795`, `tools/terrain-editor/editor.ts:5529-5536`
**Issue:** `setPlacing` leaves `mode` and `brushTool` untouched. If the user was in Brush mode with
Raise or Lower armed before opening Place, Esc ("Stopped placing.") puts them straight back into
that brush, and the next click on the map, typically an attempt to select the item just placed,
sculpts terrain instead.
**Fix:** On Esc from placing, go to Select mode (`dispatcher.setMode("select")`), which is also
the mode in which placed items can be picked; or state the restored brush in the status line.

## Info

### IN-01: `?start=` accepts at most three digits but the id counter is unbounded

**File:** `src/core/map-select.ts:113-117`, `tools/terrain-editor/start-points.ts:13-25`
**Issue:** `parseStartId` requires `start-\d{1,3}`; `startIdSeed` never reuses ids, so `start-1000`
is reachable after enough add / delete cycles and "Drive from" then falls back to the default
start with no message.
**Fix:** Share one id pattern between the two modules, or widen the digit count.

### IN-02: Placement checks ignore existing buildings, ramps and scenery

**File:** `tools/terrain-editor/features.ts:65-69`, `tools/terrain-editor/editor.ts:1716-1759`
**Issue:** `canPlaceAt` tests only the area extent and road paint. Scatter and single placement
put trees inside buildings and on ramps, and buildings can overlap each other. Overlapping fixed
colliders are harmless, but trees inside a building still count toward the triangle and feature
limits and cannot be clicked.
**Fix:** Optionally skip scatter points that fall inside a building footprint.

### IN-03: `commitLockDiff` is now a pass-through alias

**File:** `tools/terrain-editor/tool-dispatch.ts:709-712`
**Issue:** After the rename the function only forwards to `commitSceneryDiff`, and the name
`commitSceneryDiff` no longer describes what the lock, re-grade and road-fix callers use it for.
**Fix:** Keep one function with a neutral name (`commitDiff`).

### IN-04: The editor saves terrain steeper than `MAX_SLOPE_DEG` without warning (pre-existing)

**File:** `tools/terrain-editor/tool-dispatch.ts:170-171`, `tools/terrain-editor/editor.ts:4368-4374`, `:4719-4727`
**Issue:** Not introduced by this phase, but it is the mechanism behind the failing
`tests/demo-hills.test.ts` "respects the max slope" check. The Slope limit stepper goes to 80
while the tests and the game assume 35, and the save path has no slope check.
**Fix:** On save, compute `maxSlopeDegIn` over the grid and warn (or ask for confirmation) when it
exceeds `MAX_SLOPE_DEG`; show the slope limit in the info bar whenever it is not the default.
