# Phase 04.2: Code Review Report

**Reviewed:** 2026-11-02
**Depth:** standard
**Files Reviewed:** 35
**Status:** issues_found

## Narrative Findings (AI reviewer)

## Summary

Scope: the HSTR binary and sidecar codec, the triangle sampler and picker, the slope limiter, the brushes, the road brush and graph editor, undo, the chunked view, the Rapier heightfield scene, the converter, and the dev-only terrain editor with its `/__terrain/*` Vite middleware.

**Middleware security (checked first, as requested):**
- **Path traversal:** the middleware is sound. The id must match `^[a-z0-9-]{1,64}$`, the file kind is allowlisted to `bin|json`, the resolved path is checked to start with `mapsDir + sep`, and URL-encoded traversal cannot pass the regex.
- **Body size:** bodies are capped at 64 MB (bin) and 8 MB (json) while streaming, before anything is decoded or written.
- **Cross-origin access:** I read the installed Vite 8.2.2 code. Its CORS and `allowedHosts` checks are registered BEFORE the `configureServer` hooks run. So cross-origin PUTs and DNS-rebinding requests are rejected before they reach the plugin.

No traversal or injection path was found. The remaining middleware problem is a write-integrity issue (WR-07).

**Binary parser:** the bounds checks hold up. Every size is checked against a cap and against the exact byte length before anything is allocated. The surface-enum reads are bounded by `headerBytes`. Inflation stops as soon as the output passes the declared size.

**Sampler, picker and render triangulation:** I worked through both diagonal formulas, the picker's triangles and the view's index winding. They are correct and agree with each other.

**Main problems found:**
- **Encoder (CR-01):** it computes the height range, then awaits compression, then quantises the live heights. An edit made during a save can wrap a Uint16 silently and corrupt the saved file.
- **New-area flow (CR-02):** it can create areas that can never be saved.
- **Slope limiter and road brush:** they do not protect existing road vertices, which breaks D-16 (graph y == terrain y). See WR-01 and WR-02.
- **Physics grid:** the Catmull-Rom upsampled physics grid moves levelled road surfaces away from the heights the editor wrote (WR-04).
- **`main.ts`:** the feel-test migration left several branches dead, so `?gate`, the car shadow and the ground probe are gone (WR-05).

Accepted items were not re-reported: invalid road graphs being saveable, no terrain-edge boundary, and the HUD overlap.

## Critical Issues

### CR-01: Terrain save is not a consistent snapshot; edits made during save corrupt heights silently and are then marked saved

**File:** `src/core/terrain-format.ts:135-149, 155-162, 190-192`; `tools/terrain-editor/editor.ts:302-316`
**Issue:** `encodeTerrainBinary` does its work in three steps:
1. Computes `minH`/`maxH` and `offsetSteps` from `grid.heights` (lines 135-149).
2. Awaits `deflateRaw(paint.data)` (line 156). This yields to the event loop, and on a 2 km area at 0.5 m/px it deflates up to 16 M pixels.
3. Only then quantises the live `grid.heights` (line 191).

The editor keeps handling pointer events during that await: Ctrl+S or `D` (Drive here) mid-drag, or sculpting right after pressing Save. If a vertex is lowered below the precomputed `minH`, `Math.round(h/scale) - offsetSteps` goes negative. If it is raised past `maxSteps`, the value goes above 65535. `DataView.setUint16` wraps either case silently, so a vertex lowered by 1 cm is saved as +655 m. The decoder accepts the file, because every u16 is "valid".

The snapshot is also torn: the compressed paint is from before the await, but the heights are from after it.

Finally, `save()` calls `setDirty(false)` after both PUTs return. Any edit made during the save is then marked clean, so `beforeunload` no longer warns and those edits are lost on close.

**Fix:** Quantise before the first await and validate every value. Snapshot the editor state synchronously, and guard against overlapping saves:
```ts
// terrain-format.ts: quantise first, no await in between
const q = new Uint16Array(count);
for (let i = 0; i < count; i++) {
  const v = Math.round(grid.heights[i] / scale) - offsetSteps;
  if (v < 0 || v > 65535) throw new RangeError(`height at vertex ${i} out of encoded range`);
  q[i] = v;
}
const paintCopy = paint.data.slice();
// ...then await deflateRaw(paintCopy) and write q

// editor.ts
let saving = false;
async function save() {
  if (!area || saving) return false;
  saving = true;
  const editsAtStart = editCounter;           // bump editCounter in applyResult/undoRedo
  try { ... if (editCounter === editsAtStart) setDirty(false); }
  finally { saving = false; }
}
```

### CR-02: "New..." creates areas that can never be saved (vertex cap mismatch); sculpting work is unrecoverable

**File:** `tools/terrain-editor/new-area.ts:37-46`; `src/core/terrain-format.ts:123-125`; `tools/terrain-editor/index.html:127`; `tools/terrain-editor/editor.ts:279-291`
**Issue:** The two code paths enforce different vertex limits:
- `createEmptyTerrainArea` only checks `cellSizeM > 0`. It relies on `createTerrainGrid`, which allows up to 2^27 vertices.
- `encodeTerrainBinary` rejects anything over `MAX_TERRAIN_VERTICES` (4,000,000).

The form's own defaults hit this. The `new-cell` input allows `min="0.5"`, and the default area is 1000 x 1000 m. At 0.5 m cells that is 2000 x 2000 cells, which is (2001)^2 = 4,004,001 vertices. A 2000 x 2000 m area at 1 m cells gives the same count.

The area is created and installed, and the user can sculpt it for as long as they like. Every save then fails with `terrain grid has 4004001 vertices, max 4000000`. Nothing can reduce the vertex count afterwards, so the work cannot be saved.

**Fix:** Reject the grid at creation time using the encoder's limit, and give the cell input a sensible minimum:
```ts
// new-area.ts, after computing rows/cols
if ((rows + 1) * (cols + 1) > MAX_TERRAIN_VERTICES) {
  throw new RangeError(
    `${cols}x${rows} cells is ${(rows + 1) * (cols + 1)} vertices, max ${MAX_TERRAIN_VERTICES}; use a larger cell size`,
  );
}
```
Also add a max for the paint pixels (`MAX_PAINT_PIXELS`) at the same point.

## Warnings

### WR-01: Road stroke's slope limiter can move earlier roads' levelled vertices, so their graph y no longer matches the terrain (D-16)

**File:** `src/core/terrain-road.ts:817-818, 837-845`
**Issue:** Step 2 builds `protect` from road-flagged paint plus `roadVertexMaskFromGraph`, which covers every earlier edge's full levelled radius `max(halfWidth, cell*sqrt2)`. That mask is only passed to `levelRoadBand`, where it guards the shoulder blend.

The `limitSlope` call at line 843 builds its own mask: `band.mask` (the new road) plus `roadVertexMaskFromPaint`. The graph-derived part is missing. Vertices between an earlier road's paint edge (`halfWidth`) and its levelled radius are therefore unmasked:
- at 3 m cells this is 2.5..4.24 m for a dirt road;
- on juliette-ga's 8 m cells it is about 3..11.3 m.

The limiter can move those vertices. They are corners of the triangles under the earlier road's centreline, so that road's surface drifts away from its stored graph y. `syncNodeHeights` only refreshes node y, and only inside `reachWin`. Edge interior points are never refreshed.

**Fix:** Merge `protect` into the limiter mask:
```ts
const mask = band.mask;
const paintMask = roadVertexMaskFromPaint(grid, paint, win);
roadVertexMaskFromGraph(grid, area.graph, win, paintMask); // over `win`, not just reachWin
for (let i = 0; i < mask.length; i++) if (paintMask[i] || protect[i]) mask[i] = 1;
```

### WR-02: Sculpt brushes run the slope limiter with no road mask; road terrain moves and graph y goes stale

**File:** `src/core/terrain-brush.ts:211`; `tools/terrain-editor/tool-dispatch.ts:287-289`
**Issue:** The slope limiter's design says road-masked cells are "NEVER written". But `runHeightOp` calls `limitSlope(grid, dirty, { maxSlopeDeg })` with no `mask`, and no caller can pass one.

A raise, smooth, flatten or stamp near a road has two effects:
- Its expanded window lets the limiter lower or raise levelled road vertices outside the brush radius.
- Nothing updates the graph afterwards. Node and edge-point y keep their old values, the AI and route code read stale heights, and banked crossfall is destroyed.

**Fix:** Have the dispatcher build `roadVertexMaskFromPaint(grid, paint, dirty)` and pass it through `runHeightOp` to `limitSlope`. Alternatively, after any height op whose window touches road paint, re-sync graph y for the affected edges (as `syncNodeHeights` does) and record it in the stroke diff.

### WR-03: The windowed limiter "fixes" pre-existing over-cap slopes and creates steps at the window border

**File:** `src/core/terrain-slope.ts:230-260`; `src/core/terrain-brush.ts:159-169`; `tools/map-compiler/terrain/convert.ts:86-149`
**Issue:** `limitSlope` relaxes every pair inside the window. It never reads the vertices just outside it, so border cells are unconstrained against their outside neighbours.

`expandWindow` sizes the window from the edit's own `maxDelta`. That makes edit-induced propagation fit inside it. Violations that already existed in the window are a different case: they are not bounded by `maxDelta`.

The converter (`convertHeights`) never runs a slope pass. Its DEM heights and its road-level shoulders (blended over `2*cell`) can exceed 35 degrees. On such terrain, a 1 cm dab:
- reshapes every steep pair in the expanded window, well outside the brush;
- lowers or raises border vertices away from their unchanged outside neighbours, creating a new cliff at the window edge;
- reports `slopeClamped` on almost every dab, so the amber ring and hint stay on permanently.

**Fix:** Do two things:
1. Treat a one-vertex ring around the window as read-only sources: add it to the mask and include it in the sweeps.
2. Limit relaxation to pairs the op itself made steeper, for example by masking out vertices whose pre-op neighbourhood was already over the cap.

Alternatively, run one global `limitSlope` pass in `convertHeights`, with road vertices masked, so converted areas start within the cap.

### WR-04: The Catmull-Rom physics upsample changes levelled road surfaces, so the driven surface differs from editor heights and graph y

**File:** `src/core/terrain-grid.ts:212-256`; `src/core/terrain-drive-setup.ts:79-83`; `src/main.ts:364-386`
**Issue:** With `colliderSubdiv === 2`, the game builds the collider and the view from `upsampleTerrainGrid`. The new mid-cell vertices use a 4-tap cubic, which overshoots wherever the curvature changes.

At the edge of a flat levelled band next to a rising shoulder (row values `0, 0, 0, h`), the midpoint between the last two road vertices becomes `-h/16`. A 2 m rise in the next cell puts a 12.5 cm dip inside the road. A 30 cm rise still gives a 2 cm ridge or dip, which the gate measured as felt suspension jitter.

The editor, `syncNodeHeights` and the stored graph y all sample the base grid with `sampleTerrainHeight`. The car drives on a different surface. The upsampled grid is also not slope-limited, so the 35-degree cap can be exceeded between original vertices.

**Fix:** Take the extra collider resolution from linear interpolation along the base grid's own triangles. That is exact for the levelled road, and the subdivided triangles reproduce the same surface. Alternatively, only use cubic interpolation where all 4x4 taps are unmasked (not road), and linear elsewhere.

### WR-05: The feel-test migration left the `?gate` course, the car shadow and the ground probe unreachable

**File:** `src/main.ts:348-356, 553-565, 589-597, 1070-1089, 1146-1149`
**Issue:** `MAP_FORMATS["feel-test"]` is now `"terrain"`, and `isFlatTestArea` matches only `"feel-test"`. That kills several branches:
- `GATE_ENABLED = !isTerrain && AREA_ID === "feel-test" && ...` is always false. The 04.2 gate course, its view, its J-key spawns and its texture updates are unreachable, even though the module header still documents `?map=feel-test&gate`.
- `isFlatTestArea(AREA_ID) && !isTerrain` (lines 553 and 589) is always false. The proving ground has silently lost the car shadow and ground probe that its comment ("lay a shadow patch on the ground below the car") says it provides.

**Fix:** Decide what each feature should do on terrain feel-test:
- Either delete the gate wiring and the flat-plane FX branch, or re-gate them on `AREA_ID === "feel-test"`. The gate course sits at x >= 700, outside the feel-test terrain grid, so it can still be added as a second heightfield.
- Re-enable `createCarShadow` and `createGroundProbe` for feel-test under `isTerrain`.

### WR-06: Editor writes untrusted strings into `innerHTML`

**File:** `tools/terrain-editor/editor.ts:158-162` (via 269-271, 319-320, 477-478)
**Issue:** `setStatus` builds `$("status").innerHTML = \`${name}${marker}<br>${text}\``, and `text` comes from untrusted sources:
- **Load errors** that echo file content: `parseTerrainSidecar` quotes the file's `areaId`, `groundSurface` and the object `kind`, as in `unknown surface "${groundSurface}"`.
- **Server error bodies** on save.
- **`formatValidationFailures`** output, which carries graph strings.

A `.terrain.json` in `public/maps` (pulled from git, or produced by an importer) with `"groundSurface": "<img src=x onerror=...>"` runs script in the dev origin when it is loaded. That origin can then PUT arbitrary terrain files through the middleware.

**Fix:** Build the status line with DOM nodes:
```ts
function setStatus(text: string): void {
  const el = $("status");
  el.replaceChildren(area ? area.areaId : "no area");
  if (dirty) { const s = document.createElement("span"); s.className = "dirty"; s.textContent = " unsaved"; el.append(s); }
  el.append(document.createElement("br"), text);
}
```

### WR-07: Save is not atomic across the bin/json pair, and concurrent PUTs share one temp file name

**File:** `tools/terrain-editor/vite-plugin.ts:49-58`; `tools/terrain-editor/editor.ts:302-310`
**Issue:**
1. `writeAtomic` uses `${file}.${process.pid}.tmp`. Every request in the dev server shares that pid, so two concurrent PUTs to the same file write the same temp file. The editor has no in-flight guard: Ctrl+S twice, Save then `D`, or a save during another save. One rename can then publish interleaved bytes, or fail with ENOENT after the other request already renamed the file.
2. The editor PUTs the `.bin` first and the `.json` second. If the json PUT fails (sidecar validation, disk, network), the new bin is already on disk next to the old sidecar. That pair can still load (the bounds check allows one cell of slack), but its graph y no longer matches the terrain.

**Fix:** Make the temp name unique, for example ``${file}.${process.pid}.${randomUUID()}.tmp``, and serialise saves in the editor (see CR-01). For the pair, either validate both bodies before writing either one (a single multipart or combined endpoint), or have the editor PUT json first, since it is cheap and the most likely to be rejected.

### WR-08: The sidecar parser does not range-check crest, ramp or building numbers; a "valid" file can crash or freeze game boot

**File:** `src/core/terrain-format.ts:412-447`; consumer `src/core/crest-geometry.ts:264-305`
**Issue:** `parseRamp`, `parseObject` and `parseBuilding` only require finite numbers. The PUT middleware and `loadTerrainArea` therefore accept values that break the consumers:
- **`ramp.angleDeg: 0`:** `rampLengthM` returns `(h - footRise) / tan(0) = Infinity`, then `steps = Infinity`, then `new Float32Array(Infinity)`, which is a RangeError at boot.
- **Very small angles or large `heightM`:** allocations of hundreds of millions of floats, which can freeze or OOM the tab.
- **`radiusM <= 0` on a dome crest:** degenerate geometry.
- **Negative or zero `halfExtents` on buildings:** these go straight into Rapier cuboids.

The module header claims T-04.2-06..09 hardening, but that covers only the binary half.

**Fix:** Add range checks in the parsers. For example:
- `radiusM > 0 && radiusM <= MAX_AREA_SIZE_M`
- `0 < heightM <= 200`
- `0 < angleDeg < 90`
- `widthM > 0`
- `footRadiusM >= 0`
- `halfExtents.* > 0`

Also check that crest ids are unique.

## Info

### IN-01: The 413 response is never delivered

**File:** `tools/terrain-editor/paths.ts:47`; `tools/terrain-editor/vite-plugin.ts:111`
**Issue:** `readBodyCapped` calls `req.destroy()`, which tears down the socket, before the handler sends 413. The editor sees `Failed to fetch` instead of "request body too large".
**Fix:** Stop reading (`req.pause()` / `unpipe`), send 413 with `Connection: close`, then destroy the socket in the response's `finish` handler.

### IN-02: The slope cap is not preserved bit-exactly through Float32 or through save quantisation

**File:** `src/core/terrain-slope.ts:50, 123-125`; `src/core/terrain-format.ts:191`
**Issue:** `EPS_M = 1e-5` is smaller than half a Float32 ulp above 512 m elevation. Separately, saving quantises heights to 0.01 m, so a pair limited to `d - 1e-5` can come back up to about 0.01 m steeper after a round trip. The effect is tiny (about 0.2 degrees at 3 m cells), but the guarantee is not exact.
**Fix:** Scale EPS with `|h|` (for example `Math.max(1e-5, Math.abs(h) * 2 ** -22)`), and leave about one quantisation step of margin, or note the tolerance in D-03.

### IN-03: The surface remap passes out-of-range file indices through unchanged

**File:** `src/core/terrain-format.ts:330-337`
**Issue:** When the file's enum differs from the current one, any low nibble `>= fileToCurrent.length` is kept as is. Its meaning then changes from "invalid", which falls back to tarmac in the writer's build, to whichever current surface has that index.
**Fix:** Map such values to the fallback surface's index, or reject the file.

### IN-04: The medal record builder can emit splits its own parser rejects

**File:** `src/core/medal-reference.ts:236-248` vs `149-150`
**Issue:** Splits are rounded to 1 ms. Two hits less than 0.5 ms apart round to the same value, and `parseMedalReference` requires strictly increasing times. The last split is also pinned to `totalTimeSec`, which can leave the second-to-last split greater than or equal to the last one.
**Fix:** After rounding, check that the times are strictly increasing and throw a clear error, or bump the later split by 0.001 s.

### IN-05: Surface-FX slide state is module-global, and terrain decals are clipped at chunk edges

**File:** `src/render/surface-fx.ts:401, 533`
**Issue:** `WHEEL_SLIDING` is shared by every `createSurfaceFx` instance, so a second instance (tests, or a future AI car FX) would corrupt the hysteresis state. Separately, `meshAt` returns a single 64-cell chunk, so a skid mark that crosses a chunk border is cut off.
**Fix:** Move `WHEEL_SLIDING` into the closure. Project onto the neighbouring chunk too when the decal footprint crosses `x0/x1/z0/z1`.

### IN-06: The gate harness baseline always uses subdiv 1

**File:** `src/physics/telemetry/terrain-gate.ts:219-221`
**Issue:** `runFlatBaseline` passes `colliderSubdiv` 1, while the lanes are measured at 1 or 2. At subdiv 2, the jitter thresholds compare against a baseline taken at a different collider resolution.
**Fix:** Take `colliderSubdiv` as a parameter and pass it to the baseline as well.
