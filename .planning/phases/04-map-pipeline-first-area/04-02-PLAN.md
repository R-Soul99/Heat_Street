roads and buildings — with the query logic ported from the user's own Geomesh tool.

and never needs the network again.

<interfaces>
<!-- The Overpass response shape the rest of the compiler consumes. -->

`out body geom qt;` returns, per element:

```jsonc
{
  "elements": [
    { "type": "node", "id": 1234, "lat": 33.11, "lon": -83.80, "tags": { } },
    { "type": "way", "id": 5678,
      "nodes": [1234, 1235, 1236],                    // node ids, index-aligned with geometry
      "geometry": [{"lat":33.11,"lon":-83.80}, ...],  // one entry per entry in `nodes`
      "tags": { "highway": "residential", "surface": "gravel" } }
  ]
}
```

The `nodes` array is load-bearing: junction detection in plan 04-04 works by finding OSM node ids
shared between ways. `out tags geom` (the form used during research) omits `nodes` and is NOT
sufficient.

`AreaConfig` from plan 04-01 (`tools/map-compiler/areas/juliette-ga.config.ts`) supplies
`areaId`, `name`, `bbox { south, west, north, east }`, `demSource`, `osmSnapshot`,
`excludeHighwayClasses`.
</interfaces>

<plan_decisions>
- **D-P6 — `out body geom qt`, not `out tags geom qt`.** The research session's query omitted OSM
  node ids; junction topology cannot be recovered without them. This supersedes 04-RESEARCH.md's
  "Code Examples" query shape for the compiler's real query. A fallback is specified in the task
  in case `nodes` is unexpectedly absent.
- **D-P7 — the raw snapshot is committed to the repo.** It is OSM data under ODbL, already
  covered by `LICENSE-MAPDATA`, and committing it is what makes the build reproducible and
  diffable offline (04-RESEARCH.md Pitfall 1). Size is the tradeoff; the box is ~3 km across, so
  the payload is small.
- **D-P8 — roads and buildings are fetched as two separate queries into two separate cache
  files**, matching Geomesh's own `/api/roads/network` and `/api/buildings/structures` split, so
  a building-query change cannot invalidate the road snapshot (and vice versa).
</plan_decisions>

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Overpass API -> compiler | Untrusted remote response body parsed at build time |
| committed cache file -> compiler | Repo-local but machine-generated input to every later stage |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-04-05 | Spoofing / Tampering | `parseOverpassResponse` | mitigate | Leading-character check rejects an HTML/XML error page before `JSON.parse`, throwing a message naming the endpoint — the exact failure 04-RESEARCH.md Pitfall 1 observed twice, and the one that would otherwise silently produce an empty map |
| T-04-10 | Tampering | Overpass response contents | accept | OSM data is community-edited and could in principle carry hostile tag values; the surface mapping (plan 04-01) throws on unknown values and every numeric field is parsed with an explicit range check in plan 04-04, so the blast radius is a failed build, not a compromised runtime |
| T-04-03 | Information Disclosure | outbound build-time HTTP | accept | The compiler is developer-invoked and its endpoints are hardcoded constants; the only data leaving the machine is a public bounding box |
| T-04-11 | Denial of Service | shared public Overpass instance | mitigate | Bounded retry (3 attempts, exponential backoff) plus a committed disk cache so normal rebuilds make zero requests — this protects the shared public infrastructure as much as the build |
| T-04-04 | Tampering | new `tools/` source files | mitigate | Already covered by plan 04-01's widened `tests/no-google-pipeline.test.ts` scope; this plan's Geomesh provenance comments are written to state what is NOT ported (its Google-optional elevation/geocoding tiers) |
</threat_model>
