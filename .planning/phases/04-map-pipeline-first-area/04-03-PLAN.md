<objective>
Turn the road graph's centrelines into actual surface geometry: a ribbon per edge, a fan per
junction, sharing exact vertex positions so the seams SC1 forbids cannot exist by construction.

Purpose: SC1 has two independent failure modes. This plan closes the topology one (gaps, steps
and overlaps where geometry meets); plan 04-05 closes the elevation one (per-pixel DEM noise
reading as a bumpy road). Neither implies the other and both must be handled.

Output: one pure module in `src/core/` that both the offline compiler (for the `.glb` and for
collision buffers) and the browser runtime (for building colliders at load) call — which is what
makes SC3's "collision geometry and nav graph derive from the same road graph" structurally true
rather than a claim about intent.

MVP-slice increment: no user-visible change on its own — this is the shared contract plans 04-07
and 04-08 both build the visible and drivable world from. It is placed in wave 2, parallel with
the Overpass fetch, precisely because it depends on nothing but the graph shape.
</objective>

```typescript
interface RoadGraphNode { id: number; x: number; y: number; z: number; junction: boolean; osmNodeId: number; }
interface RoadGraphEdge {
  id: number; from: number; to: number;
  points: readonly (readonly [number, number, number])[]; // centreline, local ENU metres, Y-up
  lengthM: number; surface: SurfaceType; roadClass: string;
  lanes: number; widthM: number; oneway: boolean;
  speedLimitKph: number; bridge: boolean; tunnel: boolean; layer: number; osmWayId: number;
}
```

Coordinates are local ENU metres, **Y-up**: X east, Y up, Z south. Offsets are taken in the XZ
plane only; Y is never modified by this module — it is authored upstream from the DEM and is
authoritative (schema design decision 1).

Consumers of this module's output:
- `tools/map-compiler/author/gltf.ts` (plan 04-07) — merges the buffers into `.glb` primitives
- `src/physics/map-scene.ts` (plan 04-08) — feeds each buffer to
  `RAPIER.ColliderDesc.trimesh(vertices, indices, RAPIER.TriMeshFlags.FIX_INTERNAL_EDGES)`

Both want the same thing: `Float32Array` positions (stride 3) plus a `Uint32Array` index buffer,
counter-clockwise wound when viewed from +Y so the road's up-face normals point up.
</interfaces>

<plan_decisions>
- **D-P9 — this module lives in `src/core/`, not `tools/map-compiler/geometry/`.** 04-RESEARCH.md
  and 04-PATTERNS.md both placed it under `tools/`. Deliberate deviation: the browser runtime
  needs the identical algorithm to build colliders that line up with the shipped `.glb` to the
  vertex. Two implementations of a miter-joined offset polyline WILL drift, and the symptom is the
  car floating above or sinking into the road it visibly touches. `src/core/` is the project's
  pure tier (no engine, no DOM, no wall clock), it is mechanically policed by
  `tests/layering.test.ts`, and `tools/` may import from `src/` while the reverse is forbidden.
- **D-P10 — miter joins with a length clamp, not round or bevel joins.** Miters keep the vertex
  count minimal (2 per centreline point) and keep the ribbon's index pattern a simple strip.
  Clamping the miter length at 3x the half-width prevents the spike-to-infinity degenerate at a
  near-180-degree hairpin; past the clamp the joint reads as a bevel, which is visually correct
  for a road anyway.
</plan_decisions>

    - A 3-point edge with a 90-degree corner produces a miter at the interior point whose offset distance from the centreline is `halfWidth / sin(theta/2)` (about 1.414x halfWidth at 90 degrees), on the outside of the turn

  <action>
Create `src/core/road-geometry.ts`. Export `buildRibbon(edge: RoadGraphEdge): RibbonGeometry`
where `RibbonGeometry` is `{ positions: Float32Array; indices: Uint32Array; leftCorners: readonly Vec3[]; rightCorners: readonly Vec3[] }`.
`leftCorners`/`rightCorners` expose the FIRST and LAST offset pair at each end of the ribbon,
which is what the junction fan in Task 2 stitches to — exposing them here, rather than
recomputing them in the fan builder, is the mechanism that makes the shared-vertex guarantee real
rather than a coincidence of two independent calculations agreeing.

Implementation shape, per 04-RESEARCH.md Pattern 1: walk the centreline; at each point compute the
tangent (the forward difference at the first point, the backward difference at the last, the
normalised average of both at interior points), take the XZ perpendicular, and emit
`point ± normal * halfWidth`. At interior points scale the offset by the miter factor
`1 / sin(theta / 2)` where theta is the interior angle between the incoming and outgoing segments,
clamped at 3 (D-P10). Y is copied through untouched at every vertex — never recomputed, never
interpolated (schema design decision 1).

Collapse consecutive points closer than `1e-4` m before processing, so an OSM way with a duplicated
node cannot produce a zero-length tangent. Throw, naming the edge id, if fewer than two distinct
points survive.

Emit indices as a quad strip: for each pair of consecutive centreline points, two triangles from
the four surrounding offset vertices, wound counter-clockwise as seen from +Y. Write the winding
convention as a comment with the specific vertex order, because getting it wrong produces a road
whose faces are culled from above — which reads as "the road is invisible" and is a genuinely
confusing bug to diagnose from the symptom.

Module header in the project's standard shape, closing with: "Layering: pure geometry. Imports
only `src/core/road-graph.ts`. Must not import three, RAPIER, any `@gltf-transform` package, or
