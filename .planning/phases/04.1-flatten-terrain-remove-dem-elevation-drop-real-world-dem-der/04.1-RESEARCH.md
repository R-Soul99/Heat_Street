# Phase 04.1: Flatten Terrain / Remove DEM Elevation - Research

**Researched:** 2026-09-19
**Domain:** Offline map-compiler data pipeline (TypeScript/Node), procedural terrain authoring, Rapier heightfield physics
**Confidence:** HIGH (this is a rewrite of code already in this repo — every claim below is grounded in the actual source files, the actual compiled artifact, and the actual test suite, not external library research)

## Summary

This phase is a **deletion-and-simplification** phase, not a new-technology phase. Nearly
everything needed already exists in the repo: `tools/map-compiler/graph/elevation.ts` (DEM
sampling/smoothing/densification), `tools/map-compiler/sources/dem.ts` (USGS 3DEP fetch/cache/
sampler), `tools/map-compiler/author/heightfield.ts` (off-road grid), `src/core/road-geometry.ts`
(`buildRoadShoulders`), and `src/core/shoulder-clearance.ts` (building-aware width resolution) are
all real, working code whose job was entirely to cope with DEM noise. Once roads are flat (D-01)
and off-road relief is capped and fades to exactly 0 at the shoulder's outer edge (D-02b), **the
height mismatch these files exist to bridge no longer exists by construction** — most of this
machinery becomes deletable or radically simplifiable, not merely retunable.

The single most important architectural finding: `buildRoadShoulders`/`resolvePointShoulderWidth`
were built to solve a real elevation gap (measured average 5.09m in the current compiled area).
D-01 + D-02b jointly guarantee that gap becomes ~0m everywhere. That means `TARGET_SHOULDER_WIDTH_M`
(currently 20m — the literal cause of the "ridiculous" skirts) can shrink to a small cosmetic
margin (a paved/mown shoulder strip, not a structural ramp), and `HEIGHTFIELD_SINK_M` (currently
4.5m) should shrink to a near-zero physics-contact safety margin, not a real elevation offset.
Building-clearance clamping likely still has a (much smaller) job — keeping shoulder geometry from
visually overlapping a building footprint — independent of the elevation concern it was originally
built for.

A second finding, grounded in the *actual currently-compiled* Juliette, GA data (extracted during
this research session, before it is overwritten): a real 13.18m local road-elevation bump exists
partway along edge id 8 (osmWayId 9397242, a residential road, ~812m long, local point
`(-780.7, z=208.3)`), and two ~3m bumps exist along edge ids 29/34 (osmWayId 195682275, the primary
road through town). These are concrete, non-hypothetical candidates for D-04's "authored terrain
crest" jump locations — extract and hard-code them now, because this data is destroyed the moment
`applyElevation` stops running DEM sampling.

A third finding requiring planner attention: D-01 ("roads flat everywhere, no exception") and D-04
("authored terrain crests... for a 'launch over the hill' moment") read as in tension unless the
crests are understood as **off-road** features (consistent with D-02's off-road-only relief and
D-02b's fade-to-zero-at-the-paved-edge rule) that a player deliberately drives onto, not a bump in
the paved road itself. This document flags it as an assumption needing confirmation, not a settled
fact.

**Primary recommendation:** Delete `tools/map-compiler/sources/dem.ts` and its network/cache
machinery entirely; replace `elevation.ts`'s DEM-sampling pipeline with a trivial
constant-zero-plus-authored-overrides pass; replace `heightfield.ts`'s DEM-sampled grid with a
pure deterministic value-noise generator gated by distance-to-nearest-road, requiring **zero new
npm dependencies**; collapse `TARGET_SHOULDER_WIDTH_M` and `HEIGHTFIELD_SINK_M` to small constants
reflecting their new, much narrower job; keep `src/core/road-geometry.ts`'s shared
compiler/runtime algorithm pattern unchanged (it is unaffected by the elevation source and remains
the correct shape).

## User Constraints (from CONTEXT.md)

### Locked Decisions

- **D-01:** Roads are flat everywhere — every road node/point gets `y = 0` (or a single
  project-wide constant), not DEM-sampled, not smoothed. This removes the shoulder-bridging
  problem by construction rather than by a clamping/resolution algorithm: road and terrain meet
  at the same height because both start from the same flat baseline near the road.
- **D-02:** Off-road terrain is NOT perfectly flat — it gets a small, capped, procedural relief
  (not DEM-derived, not hand-placed) for visual texture in open areas away from roads.
  - **D-02a:** Cap amplitude: ±2m (a starting/reasoned default — the user picked this over a ±5m
    option; both were explicitly offered, ±2m chosen as noticeably subtler).
  - **D-02b:** The relief fades to exactly 0 within the shoulder width, i.e. by the time it reaches
    the road's paved edge — this is the guarantee that a shoulder never bridges more than a
    trivial residual gap, not a real multi-metre cliff. Falloff mechanism/curve shape is Claude's
    discretion (smoothstep, linear, etc.).
  - The exact amplitude/falloff-distance numbers are a REASONED DEFAULT, retunable empirically
    against the real compiled area, same as `SMOOTHING_WINDOW`/`HEIGHTFIELD_SINK_M` in Phase 4.
- **D-03:** The height generator for the "dead flat" baseline (roads, and the off-road relief's
  zero-point) is a literal constant zero — no noise function, no per-area authoring needed for the
  flat baseline itself. Only the off-road relief (D-02) needs an actual generator (a deterministic,
  seeded low-amplitude function — e.g. simplex/value noise — Claude's discretion on the specific
  algorithm).
- **D-04:** Phase 4 CONTEXT.md's D-09 ("real rolling elevation/crests") is superseded for the
  current area. Jumps now come from two sources: (a) primarily, Phase 2's proven hand-placed ramp
  mechanic; (b) secondarily, a small number of deliberately AUTHORED (not DEM-derived, not
  procedural) terrain crests at specific hand-picked spots for a "launch over the hill" moment.
  Both are explicit, deterministic, designer-placed — never sourced from real-world elevation data.
- **D-05:** D-09's target-area-selection criterion (favor real rolling terrain) is RETIRED as the
  operative rule for the current/v1 area, but not permanently ruled out — recorded as a possible
  criterion for a future v2 area. Note as superseded-for-now in the ADR amendment (D-08).
- **D-06:** Once flat-terrain recompiles, a FULL re-run of the Phase 04-11 drive-every-road SC1
  human sign-off session is required — same bar as Phase 4's own completion.
- **D-07:** Existing OSM-derived surface-type tagging (`edges[].surface`) is UNCHANGED by this
  phase — surface comes from OSM `surface=*` tags, independent of elevation. Nothing about
  gravel/dirt/tarmac grip or FX should need retuning as a result of this phase.
- **D-08:** `docs/adr/0001-map-data-source.md` is AMENDED IN PLACE (not superseded by a new
  document) to reflect that elevation is no longer DEM-sourced — OSM remains the frozen
  road/building topology source; only the elevation sub-decision changes. Preserve the original DEM
  reasoning as historical context, matching ADR 0004's house style.

### Pattern 1: Flat baseline with explicit authored overrides

**What:** Replace DEM sampling with a function that returns `0` for every node/point, except for
a small, explicit, hard-coded lookup table of authored exceptions (by node id or by
lat/lon-derived local x/z) for D-04b's jump crests, if those are confirmed to be on-road (see Open
Questions #1).

**When to use:** `applyFlatElevation`'s node/edge-point pass, replacing `applyElevation`.

**Example:**
```typescript
// tools/map-compiler/graph/elevation.ts (new shape)
const FLAT_Y = 0;

/** Explicit, hand-picked exceptions to FLAT_Y — see D-04b. Empty by default. */
const AUTHORED_ELEVATION_OVERRIDES: ReadonlyMap<number, number> = new Map([
  // [osmNodeId, yMetres] — filled in during planning/execution against the
  // concrete candidates this research identified (edge id 8, osmWayId
  // 9397242; edge ids 29/34, osmWayId 195682275).
]);

export function applyFlatElevation(graph: RoadGraph): { graph: RoadGraph } {
  const nodes = graph.nodes.map((node) => ({
    ...node,
    y: AUTHORED_ELEVATION_OVERRIDES.get(node.osmNodeId) ?? FLAT_Y,
  }));
  const edges = graph.edges.map((edge) => ({
    ...edge,
    points: edge.points.map(([x, , z]) => [x, FLAT_Y, z] as const),
    lengthM: polylineLength2D(edge.points), // 2D is exact once y is constant
  }));
  return { graph: { ...graph, nodes, edges } };
}
```

### Pattern 2: Distance-gated deterministic relief

**What:** A pure function `reliefAt(x, z)` for `buildHeightfield`'s grid loop, replacing the DEM
`ElevationSampler.sample(lat, lon)` call. Two inputs: a deterministic hash/value-noise term
(D-03), and a falloff term driven by distance to the nearest road edge (D-02b), multiplied
together and clamped to `±RELIEF_AMPLITUDE_M`.

**When to use:** `tools/map-compiler/author/heightfield.ts`'s `buildHeightfield` grid-sampling
loop.

**Example:**
```typescript
// tools/map-compiler/author/heightfield.ts (new shape) — pattern only, not
// exact final code; see 04.1-PLAN.md for the locked implementation.

/** [ASSUMED, D-02a] reasoned default, retune empirically like every other constant in this file's history. */
const RELIEF_AMPLITUDE_M = 2;

/** Distance (metres) over which relief ramps from RELIEF_AMPLITUDE_M down to 0 -- must be <= the smallest real shoulder width so D-02b's guarantee holds even at a building-clamped MIN_SHOULDER_WIDTH_M point. */
const RELIEF_FALLOFF_DISTANCE_M = /* <= new, shrunk TARGET_SHOULDER_WIDTH_M */ 4;

function hashNoise2D(x: number, z: number, seed: number): number {
  // Deterministic, seeded, pure -- any stable hash-based value noise works;
  // exact algorithm is Claude's discretion per D-03. Must NOT use Math.random.
  const s = Math.sin(x * 12.9898 + z * 78.233 + seed) * 43758.5453;
  return s - Math.floor(s); // [0, 1)
}

function distanceToNearestRoadEdgeXZ(x: number, z: number, graph: RoadGraph): number {
  // Linear scan over graph.edges' point-to-segment distance in the XZ plane.
  // O(edges) per grid point is fine at this map's ~64-edge scale (see
  // "Alternatives Considered" above).
  let best = Number.POSITIVE_INFINITY;
  for (const edge of graph.edges) {
    for (let i = 1; i < edge.points.length; i++) {
      best = Math.min(best, pointToSegmentDistanceXZ(x, z, edge.points[i - 1], edge.points[i]));
    }
  }
  return best;
}

function reliefAt(x: number, z: number, distanceToRoad: number): number {
  const falloff = Math.min(1, distanceToRoad / RELIEF_FALLOFF_DISTANCE_M); // 0 at road, 1 past falloff distance
  const smoothFalloff = falloff * falloff * (3 - 2 * falloff); // smoothstep, Claude's discretion per D-02b
  const noise = hashNoise2D(x, z, RELIEF_SEED) * 2 - 1; // [-1, 1)
  return noise * RELIEF_AMPLITUDE_M * smoothFalloff;
}
```

### Anti-Patterns to Avoid

- **Re-deriving distance-to-road per frame at runtime:** the relief grid is baked once at compile
  time into `HeightfieldGrid.heights` exactly like the DEM version was — nothing about this
  computation belongs in `src/` or the browser tick loop.
- **Coupling `RELIEF_FALLOFF_DISTANCE_M` to the OLD `TARGET_SHOULDER_WIDTH_M` (20m):** D-02b's
  guarantee only holds if the falloff distance is `<=` whatever the shoulder width becomes AFTER
  this phase shrinks it, not the old pre-phase value. Getting this backwards would let relief
  poke up mid-shoulder again — reintroducing a smaller version of the exact bug this phase fixes.
- **Leaving `demSource`/`attribution.dem` referencing USGS 3DEP in a compiled map that used no
  DEM:** a shipped, inaccurate provenance string is a legal-attribution correctness bug (ADR 0001's
  entire purpose), not just a stale comment. See Open Questions #2.
- **Deleting `resolvePointShoulderWidth`'s building-clamp logic outright:** even though its
  original elevation-bridging job disappears, a flat-width shoulder strip can still visually
  overlap a building footprint if not clamped. Verify empirically before deleting rather than
  assuming clamping is now pointless.

## Don't Hand-Roll

| Problem | Don't Build | Use Instead | Why |
|---------|-------------|-------------|-----|
| Rapier heightfield collider construction/orientation | A new probe/verification of Rapier's storage order | The ALREADY-VERIFIED `heights[row + col * (nrows+1)]` convention documented in `tools/map-compiler/author/heightfield.ts`'s header and consumed unchanged by `src/physics/map-scene.ts` | This was empirically verified against the installed Rapier build in Phase 4 (throwaway-world probe, documented in detail) — redoing that investigation for this phase would be pure waste; the grid *shape* contract does not change, only what fills it |
| Bilinear sampling of a height grid | A second sampler for the new relief grid | `src/core/heightfield-sample.ts`'s existing `sampleHeightfieldBilinear` | Already generic over any `SampleableHeightfield`-shaped grid; used identically by both compiler (`shoulder-clearance` height lookups) and runtime (`map-scene.ts`) |

**Key insight:** This phase's entire domain is "delete/simplify code that already exists to cope
with a problem that is being designed away," not "integrate an unfamiliar library." The
`Don't Hand-Roll` risk here is inverted from the usual case — the risk is *hand-rolling a new
verification pass* for something Phase 4 already verified (Rapier grid orientation) rather than
reusing it.

## Common Pitfalls

### Pitfall 1: Treating this as a pure `elevation.ts` edit and missing the knock-on schema/config edits

**What goes wrong:** `AreaConfig.demSource` is a TypeScript literal union type
(`"usgs-3dep-1m" | "copernicus-glo30"`), and the wire schema's `source.demSource` /
`attribution.dem` fields are mandatory strings (`parseRoadGraph`'s `requireString`, verified in
`src/core/road-graph.ts`). Once no DEM is fetched, both need a new value that is not a lie about
provenance. If left unchanged, the shipped `.map.json` will claim `usgs-3dep-1m` DEM provenance
for a map that used no DEM at all — a real accuracy defect in a file whose entire purpose (per
ADR 0001) is legal/licensing provenance.

**Why it happens:** D-08 explicitly scopes the ADR amendment to "amend ADR 0001 in place," which
reads narrower than the actual blast radius (the ADR + the schema doc's prose + the `AreaConfig`
TS type + every area config's literal value).

**How to avoid:** Confirmed via this session's `tests/road-graph-schema.test.ts` read: the test
only asserts **key presence** (`REQUIRED_SOURCE`/`REQUIRED_ATTRIBUTION`), never specific string
values — so repurposing the *values* (e.g., `demSource: "none-flat-authored"`,
`attribution.dem: "No DEM used — flat/hand-authored terrain, see ADR 0001 amendment"`) is a safe,
non-breaking edit. Widen `AreaConfig.demSource`'s type (or rename the field) to admit the new
value. Update `docs/schemas/road-graph.v1.md`'s field-reference table and design-decision 1's
prose (which currently says "`y` is authored by the compiler from the DEM") — this is a prose
edit, not a schema version bump (field shape is unchanged, so `docs/schemas/road-graph.v1.md`'s
own Versioning rule does not require a new document).

**Warning signs:** `npm run compile-map` succeeds and `parseRoadGraph`'s self-check passes even if
`demSource` is left saying `"usgs-3dep-1m"` — the schema parser has no way to catch a
provenance *lie*, only a missing *key*. This will not surface as a test failure; it must be caught
by review.

### Pitfall 2: Recompiling before deleting the stale DEM cache file

**What goes wrong:** `tools/map-compiler/areas/juliette-ga.dem.tif` (the cached raw GeoTIFF) and
`tools/map-compiler/areas/juliette-ga.raw-osm.json` will remain on disk after this phase. The DEM
cache file becomes pure dead weight (nothing reads it once `dem.ts` is deleted) but a future
`git status` or repo audit could mistake it for still-live data.

**Why it happens:** `loadOrFetchDem`'s cache-first behavior means the file is silently never
touched again rather than erroring — there is no "orphaned cache" detector in this codebase.

**How to avoid:** Delete `tools/map-compiler/areas/*.dem.tif` explicitly as part of this phase's
cleanup, alongside deleting `sources/dem.ts`/`sources/dem.test.ts`.

**Warning signs:** `git status` shows the `.dem.tif` file as unchanged/untouched after a phase that
claims to remove DEM entirely — a reviewer should flag this.

### Pitfall 3: Falloff distance measured from the wrong reference point

**What goes wrong:** D-02b says relief "fades to exactly 0 ... by the time it reaches the road's
paved edge." If the falloff distance is measured from the road **centreline** instead of the
paved **edge** (`halfWidthM` away), wide roads (primary class, up to ~7m wide per the real
compiled data) will show relief bleeding onto their shoulder even at a correctly-tuned falloff
distance, because the falloff "clock" started too early.

**Why it happens:** `road-geometry.ts`'s existing `computeEdgeRails` already solves "distance from
centreline to paved edge" (`halfWidth`) — a new relief-falloff implementation could easily
reinvent this incorrectly instead of reusing the existing per-edge `widthM`/2 value.

**How to avoid:** When computing `distanceToNearestRoadEdgeXZ`, subtract each edge's own
`widthM / 2` (or better: reuse `computeEdgeRails`'s already-computed `left`/`right` rail points as
the distance targets, not the raw centreline points) so the falloff genuinely starts at the paved
edge, matching D-02b's literal wording.

**Warning signs:** Wide primary/tertiary roads show visible relief bumps closer to the road than
narrow residential/track roads at the same nominal falloff-distance constant — a tell that
centreline distance, not paved-edge distance, is being used.

### Pitfall 4: `HEIGHTFIELD_SINK_M` dropped to exactly `0`

**What goes wrong:** Two coincident (exactly-touching, zero-gap) static Rapier colliders — the
road ribbon at y=0 and the heightfield grid at y=0 — can produce contact-solver jitter/z-fighting
at the boundary, a well-known category of physics-engine instability distinct from the "visible
elevation gap" problem this phase is fixing.

**Why it happens:** It is tempting to read D-01+D-02b's "gap becomes 0 by construction" as license
to set the sink to literally 0, conflating "no *visible/gameplay* gap" with "no *numerical*
separation needed at all."

**How to avoid:** Keep `HEIGHTFIELD_SINK_M` as a small nonzero constant (a candidate starting point
in the few-centimetres range, e.g. 0.05-0.15m) — its job changes from "bridge a real elevation
mismatch" to "a physics-contact safety margin," and should be documented as such (matching this
codebase's own established convention of a doc comment explaining exactly which failure mode a
constant brackets, per `SMOOTHING_WINDOW`'s and `HEIGHTFIELD_SINK_M`'s existing comments).

**Warning signs:** Only detectable by driving/playtesting (D-06's required re-verification
session) — jitter at the road/shoulder boundary, or a car resting slightly unstable off-road near
the pavement edge.

### Recomputing `lengthM` once `y` is constant

```typescript
// tools/map-compiler/graph/elevation.ts (or wherever the flat-elevation
// pass lives) -- 2D length is EXACT once every point shares one y value,
// unlike the old polylineLength3D which existed specifically because y
// varied. Simpler AND correct, not just simpler.
function polylineLength2D(points: readonly (readonly [number, number, number])[]): number {
  let total = 0;
  for (let i = 1; i < points.length; i++) {
    const dx = points[i][0] - points[i - 1][0];
    const dz = points[i][2] - points[i - 1][2];
    total += Math.sqrt(dx * dx + dz * dz);
  }
  return total;
}
```
