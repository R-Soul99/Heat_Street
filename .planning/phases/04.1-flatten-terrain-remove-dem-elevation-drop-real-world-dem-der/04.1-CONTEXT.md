# Phase 04.1: Flatten Terrain / Remove DEM Elevation - Context

**Gathered:** 2026-09-19
**Status:** Ready for planning

<domain>
## Phase Boundary

Replace real-world DEM-derived elevation (USGS 3DEP / Copernicus) in the map compiler and
runtime with hand-authored, deterministic flat terrain, keeping OpenStreetMap as the sole
source for road topology. This phase delivers: flat road elevation, a small capped procedural
off-road relief, updated/deleted shoulder-bridging machinery, an amended ADR 0001, and a
recompiled reference map area (Juliette, GA) that passes a full human drive-every-road
re-verification. It does NOT deliver a new target area, new race modes, or any Phase 5+
capability — this is a course-correction to Phase 4's compiled output only.

**Why now:** the current DEM elevation forces `src/core/shoulder-clearance.ts`'s per-point
road-shoulder ramps up to `TARGET_SHOULDER_WIDTH_M` (20m) in places to bridge the gap between
paved road and the sunk off-road heightfield (`HEIGHTFIELD_SINK_M` in
`tools/map-compiler/author/heightfield.ts`) — this reads as visually broken ("ridiculous").

</domain>

<decisions>
## Implementation Decisions

### Flatness target

- **D-01:** Roads are flat everywhere — every road node/point gets `y = 0` (or a single
  project-wide constant), not DEM-sampled, not smoothed. This removes the shoulder-bridging
  problem by construction rather than by a clamping/resolution algorithm: road and terrain meet
  at the same height because both start from the same flat baseline near the road.
- **D-02:** Off-road terrain is NOT perfectly flat — it gets a small, capped, procedural relief
  (not DEM-derived, not hand-placed) for visual texture in open areas away from roads.
  - **D-02a:** Cap amplitude: **±2m** (a starting/reasoned default — the user picked this over
    a ±5m option; both were explicitly offered, ±2m chosen as noticeably subtler).
  - **D-02b:** The relief fades to exactly 0 within the shoulder width, i.e. by the time it
    reaches the road's paved edge — this is the guarantee that a shoulder never bridges more
    than a trivial residual gap, not a real multi-metre cliff. Falloff mechanism/curve shape is
    Claude's discretion (smoothstep, linear, etc. — same category of design choice
    `SMOOTHING_WINDOW` was in Phase 4).
  - The exact amplitude/falloff-distance numbers are a REASONED DEFAULT, not committed to the
    same rigor as a feel-tuned constant — the user explicitly said Claude may retune ±2m
    empirically against the real compiled area the same way `SMOOTHING_WINDOW` and
    `HEIGHTFIELD_SINK_M` were tuned in Phase 4, if ±2m reads wrong once built.
- **D-03:** The height generator for the "dead flat" baseline (roads, and the off-road relief's
  zero-point) is a literal constant zero — no noise function, no per-area authoring needed for
  the flat baseline itself. Only the off-road relief (D-02) needs an actual generator (a
  deterministic, seeded low-amplitude function — e.g. simplex/value noise — Claude's discretion
  on the specific algorithm).

### Jumps & rolling terrain (resolves tension with Phase 4's own D-09)

- **D-04:** Phase 4 CONTEXT.md's D-09 ("terrain should include real rolling elevation/crests,
  tied to the Core Value's jumps callout") is superseded for the current area. Jumps now come
  from **two sources**: (a) primarily, Phase 2's already-proven hand-placed ramp mechanic
  (explicit convex-hull wedge ramps at deliberate spots — same mechanism verified in
  `02-06-SUMMARY.md` to produce a monotonic climb and airborne launch), and (b) secondarily, a
  small number of deliberately AUTHORED (not DEM-derived, not procedural) terrain crests at
  specific hand-picked spots for a "launch over the hill" moment closer to the original
  chase-movie reference. Both are explicit, deterministic, designer-placed — never sourced from
  real-world elevation data.
- **D-05:** D-09's original selection criterion (favor real towns with genuine rolling terrain
  when picking a target area) is RETIRED as the operative rule for the current/v1 area, but is
  explicitly NOT permanently ruled out — it's recorded as a possible criterion to revisit if a
  future v2 area is ever added. Don't delete D-09's reasoning from history; note it as
  superseded-for-now in the ADR amendment (D-08 below).

### Verification & ADR scope

- **D-06:** Once the flat-terrain area recompiles, a FULL re-run of the Phase 04-11
  drive-every-road SC1 human sign-off session is required — same bar as Phase 4's own
  completion, not just an automated-test-and-spot-check pass. Flat terrain removes the
  floating-road/skirt failure MODE, but the session should still confirm nothing else regressed
  (surface-type behavior, junction geometry, building collision, frame budget) on the
  regenerated geometry.
- **D-07:** Existing OSM-derived surface-type tagging (`edges[].surface`, the six-value closed
  enum) is UNCHANGED by this phase — surface types come from OSM `surface=*` tags via
  `road-graph.v1.md`'s mapping table, which is entirely independent of elevation. Nothing about
  gravel/dirt/tarmac grip or FX should need retuning as a result of this phase; if the
  re-verification session finds otherwise, treat it as a genuine new finding, not an expected
  consequence.
- **D-08:** `docs/adr/0001-map-data-source.md` is AMENDED IN PLACE (not superseded by a new
  separate ADR document) to reflect that elevation is no longer DEM-sourced — OpenStreetMap
  remains the frozen road/building topology source; only the elevation sub-decision changes.
  The amendment should preserve the original DEM reasoning as historical context (why DEM was
  chosen originally, why it's now being dropped) rather than deleting it outright, matching how
  ADRs in this project generally read (compare `docs/adr/0004`'s "what would justify revisiting"
  sections).

### Claude's Discretion

- Exact off-road relief noise algorithm/seed strategy (D-03).
- Falloff curve shape from ±2m relief down to 0 at the shoulder edge (D-02b).
- Whether/how much of `tools/map-compiler/graph/elevation.ts`'s existing machinery
  (`SMOOTHING_WINDOW`, `GRADIENT_WARNING_THRESHOLD`, `densifyEdgePoints`,
  `arcLengthMovingAverage`) survives vs. gets deleted — likely most of it becomes dead code once
  roads are flat, but the researcher/planner should confirm nothing else depends on it before
  deleting.
- Whether `src/core/shoulder-clearance.ts`'s per-point building-aware width resolution is still
  needed at all once shoulders are trivial-width, or can collapse to a much simpler fixed-width
  ramp — the building-clearance clamping logic may no longer be load-bearing.
- Exact new/retained value of `HEIGHTFIELD_SINK_M` (may drop to ~0, or a small residual margin
  for floating-point/physics-contact safety).
- Number and placement of the "authored terrain crests" from D-04b — not discussed in detail;
  Claude/researcher should propose specific candidate spots against the real Juliette, GA
  geometry for the next discussion or the planner to lock down.

</decisions>

## Existing Code Insights

### Reusable Assets
- Phase 2's ramp mechanic (`02-06-SUMMARY.md`) — reused as-is for D-04's primary jump source,
  no changes needed to the ramp collider approach itself.
- `road-graph.v1.md`'s surface-type mapping and `src/core/surface-types.ts` — entirely
  unaffected by this phase (D-07); do not touch.

### Established Patterns
- Phase 4 already established the pattern of "reasoned-default constant, retuned empirically
  against the real compiled area, documented with a doc comment explaining the failure modes it
  brackets" for exactly this kind of value (`SMOOTHING_WINDOW`, `HEIGHTFIELD_SINK_M`,
  `TARGET_SHOULDER_WIDTH_M`, `GRADIENT_WARNING_THRESHOLD` all follow this). D-02a's ±2m relief
  cap and D-02b's falloff curve should follow the same documented-constant convention.
- Phase 4's own ADR practice (`docs/adr/0004`) is the template for how D-08's amendment to ADR
  0001 should read — preserve original reasoning as history, add new reasoning for the change,
  note what would justify revisiting again.

### Integration Points
- `tools/map-compiler/cli.ts` is the single compiler entry point that calls both
  `applyElevation` (or its replacement) and `buildRoadShoulders` — likely the file that most
  directly reflects whatever the new elevation stage looks like end to end.
- The compiled `.map.json`/`.glb` for Juliette, GA (`public/maps/juliette-ga.map.json` or its
  successor) must be regenerated; every consumer of `edges[].points`' `y` values downstream
  (physics colliders, render mesh, minimap) inherits the flat values automatically once the
  compiler changes — no separate runtime change expected beyond the compiler and the two
  shoulder/heightfield files above.
