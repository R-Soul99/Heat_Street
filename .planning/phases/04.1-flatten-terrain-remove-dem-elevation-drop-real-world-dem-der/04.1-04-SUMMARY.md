# Phase 04.1 Plan 04: Replace DEM Heightfield with Seeded Off-Road Relief Summary

**`buildOffRoadRelief` replaces DEM-sampled `buildHeightfield` with a pure, seeded two-octave value-noise generator capped at +/-2m and gated to exactly 0 at every road's paved edge, with the unchanged verified Rapier grid shape and a `HEIGHTFIELD_SINK_M` reduced from a 4.5m elevation-bridging offset to a 0.1m physics-contact margin.**

**2. [Rule 3 - Blocking] Deleting `buildHeightfield` broke two out-of-scope test files**

- **Found during:** Task 1 verification (`npx tsc --noEmit`)
- **Issue:** The plan's own `<action>` text states "`collision.ts`, `gltf.ts` ... need no change at all" since they "consume `HeightfieldGrid` by shape." That claim is correct for the production files themselves, but `collision.test.ts` and `gltf.test.ts` (not listed by the plan, and not mentioned in its `<code_context>`) each called `buildHeightfield` directly as a fixture constructor for a flat, constant-value ground plane. Removing `buildHeightfield` broke both files' compilation, which would have caused Task 1's own acceptance criterion ("`npx tsc --noEmit` reports errors ONLY in `tools/map-compiler/cli.ts`") to fail.
- **Fix:** Added a small local `makeFlatHeightfield` helper to each file that constructs the `HeightfieldGrid` object literal directly (no DEM, no `buildOffRoadRelief` noise) -- preserving the exact-flat-value fixture these files' own building-grounding math assertions require, without touching `collision.ts`/`gltf.ts` production code at all. `collision.test.ts` additionally needed one assertion's `toBeCloseTo` precision lowered from 6 to 4 decimal places: lowering `HEIGHTFIELD_SINK_M` shifted the expected value `100 - sinkM` from `95.5` (exactly representable in a `Float32Array`) to `99.9` (not exactly representable), and the tighter 6-decimal tolerance could not absorb the resulting ~1.5e-6 float32 rounding error. This matches an identical, already-documented precedent in this same codebase (`heightfield.test.ts`'s own historical "Precision 4, not 6 ... f32's ~7-digit relative precision" comment, and `tests/map-scene.test.ts`'s equivalent note).
- **Files modified:** `tools/map-compiler/author/collision.test.ts`, `tools/map-compiler/author/gltf.test.ts`
- **Verification:** `npx vitest run tools/map-compiler/author/collision.test.ts tools/map-compiler/author/gltf.test.ts` -- 23/23 passing; `npx tsc --noEmit` confined to `cli.ts` only after this fix
- **Committed in:** `8847556` (Task 1 commit)

**3. [Rule 1 - Bug] `reliefAt` returned `-0` instead of `0` at the paved edge**

- **Found during:** Task 2, first test run
- **Issue:** `noise * RELIEF_AMPLITUDE_M * falloff` produces IEEE-754 `-0` when `falloff` is `0` and `noise` is negative. This is numerically equal to `0` but fails a strict `toBe(0)`/`Object.is` test assertion, which the plan's own acceptance criteria require ("exact equality, not a tolerance") for D-02b's guarantee.
- **Fix:** `reliefAt` now special-cases `falloff === 0` to `return 0` (the literal, positive zero) before computing the noise term at all.
- **Files modified:** `tools/map-compiler/author/heightfield.ts`
- **Verification:** `npx vitest run tools/map-compiler/author/heightfield.test.ts -t "returns exactly 0"` passes; re-verified via mutation testing (see Issues Encountered) that removing this guard AND the falloff multiplier together makes the test fail as expected, confirming the guard is load-bearing and not accidentally masking a real bug
- **Committed in:** `8847556` (Task 1 commit)
