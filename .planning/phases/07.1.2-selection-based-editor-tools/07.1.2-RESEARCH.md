## Summary

This phase is almost entirely in-repo refactoring; no packages are installed. Three things carry the risk. (1) D-23 is a real, reproducible bug with a one-line-class fix: the road "hold" mask is a disc of radius `max(halfWidth, cell*sqrt2)` around the centreline, which does not enclose the terrain triangles under the road's lateral edge, so free vertices just outside the disc move (up to a full slope-limiter step) and tilt the triangles the road edge sits on. I reproduced it headless (road edge height moved 0.84 m at the default 35 degree limit and 5.6 m at 80 degrees on a 7 m road with 3 m cells, centreline untouched) and verified that holding every vertex of any cell the road touches (8-neighbour dilation of the current mask) drives the edge shift to 0.0000 for four width/cell combinations even at 80 degrees. (2) The selection model changes from one `CellWindow` to a cell mask, which touches the dispatcher, the outline renderer, push/pull, and road cutting; build it as a pure core module first. (3) The shell change (bottom toolbar and dock removed, floating toolbar added) touches both editors, and the map editor has one silent coupling to `.shell-toolbar-bottom`.

Everything else reuses existing, tested machinery: `runHeightOp` (hold + limiter + one-diff recorder) for every height operation, `setWindowFromBase` for hold-to-repeat and Alt push/pull, `smoothRegion` for Smooth, `paintSurface` for Terrain fill (already skips road-flagged pixels), `setRoadLock` for Lock/Unlock, and `eraseGraphDisc` as the template for the cut-at-selection-edge geometry (generalise its splitter). The 07.1.1 test pattern (pure data modules + node vitest, no DOM) continues to apply; vitest 5.0.0 node env works (174 tests in the touched dirs pass in 1.8 s).

**Primary recommendation:** Do the D-23 fix first as its own plan (opt-in `padM`/dilation on `roadVertexMask` used only by sculpt ops, default unchanged so the golden test stays green), then build the pure `CellMask` + mask-aware operations in core/dispatcher, then the toolbar/shell, then the map editor, with Wave 0 test files created up front.

### Pattern 1: Selection as a cell mask
**What:** `CellMask { rows, cols, data: Uint8Array(rows*cols) }` indexed by cell (a cell is the quad between vertices r..r+1, c..c+1). Drag box -> `windowBetween` (already guarantees >= 1 cell, clipped) -> cells `[minRow,maxRow) x [minCol,maxCol)`. Plain drag: clear then add. Shift: add. Ctrl: subtract. Derived: `vertexMask()` = vertices that are a corner of any selected cell (this is what height ops write), `bounds()` = vertex `CellWindow` for `runHeightOp`, `cellAtXZ(x,z)` for road cutting, `boundarySegments()` = edges between selected and unselected cells for the outline.
**When to use:** all selection state. Max grid is 4,000,000 vertices (`MAX_TERRAIN_VERTICES`), so one byte per cell is at most about 4 MB.
**Why not a rect list:** Subtract needs polygon boolean and the outline of an L-shape or one with a hole is a polygon-union problem; with a bitmask it is a one-pass edge scan. [ASSUMED design recommendation; the storage choice is in Claude's Discretion.]

### Pattern 2: Every height operation goes through `runHeightOp`
`runHeightOp(grid, touched, compute, rec, relax, opts)` already: skips road-masked vertices (`hold`), records a first-touch window for undo, expands the window for the slope limiter, freezes pre-existing steep pairs, and runs `limitSlope` with road vertices as fixed sources. Mask operations should be thin wrappers that pass the mask bounds as `touched` and make `compute` return `h` for vertices not in `vertexMask()` (exact same way smoothRegion and setWindowFromBase already work). Do not add a second write path; D-13/D-23 then hold for free. [VERIFIED: src/core/terrain-brush.ts lines 224-347]

### Pattern 3: Hold-to-repeat = push/pull with a stepped delta
`raiseSelection` today does `raiseWindow` (`h + step`) per click and pushes one undo diff per call. For hold-to-repeat that gives N undo steps and slope-limiter ratcheting (the source comment on `setWindowFromBase` documents the ratchet). Instead: on pointerdown of Raise/Lower take `snapshotWindow(bounds)` once (as `beginPushPull` does), each repeat tick sets `setWindowFromBase(base, deltaM += sign*step)` into one shared recorder, and commit one undo entry on release. This is exactly the existing push/pull machinery (`beginPushPull`/`pushPullTo`/`endPushPull`), driven by timer ticks instead of mouse Y. [VERIFIED: tool-dispatch.ts lines 904-948; terrain-brush.ts 513-542]

### Anti-Patterns to Avoid
- **A second hold computation for selection ops.** Use `heightOpOptions(area, options)` for every operation, or D-13 and D-23 diverge.
- **Changing `roadVertexMask` default behaviour.** `tests/terrain-road-lock-golden.test.ts` and `tests/terrain-road-lock.test.ts` pin it; road strokes (`applyRoadStroke`, `regradeInto`, `limitAroundBand`) also use it as "protect" and extra padding would produce spurious road-violation warnings near junctions. Add an opt-in parameter instead.
- **Relying on `.shell-toolbar-bottom` selectors.** The map editor measures it (see Pitfall 5).
- **Setting `selection` per mode.** One shared mask, persists across modes (D-06).

## D-23: Locked-road warp, root cause and fix

### Reproduction (headless, node)
Script run in the scratchpad against the real dispatcher: straight road, raise brush (radius 15 m, 60 clicks) centred 14 m beside the road. Centreline height stayed 0.000 in all runs.

| Cell | Road width | Slope limit | Max road-EDGE height shift (at lateral = width/2) |
|------|-----------|-------------|---------------------------------------------------|
| 3 m | 7 m | 35 deg (default) | 0.84 m at the near edge (vertex beyond hold moved 2.10 m) |
| 3 m | 7 m | 80 deg | 5.64 m |
| 3 m | 10 m | 80 deg | 12.69 m |
| 2 m | 6 m | 80 deg | 9.38 m |
| 1 m | 6 m | 80 deg | 3.97 m |

[VERIFIED: ran against the repo code, 2026-11-14]

### Root cause
`roadVertexMask` (src/core/terrain-road.ts:518) holds (a) vertices whose paint pixel has `PAINT_ROAD_FLAG` and (b) every vertex within `roadLevelRadiusM(halfWidth, cell) = max(halfWidth, cell*sqrt2)` of a graph edge polyline (`roadVertexMaskFromGraph`). `heightOpOptions` (tool-dispatch.ts:191) feeds exactly that to `runHeightOp` and the slope limiter. The radius is justified in its comment as "whole triangles under the centreline (D-06)", which is true for the centreline but not for the road edge:

- The road surface (painted pixels, rendered road, and the ground the car drives on) extends to lateral distance `halfWidth`.
- A point at lateral distance `halfWidth` lies in a terrain cell whose four corners can be up to `cell*sqrt2` farther out, i.e. at lateral distance up to `halfWidth + cell*sqrt2`.
- Held radius is only `max(halfWidth, cell*sqrt2)`. For half=3.5 m, cell=3 m: held 4.24 m, but corners reach 7.74 m. Corner vertices between 4.24 m and 7.74 m are free.
- Free vertices next to the held ring are legal sources for the sculpt and are only limited by the slope limiter relative to the held vertex: up to `tan(limit)*cell` per cell (2.10 m at 35 deg, 3 m cell; up to many metres at 80 deg). Terrain under the road edge is the bilinear/triangle interpolation across held and free vertices, so the edge tilts or rises.

Not the cause (checked): smoothing across the held boundary (held vertices are never written: `runHeightOp` returns `old[k]` for held, `smoothRegion` copies held through every pass); the slope limiter writing held cells (`relax()` returns early on `mask[i]`); `tool-dispatch` choosing the wrong set (it correctly passes locked roads, and `free` only subtracts unlocked ones). `freezePreexistingSteep` and the limiter ring are not involved. The unlocked-zone subtraction (`zone` padded by one paint pixel) is only relevant when roads are unlocked.

### Proposed fix
Hold every vertex of every cell the road touches, for sculpt operations only.
1. Add an opt-in parameter to `roadVertexMask(grid, paint, graph, area, free?, padM = 0)`. For locked-edge ownership use `roadLevelRadiusM(half, cell) + padM` where sculpt callers pass `padM = cell * Math.SQRT2` (equivalently `half + cell*sqrt2`), and dilate the paint-derived mask by one vertex (8-neighbour) when `padM > 0`. Keep the unlocked `zone` subtraction logic, but use `padM + paint.metresPerPixel` for the zone pad so an unlocked road is still released.
2. `heightOpOptions` passes the padded mask. Road tools (`applyRoadStroke`, `regradeInto`, `limitAroundBand`) keep `padM = 0`.
3. Prototype used for verification: take `roadVertexMask(...)` and OR in all 8 neighbours of every held vertex. Result: max edge shift **0.0000** at 80 deg limit for (3 m, 7 m), (3 m, 10 m), (2 m, 6 m), (1 m, 6 m). [VERIFIED: ran against repo code]
4. Side effect to accept and surface: a ring about one cell wider beside every locked road is now untouchable by sculpting; `heldStatus` messaging already covers "vertices did not move".

Cost note: the unlocked-road "zone" logic means unlocking a road still frees its vertices, so the "Unlock to move it" workflow (D-13) is unchanged.

## Selection operations on a mask

What exists [VERIFIED: tool-dispatch.ts 549-967, terrain-brush.ts]:
- `selection: CellWindow | null` (single vertex window); `raiseSelection(sign)` -> `raiseWindow` (+/- `selectStepM`, sharp, no relax); `beginPushPull/pushPullTo/endPushPull/cancelPushPull` use `snapshotWindow` + `setWindowFromBase`; `smoothRegion(grid, window, {strength,passes}, rec, opts)` already multi-pass with held vertices and one diff; `flattenBrush(grid, params, targetM, ...)` is a disc brush; `paintSurface` is disc-based; `raiseBlock`/`blockWindowAt`/`stampTerrain` go away (D-17).

Needed (all expressible as `runHeightOp` wrappers):
- **Raise/Lower**: `setWindowFromBase(bounds, base, delta)` with `compute` returning `h` where `!vertexMask`. Hard step comes from `relax = false` (already). **Caveat:** the slope limiter still runs, so a step larger than about `tan(limit)*cell` (2.1 m at 35 deg / 3 m cells) is clamped by lowering the selection or raising neighbours, i.e. a true cliff cannot form above the limit. CONTEXT says "a cliff forms at the edge". Either accept (limiter is an editor-wide rule and the Slope limit field is in the sidebar; Step max is 5 m) or add an explicit "no limiter for selection steps" option. Needs a user decision; default recommendation: keep the limiter and tell the user via the existing `slopeClamped` status.
- **Flatten to average**: target = mean height of `vertexMask` vertices (read before write); compute returns `target` for selected, un-held vertices. Decision needed: whether locked-road vertices inside the selection count toward the average (they stay put). Recommendation: include all selected vertices so the result is the true average of what the user sees; document in the tooltip.
- **Smooth, one pass**: extend `smoothRegion` with an optional `selected?: (row,col)=>boolean`; unselected vertices are treated as held in the pass (same code path as the road mask). `passes: 1`, strength = Select-mode Strength. Hold repeats = repeated clicks; group repeats into one undo entry using `mergeDiffs` (exists in tool-dispatch.ts, line 304) or the shared recorder.
- **Terrain fill**: for each paint pixel whose centre is in a selected cell, `paintSurface`-style write skipping road-flagged pixels (keeps D-13 for paint). Implement as `paintMask(paint, mask, grid, surface, rec)` using `beforePaintWrite(rect)` for the mask's pixel bounds.
- **Status and held counts** reuse `heightResult`, `heldStatus`, `slopeClampHint`.

Outline: replace the single `LineLoop` (`selectionOutline`, `setOutline`, `windowPerimeter` in editor.ts ~340-390) with a `LineSegments` fed by `CellMask.boundarySegments()` lifted onto terrain heights; a second, fainter material (opacity ~0.35) for Brush mode (D-06). Keep the cyan drag-preview box as is (`selectionPreview`).

## Road graph operations on a selection

How roads are represented [VERIFIED: src/core/road-graph.ts 66-110]: `RoadGraph { nodes[{id,x,y,z,junction}], edges[{id,from,to,points:[x,y,z][],lengthM,widthM,surface,...}] }`. Edge ids are stable and never reused (`nextEdgeId` monotonic). Lock state = `area.unlockedEdgeIds` (list of UNLOCKED edge ids; empty = all locked). Road paint = `PAINT_ROAD_FLAG` bit per paint pixel, separate from the graph.

- **Edges inside the mask** (for Lock/Unlock): `edgeIdsInMask(graph, mask)` = edges with any polyline segment passing through a selected cell (sample at grid-line crossings, test midpoints). Whole edge is locked/unlocked even if only partly inside. Open question below. Feed to `setRoadLock(area, ids, locked)`; it already returns a single diff and re-grades stale roads before locking. `lockAll` in the dispatcher shows the wrapper pattern (`commitLockDiff`).
- **Delete road with cut (D-15)**: `eraseGraphDisc` (terrain-graph.ts 853-928) is the exact template: refine each polyline at boundary crossings (`refineAgainstDisc`), keep runs of "outside" segments, first surviving piece keeps the id, later pieces get fresh ids (`splitFrom`), cut ends become new dead-end nodes (`osmNodeId: 0`), then `withJunctionFlags` + `compactInternal`. Generalise by extracting the splitter: replace the disc-specific `refineAgainstDisc` with a function `(pts) => { pts, keep[] }`. For a cell mask the refinement inserts points where each segment crosses vertical grid lines `x = originX + k*cell` and horizontal ones `z = originZ + k*cell` (sorted by parameter t, with `lerp3` so heights interpolate and gradient is preserved), and `keep[i] = !mask.cellAtXZ(midpoint)`. Because selection boundaries lie on grid lines, crossings on grid lines are sufficient (no polygon clipping). Keep `eraseGraphDisc` as a thin caller of the shared function so its tests keep passing.
- **Paint**: also clear `PAINT_ROAD_FLAG` for pixels whose centre lies in a selected cell (reset to `area.groundSurface`), as `eraseRoad` does for discs, so the road texture matches the graph. Heights are not touched (D-15 in the original eraseRoad).
- **Undo as one step**: use one `StrokeRecorder` (`beforePaintWrite`, `recordGraph`, `recordLock` via `carryLock`) and `rec.commit()` as in `eraseRoad` (terrain-road.ts 1011-1061). `ensureDefaultSpawn` after erasing (as eraseRoad does).

## Common Pitfalls

### Pitfall 1: D-23 fix leaks into road drawing
**What goes wrong:** Padding `roadVertexMask` globally makes new road strokes and re-grade see a wider "protect" ring, producing spurious "slope limit reached" warnings near junctions and changing the golden test.
**How to avoid:** `padM` defaults to 0; only `heightOpOptions` opts in. Run `tests/terrain-road-lock-golden.test.ts` unchanged.
**Warning signs:** golden test diffs; road violations warnings on previously clean strokes.

### Pitfall 2: Slope limiter eats the hard step
**What goes wrong:** D-08 expects a hard cliff, but `limitSlope` (default 35 deg, editable 5-80) re-grades steps steeper than `tan(limit)*cell`. A 5 m step on 3 m cells is 59 degrees.
**How to avoid:** Decide explicitly (keep limiter + status, or bypass for selection steps); test both the sub-limit exact step and the clamped case.

### Pitfall 3: Undo explosion on hold-to-repeat
**What goes wrong:** One undo entry per tick (50-entry stack cap in `createUndoStack(50)`), and incremental `h + step` ratchets under the limiter.
**How to avoid:** One recorder per hold using the base-snapshot + cumulative delta pattern; commit on release/blur/Esc. Cancel on `window` blur like the stepper does.

### Pitfall 4: Selection stored in vertex vs cell coordinates
**What goes wrong:** The old selection is a vertex `CellWindow` (`minRow..maxRow` inclusive vertices, at least one cell). Mixing "vertex inclusive" and "cell exclusive" produces off-by-one writes and wrong road cuts.
**How to avoid:** One convention: mask is per cell; vertex set = corners; convert `windowBetween` output once. Unit-test a 1x1-cell selection (4 vertices) and an L-shape.

### Pitfall 5: Removing the bottom toolbar breaks hidden consumers
**What goes wrong:** `.shell-toolbar-bottom` is referenced in map-editor/editor.ts; `splitDockTools`, `groupTools`, `displayLabel` are used by `createShell` and shortcuts dialog; `shell.setToolEnabled`/`setActiveTool` flow drives sidebar title via `options.tools`. CSS rules for `.shell-toolbar-bottom`, `.sidebar-pair` become dead.
**How to avoid:** grep for each removed export before deleting; keep the shortcuts dialog source of truth (it iterates `options.tools` for `keyLabel`), so the floating toolbar's buttons must still be listed there.

### Pitfall 6: Lock/regrade workflow loses its UI
**What goes wrong:** Removing the Lock tool drops "Re-grade selected", "Re-grade all unlocked", "Lock all/Unlock all", the per-road hover status, and Shift+click road selection (`selectedEdgeId`). The save guard still refuses saves with stale unlocked roads, so the user could be stuck.
**How to avoid:** Re-home these (e.g. Lock/Unlock sidebar section "Re-grade unlocked" button, lock overlay stays always on) and keep `staleRoadBlockMessage` text pointing to controls that exist.

### Pitfall 7: Stale saved tuning (known project issue)
**What goes wrong:** localStorage override hides new defaults (memory note `tuning-localstorage-override`). New per-mode option defaults may not appear.
**How to avoid:** If options are persisted, namespace new keys and ignore unknown/removed keys; note it in UAT.

### Pitfall 8: Pointer vs Alt focus
**What goes wrong:** Alt keyup moves focus to the browser menu, the canvas stops receiving key events; Alt+click can start window drag on some platforms.
**How to avoid:** `preventDefault` on Alt keydown/keyup; verify manually (see UAT).

### Mask-aware operation wrapper
```ts
// src/core/terrain-brush.ts (new) - same pipeline as setWindowFromBase
export function setMaskFromBase(
  grid: TerrainGrid, mask: CellMask, base: Float32Array, bounds: CellWindow,
  deltaM: number, rec?: StrokeRecorder, opts?: HeightOpOptions,
): BrushResult {
  const sel = mask.vertexMask(grid);               // Uint8Array, heights indexing
  const stride = grid.rows + 1, rowsN = bounds.maxRow - bounds.minRow + 1;
  return runHeightOp(grid, bounds, (x, z, h) => {
    const col = Math.round((x - grid.originX) / grid.cellSizeM);
    const row = Math.round((z - grid.originZ) / grid.cellSizeM);
    if (!sel[row + col * stride]) return h;
    return base[row - bounds.minRow + (col - bounds.minCol) * rowsN] + deltaM;
  }, rec, false, opts);   // opts = heightOpOptions(...) so roads hold + limiter apply
}
```
