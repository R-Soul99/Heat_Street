# Phase 04.3 Part 3: Code Review Report

**Depth:** standard. All 16 files read in full. Cross-checked against `src/core/heading.ts`, `src/core/tuning-snapshot.ts`, `src/core/terrain-road.ts`, `src/core/terrain-brush.ts`, `tools/map-compiler/sources/overpass.ts`, `tools/terrain-editor/new-area.ts`, `src/debug/debug-gate.ts` and `package.json`.

## Summary

No crashes on malformed saved data were found. The localStorage and import paths all go through `parseSaved*` / `parseTuningSnapshot`, and map artifact failures route to the on-screen error. The generators are deterministic: no `Math.random` or `Date` in `playground-layout.ts`, `proving-ground.ts`, `generate-playground.ts`, `convert.ts` or `author-feel-test-routes.ts`.

The tool dispatcher's undo and diff merging held up under tracing. `roadVertexMask` returns a fresh grid-sized array, so the block-tool mask mutation is safe.

The real defects are:
- a key collision in the debug build,
- two CLI argument and cache hazards,
- a heading convention mismatch in the route author,
- non-atomic artifact writes (CLI and editor save).

## Warnings

### WR-01: `G` is bound to both the tuning panel and "repeat last station launch"

**File:** `src/main.ts:892` and `src/debug/test-stations.ts:175`
**Issue:** `onDebugKey("KeyG", () => panel.toggle())` (main.ts:892) and the raw keydown listener in `createTestStations` (`e.code === "KeyG"` -> `go(last)`, test-stations.ts:175) both fire on the same keypress. Both listeners are on `window` and neither stops the other. The same collision affects the other `KeyG` documentation in the module header ("G repeats the last launch").

Scenario: open `?map=feel-test&debug` (or any terrain map that has a `*.stations.json`) and launch station 3. Press `G` to open the tuning panel. The panel opens, and the car is teleported back to the station pad at the chosen speed, mid-tuning session. Opening the panel after any launch always resets the car.

**Fix:** Rebind one of them. For example, change the repeat key in `test-stations.ts` to `KeyV`/`Enter`, or have the stations listener skip `KeyG` when `DEBUG_ENABLED`. Update the header comment and the on-screen hint (`[G] repeat`) with the new key.

### WR-02: `author-feel-test-routes.ts --area` with no value silently rewrites the feel-test routes and medals

**File:** `tools/map-compiler/synthetic/author-feel-test-routes.ts:91-92`
**Issue:** `AREA = AREA_FLAG === -1 ? "feel-test" : (process.argv[AREA_FLAG + 1] ?? "feel-test")`. If `--area` is the last argument, the script falls back to `feel-test` instead of failing. Compare `compile-map`'s `parseAreaArg`, which errors in the same case.

Scenario: `node ...author-feel-test-routes.ts --area $AREA` with an empty `$AREA` in a script or npm wrapper. The command succeeds and overwrites `public/maps/feel-test.routes.json` and `feel-test.medals.json`. Those files hold hand-recorded medal references (commit f1cfeba re-records them from human runs), so the overwrite replaces them with a synthetic `AVERAGE_SPEED_MPS = 14` estimate.

**Fix:**
```ts
const AREA_FLAG = process.argv.indexOf("--area");
const rawArea = AREA_FLAG === -1 ? "feel-test" : process.argv[AREA_FLAG + 1];
if (rawArea === undefined || !Object.hasOwn(AREA_ROUTES, rawArea)) {
  throw new Error(`unknown or missing --area value: ${String(rawArea)}`);
}
const AREA = rawArea;
```
Also consider refusing to overwrite an existing `*.medals.json` without `--force`.

### WR-03: Route author writes an x-mirrored yaw, contradicting the repo's documented convention

**File:** `tools/map-compiler/synthetic/author-feel-test-routes.ts:183`
**Issue:** `headingRad = Math.atan2(next.x - startNode.x, -(next.z - startNode.z))`. `src/core/heading.ts:86` documents the round-trip-correct yaw as `yawFromTravelDirection(dx, dz) = atan2(-dx, -dz)`, since forward = (-sin h, -cos h). The authored value has the wrong sign on x.

Evidence from the generated artifacts: `public/maps/playground.routes.json` has p2p start `0.0598` for a north-going leg (correct is `-0.0598`). The circuit start is `1.657`, a leg that runs east along the ring top. Under `forwardFromYaw`, 1.657 gives forward = (-0.996, +0.08), which is west, the opposite of the first leg. The east/west component of the heading is inverted. North-south headings only err by a few degrees, so the bug is invisible for p2p but large for the circuit.

`course.start.headingRad` is consumed as a yaw by `checkpoint-pose.ts:94-96` (fallback reset heading) and seeds `race-state.ts:72/186`. The same formula appears in `author-grid-routes.ts:149`, `author-newton-routes.ts:136` and `build-graph.ts:677`, so this is a systemic pre-existing pattern that this phase extends to the playground. I could not confirm which consumer observably misbehaves. The heading.ts DEVIATION comment suggests the team already hit this once and fixed only the library side.

**Fix:** Import and use the shared helper, then re-author the committed routes:
```ts
import { yawFromTravelDirection } from "../../../src/core/heading.ts";
const headingRad = yawFromTravelDirection(next.x - startNode.x, next.z - startNode.z);
```
(Normalising the vector is not required if `atan2` is used directly.) Re-run `author-playground-routes` and re-check `feel-test`.

### WR-04: `compile-map --area playground` (or `--refresh`) silently replaces the synthetic map with real OSM data

**File:** `tools/map-compiler/cli.ts:393-397`, `tools/map-compiler/areas/playground.config.ts:15-24`
**Issue:** The playground is synthetic. Its "OSM" cache is written by `generate-playground`, and `osmExtract` is `synthetic://...`. `loadOrFetchArea` has no notion of a synthetic area. On a cache miss, or whenever `bbox` differs, or with `--refresh`, it queries the real Overpass endpoint for the bbox (33.0, -84.0, rural Georgia) and overwrites `areas/playground.raw-osm.json` / `playground.raw-buildings.json` (overpass.ts:305-326).

Scenario: a fresh checkout, or a bbox tweak, followed by `npm run compile-map -- --area playground` without first running `generate-playground`. A "playground" is compiled from real roads and buildings. If the user ran `--refresh`, the synthetic cache is destroyed and must be regenerated. The playground tests and `author-playground-routes` (hard-coded ring coordinates, `bestD > 5` check) then fail with a confusing "no node within 5 m" error.

**Fix:** Add a `synthetic?: true` flag to `AreaConfig`, set it for `playground` (and `feel-test`, `grid-test`), and have `main()` in cli.ts refuse `--refresh`. It should also fail with "run generate-X first" when the cache is missing, instead of calling `loadOrFetchArea`'s network path.

### WR-05: `compile-map` writes `<area>.map.json` before later stages that can still fail

**File:** `tools/map-compiler/cli.ts:471-474` (write), later failure points at 490, 530-534, 585-594
**Issue:** `map.json` is written at line 473. Afterwards `decodeGreyPng` (readFile / PNG decode), `buildRealRelief`, `buildMapCollision`, `parseMapCollision` (the self-check) and `writeGlb` can still throw. The header promises "a failing map is never written", but that only holds for the validation gate.

Scenario: a bad `heightmap.file` path or a self-check failure leaves a new `*.map.json` beside the old `*.collision.json` / `*.glb`, with the process exiting 1. `main.ts` then loads graph/collision/glb that disagree, with node ids and building sets from different compiles. For terrain maps, `convert-terrain` reads that mismatched pair.

**Fix:** Build every artifact string or buffer in memory first (graph JSON, collision JSON, glb document), then write all files at the end. Write each file to a temp name and rename.

### WR-06: Terrain editor save writes the sidecar before the binary with no rollback, so a failed second PUT leaves a mismatched pair

**File:** `tools/terrain-editor/editor.ts:398-399`
**Issue:** The WR-07 comment argues the order protects the old pair "if the server rejects the sidecar". That covers only the first PUT. If the second PUT (`bin`) fails (network drop, disk error, dev-server restart), the sidecar (graph, crests, objects, buildings) is the new one while `*.terrain.bin` (heights, paint) is the old one. The sidecar has no checksum or revision link to the bin (grep of `terrain-format.ts` shows none), and `loadTerrainArea` only checks structural sizes.

Scenario: road edits are saved as sidecar and graph but the levelled heights and paint are lost. The map loads without error, with graph edges floating over unlevelled terrain. The editor reports "Save failed ... Your edits are still in memory", which is true, but the user then closes the tab thinking the on-disk state is unchanged.

**Fix:** Have the plugin accept both halves in one request (multipart or a single JSON/base64 envelope) and commit via temp-file rename. Or write a content hash of the bin into the sidecar and verify it in `loadTerrainArea`.

## Info

### IN-01: Post-save `refreshAreaList` failure is reported as "Save failed"

**File:** `tools/terrain-editor/editor.ts:409-415`
**Issue:** After both PUTs succeed and `setDirty(false)` has run, `await refreshAreaList(...)` is still inside the `try`. If `/__terrain/areas` fails, the catch shows "Save failed ... edits are still in memory" and `save()` returns false. That aborts `driveHere` even though the save succeeded and the dirty marker was already cleared.
**Fix:** Move `refreshAreaList` into its own `try/catch` (log only) and return `true` regardless.

### IN-02: Global editor shortcuts ignore focused `<select>`, so `D` can save and open a tab

**File:** `tools/terrain-editor/editor.ts:1092-1136`
**Issue:** The `typing` guard covers only text/number inputs and textareas. After choosing an area in `#area` (which, unlike the option selects, is never blurred), pressing `D` runs `driveHere()`. That calls `save()` (a disk write) and `window.open`. Likewise `E`, `H` and so on switch tools while a select has focus.
**Fix:** Treat `HTMLSelectElement` (and `isContentEditable`) as typing targets, or `blur()` `#area` after `change`.

### IN-03: `loadArea` has no staleness check between the discard prompt and install

**File:** `tools/terrain-editor/editor.ts:324-342`
**Issue:** `confirmDiscard()` runs before two awaited fetches. Edits made while the fetches are in flight, or a second faster `loadArea` call, are replaced by `installArea` without another prompt. A slower first load can also overwrite a later one.
**Fix:** Keep a load token (`const my = ++loadSeq`) and bail if it changed. Re-check `dirty` just before `installArea`.

### IN-04: Editor render loop has no error isolation

**File:** `tools/terrain-editor/editor.ts:1159-1165`
**Issue:** `requestAnimationFrame(frame)` is the last statement. Any exception from `terrainView.updateTextures` or `renderer.render` (for example from a malformed loaded area) permanently freezes the viewport while the DOM stays live.
**Fix:** Schedule the next frame first, or wrap the body in `try/catch` and log once.

### IN-05: Dead field and unsynced option state in the tool dispatcher

**File:** `tools/terrain-editor/tool-dispatch.ts:279`, `:599-601`, `:455`
**Issue:**
- `Stroke.removedAny` is written (line 378) but never read.
- A mound-stamp drag writes `options.stampWidthM`/`stampLengthM`, but only height and width are wired to DOM inputs and neither is refreshed. The panel shows a stale width until the next input event.
- The preset validity check `ROAD_PRESETS[patch.roadPreset] === undefined` passes for inherited keys such as `"constructor"`. The DOM only supplies real preset ids, so this is theoretical.
**Fix:** Remove `removedAny`. Return the changed options in `ToolResult` so the editor can resync inputs. Use `Object.hasOwn(ROAD_PRESETS, id)`.

### IN-06: Tuning-panel import chain has no `.catch`

**File:** `src/debug/tuning-panel.ts:895-948`
**Issue:** `file.text().then(...)` has no rejection handler, and the apply sequence is not exception-safe. `parseTuningSnapshot` guarantees fully populated domains, so `writeLeavesOnto` itself is safe. But `handlers.onApplyVehicle()` calls `scene.setTuning`, which can throw. If it does, the surfaces and camera domains are skipped, the controllers are not refreshed, and nothing is persisted (`persistAll` is skipped). The panel then shows stale values against a half-applied tune, with only an unhandled rejection in the console. Note also that `parseSavedTuning(JSON.stringify(...))` fills missing leaves from the RWD `defaultTuning()`, not the active class base, so importing a partial file under `?car=fwd` mixes RWD leaves into the class.
**Fix:** Append `.catch(() => flashImportFailure())` and call `updateDisplay()` / `persistAll()` in a `finally`.

### IN-07: Drive logger activates while a `<select>` has focus; download URL revoked immediately

**File:** `src/debug/drive-logger.ts:186-187`, `:160-165`
**Issue:**
- The focus guard lists INPUT, TEXTAREA and contentEditable but not SELECT. `test-stations.ts:158-164` does include SELECT. With the debug map dropdown (`createMapMenu`) focused, pressing `L` or `M` starts or stops a recording (a stop triggers a CSV download).
- `URL.revokeObjectURL(a.href)` runs synchronously after `a.click()`. This is fine in Chromium but known to abort the download in some Safari/Firefox versions. The same pattern is in `tuning-panel.ts:855`.
- Neither the logger nor test-stations exposes a dispose, so their `window` listeners and DOM badges live for the page (acceptable for a page-lifetime debug tool, but not reusable or testable).
**Fix:** Add SELECT to the guard, and defer the revoke with `setTimeout(..., 0)`.

### IN-08: Storage access outside the error boundary; AI tune inconsistent across classes

**File:** `src/main.ts:174-199`, `:186-191`
**Issue:**
- `localStorage` is read at module top level, before the `try` that renders the named failure message. In browsers with storage blocked (Chrome "block all cookies", some embedded views), merely touching `window.localStorage` throws a SecurityError. `typeof localStorage` is not a safe guard there. The page dies with a blank canvas and an uncaught error, which is the exact outcome D-P27 forbids.
- For non-RWD classes the AI fleet gets `parseSavedTuning(TUNING_STORAGE_KEY) ?? defaultTuning()`, while for RWD it shares the player's `shippedTuning` (default feel preset applied). So circuit-race AI pace silently differs between `?car=rwd` and `?car=fwd|awd`, and the saved-blob fallback also bypasses the `shippedTuning` base used for the player.
**Fix:** Wrap storage reads in a `safeGetItem(key)` helper that returns null on exception. Build `aiTuning` from `parseSavedTuning(raw, () => shippedTuning("rwd")) ?? shippedTuning("rwd")`.

### IN-09: Fragile and duplicated geometry code in the synthetic generators; CLI usage text stale

**File:** `tools/map-compiler/synthetic/proving-ground.ts:393-416`, `playground-layout.ts:57-111`, `tools/map-compiler/terrain/cli.ts:51`, `src/debug/test-stations.ts:59-83`
**Issue:**
- `proving-ground.ts` connects the spine ends and the skid-pan feeder to the ring (575,30), (575,1070) and (1275,1070) only because the ring vertices happen to fall on 25 m multiples (100+25k and 1300-25k). Unlike column A, which uses `insertOnRing`, these joints are never spliced or checked. Changing `WIDTH_M`, `RING_RADIUS_M` or `STRAIGHT_STEP_M` silently disconnects them, and the compiler prunes the spine and everything hanging off it, with no error here. `playground-layout.ts` does this correctly (`spliceOnto` throws if the point is off the ring), but it duplicates both `ringWays` and the on-segment test from proving-ground.
- `convert-terrain` usage text lists `feel-test|grid-test|juliette-ga|all`, omitting `playground`. `CONVERT_CONFIG` includes it.
- `parseStations` does not validate that `key` is a single reachable key (`0-9`, `-`, `=`, `\`, `/`), and it ignores duplicate keys. A station with key `"10"` or `"a"` is silently unlaunchable.
**Fix:** Share one `ringWays` and `spliceOnto` implementation and use it for the spine and skid-feeder joints. Derive the usage string from `Object.keys(CONVERT_CONFIG)`. Reject `key` values outside the supported set in `parseStations`.
