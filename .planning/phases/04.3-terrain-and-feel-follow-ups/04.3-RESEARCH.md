**Lift-off oversteer fix**
- **D-01:** The target feel is "keep it lively". Lifting mid-corner should still make the tail step out clearly and catchably. Only the unwanted spins go: a lift on a straight, or with small steering corrections on a gentle bend or narrow fast road, must not spin the car.

### Anti-Patterns to Avoid
- **Lowering the `liftOff` number or `liftOffOversteer` default.** D-02 forbids it; shipped value stays 5.

## Item 1: Lift-off oversteer (P43-LIFT)

### How it works today [VERIFIED: src/physics/vehicle.ts L699-746]
```
lift     = max(0, throttleRef - throttle)            // throttleRef decays, tau LIFT_OFF_REF_TAU = 0.3 s
liftRaw  = clamp(liftOffOversteer * lift * |steer| * lockScale * clamp((groundSpeed-8)/10,0,1), 0, 1)
liftHold = max(liftRaw, liftHold * exp(-DT/0.5))     // LIFT_OFF_HOLD_TAU
liftBlend = liftHold * counterSteerFade
rearSfs  = lerp(rearSideFriction(0.28), powerOversteerRearSideFriction(0.024), max(flick,pivot,power,liftBlend))
```
Shipped gain: `FEEL_DEFAULTS.liftOff = 5`, `applyFeel` maps `base * lerp(0,2,5/10)` = 1x, so `liftOffOversteer = 5`. [VERIFIED: src/core/feel.ts L89, L179; vehicle-tuning.ts L623]

Why it spins: with gain 5, a full lift (lift near 1) and `|steer|*lockScale` of only 0.2 gives liftRaw = 1 so the rear side friction drops 12x (0.28 to 0.024) from any small input, including steering corrections on a straight. `lockScale` shrinks with speed, so the effective trigger is steer input of several tenths at speed; keyboard steer ramps at 5/s, so even small taps pass through. `liftHold` then holds the loose rear for about 0.5 s. [ASSUMED: exact saturation point depends on `steerLockScale`; measure]

### Recommended reshaping (starting values, tune from measurements)
Keep the three existing multipliers (`lift`, speed fade, `counterSteerFade`) and replace the `|steer|*lockScale` linear factor and the final clamp:
1. `wheelDrive = |steer| * lockScale` (real wheel angle proxy, 0..1) and `slipDrive = |slipRad| / SLIP_REF` (SLIP_REF about 0.25 rad); `drive = max(wheelDrive, slipDrive)`. Slip is already computed just above (L695).
2. Progressive response: `shaped = smoothstep(T0, T1, drive)` or `drive^2`, with T0 about 0.10 and T1 about 0.45 as first guesses. Small inputs contribute about 0.
3. `liftRaw = clamp(LIFT_CAP * (liftOffOversteer / 5) * lift * shaped * speedFade, 0, LIFT_CAP)` with `LIFT_CAP` about 0.6 (rear side friction at cap is 0.28 + 0.6*(0.024-0.28) = 0.126, so the tail steps out clearly but is not fully released). Dividing by 5 keeps `liftOff` slider semantics (0 = off, 10 = 2x).
4. Keep `liftHold` and `counterSteerFade` unchanged.

Names/constants (`LIFT_CAP`, `LIFT_SHAPE_T0/T1`, `LIFT_SLIP_REF`) go next to `LIFT_OFF_HOLD_TAU` (L86-94) with doc comments. Update the `liftOffOversteer` doc in `src/core/vehicle-tuning.ts` L418 and the row in `docs/vehicle-tuning-guide.md` L175 (the guide-sync test only checks control names, but keep prose honest).

## Item 2: 2/60 one-tick contact losses (P43-CONTACT)

### Likely causes (all [ASSUMED], none verified; the diagnosis task decides)
- The feel preset (grip 10 and others) changes `frictionSlip`, roll and assist terms, so the car is lighter or more tail-happy on crest/vertical-curve transitions than the base car: one wheel's ray (reach about rest length + radius) briefly leaves the ground over a convex break.
- Interaction with the new lift-off term or the pure-pursuit follower's throttle lift (`throttle: braking ? 0 : ...`, `brake: 0.3`): lifting on a descent hill 15 dir -1 triggers `liftBlend` while steering corrections are active, loosening the rear and changing load. This is plausible given the hill-descent case; item 1's fix may remove one of the two.
- Heightfield triangle seams at the 60 m parabolic vertical curves.

### Plan (diagnosis first, then smallest fix)

## Item 5: juliette-ga render CPU (P43-RENDER)

### Facts [VERIFIED]
- juliette-ga: 708 x 689 vertices at 8 m (5664 x 5512 m); chunk = 64 cells = 512 m, so 12 x 11 = 132 chunk meshes, each its own `MeshStandardMaterial` + `DataTexture`. Paint map 11024 x 11328 px at 0.5 m (about 125 MB). Reading 7.71 ms, 63 draw calls, 42,576 triangles. [frame-budget.md, terrain-migration.md]
- `updateTextures(focus)` flips a chunk between `full` (one texel per 0.5 m: a 512 m chunk is about 1024 x 1024 RGBA = 4 MB, filled by a per-pixel loop calling `paintIndexAt`) and one-texel-per-cell (64 x 64) using `radius = 600 m`; since chunks are 512 m, up to roughly 4 x 4 chunks are full-res around the car. A flip calls `chunk.texture.dispose()`, rebuilds the texture, sets `material.needsUpdate = true`, and uploads on the next draw. [VERIFIED: terrain-view.ts L193-229, L287-300, L333-339]
- That call sits inside `render(alpha, dtMs)` which the loop times as `renderMs`. [VERIFIED: loop.ts L243-246; main.ts L1151-1156]
- The HUD's frame ms line was unreadable (map-select dropdown covers the first line), so a frame figure for juliette was never captured; fixing that overlap is an open follow-up in frame-budget.md. [VERIFIED]
- 63 draw calls is over the 55 target but 63 draws cannot by themselves explain 7.7 ms; texture work or shadow passes are more likely. [ASSUMED]

### Plan (measure first)
1. Instrument (debug-only, `?debug`): in `main.ts` render callback time `terrainView.updateTextures` separately from `renderer.render`; count chunk LOD flips per second and `renderer.info.memory.textures`; show in the profiler HUD or console. Fix the HUD/dropdown overlap so frame ms can be read. Record the breakdown (steady cruise vs crossing a chunk boundary) in `docs/frame-budget.md`.
2. Candidate optimisations, in order of expected value, pick by measurement:
   - **Amortise LOD flips:** at most one chunk texture rebuild per frame (queue sorted by distance), hysteresis on the radius (separate enter/exit radii), keep the 1-texel-per-cell fallback until the full one is ready. Rebuilding is pure CPU, so this directly lowers the per-frame spike.
   - **Cap full-res texel density for large chunks:** for example max 512 px per chunk side (1 m/px for 512 m chunks) since the camera is mid-to-far helicopter; or reduce `textureRadiusM` for juliette to roughly the neighbouring ring (about 1 chunk beyond the car). Reduces CPU fill and VRAM.
   - **Faster fill:** replace per-pixel `paintIndexAt` with row-wise indexing (precomputed offsets); typed-array writes only.
   - **Material/texture churn:** avoid `material.needsUpdate = true` on a pure `map` swap (the map slot already exists); reuse the DataTexture buffer when sizes are equal instead of dispose + new.
   - **Draw count:** merge legacy building meshes (the `.glb` `buildings` node) or confirm draws/shadow casters; terrain chunks are already culled by frustum.
   - **Shadow pass:** confirm terrain is `receiveShadow` only and the shadow frustum is tight.
3. Success criterion: HUD render CPU below 6.0 ms on juliette-ga at the busiest view while driving (human reading under `?debug`), recorded as a new dated section in `docs/frame-budget.md`. The budget constants in `src/core/frame-budget.ts` stay (D-04 budget NOT raised); the doc and constants mirror test (`tests/frame-budget.test.ts`) must still pass; if `SCENE_TARGETS` draw-call target changes, change both.
4. Automated proxy (since ms is not unit-testable): extend `tests/terrain-view.test.ts` "paint textures" cases to assert at most K chunk-texture rebuilds (texels written) per `updateTextures` call and that a flip does not set `material.needsUpdate` more than needed. Existing cases to keep green: near chunks full-res, far chunks one texel per cell, moving focus disposes old full-res texture (terrain-view.test.ts L164-220). ## Item 7: Square raise/lower, smoothing, visibility aids (P43-SQUARE)

### Existing conventions [VERIFIED]
- Tools and keys: `Tool = "raise"|"smooth"|"flatten"|"paint"|"road"|"stamp"|"erase"`, `TOOL_KEYS` (H, G, F, P, R, W, E). Add `"block"` and `"smoothArea"` as needed (keys: pick unused letters, for example `B` for block; check editor key handling).
- Lower = **Alt** held at pointer down (`Modifiers {alt}`); stored per stroke.
- Each stroke = one undo entry: `createStrokeRecorder` + `finish(s.recorder.commit())` + `stack.push`. UNDO_DEPTH 50. Smoothing passes must be exactly one stroke each, using a recorder around one op (one `finish`).
- All height ops go through `runHeightOp(grid, touchedWindow, compute, rec, relax, opts)` in `src/core/terrain-brush.ts` (non-exported): snapshots, computes, `expandWindow` for the slope fade, `beforeHeightsWrite`, writes, optional 1-2-1 relax, then `limitSlope(grid, dirty, {maxSlopeDeg: 35, mask})`. `opts.roadMask(win)` = `roadVertexMask(grid, paint, graph, win)` (tool-dispatch `heightOpOptions`). WR-03 `freezePreexistingSteep` keeps old cliffs untouched.
- Options UI: `#tool-opts` children with `data-for="tool1 tool2"`, number + range linked by `linkNumberAndRange`; `setOptions` accepts partial `ToolOptions`; `paintRing` draws the cursor ring (a `THREE.Line` with `RING_SEGMENTS`, terrain-conforming, green/amber on slope clamp).
- Editor test file `tools/terrain-editor/tool-dispatch.test.ts` already tests the dispatcher purely.

### Block op (new, in terrain-brush.ts)
`raiseBlock(grid, {x, z, blockCells, stepM}, sign, rec, opts)`:
- Snap `(x, z)` to the cell index `(r0, c0)` of the cell containing the hit, anchor the N x N block there (for example centred: `r0 = row - floor((N-1)/2)`); the block's vertex window is `[r0, r0+N] x [c0, c0+N]` (N+1 vertices per side).
- Call `runHeightOp` with `compute = inside window ? h + sign*stepM : h`, `relax = false` (sharp edges are intended, specifics: "Sharp-looking blocks are fine"), `opts` with `roadMask` as for the other ops. The limiter makes steps taller than `tan(35 deg) * cell` (2.1 m at 3 m cells, 5.6 m at 8 m) form skirts; the road mask keeps roads put (D-20). Status `SLOPE_CLAMP_HINT` as for other ops.
- **Once-per-block per stroke:** the dispatcher keeps a `Set<number>` of block keys for the stroke; skip a block already stepped. (Note ordering: after the first block raises, neighbouring blocks in the same drag step independently, which is intended.) Click = a single block.
- Quantisation: heights are quantised to 0.01 m on save (see PREEXISTING_TOL_M comment); use steps that are multiples of 0.25.
- Block cursor ring must change for this tool: a rectangle outline of the exact vertex window plus height label.
- Defaults: `blockCells` 2 (range 1-8), `blockStepM` 1 (range 0.25-5, step 0.25). Cell size varies per map (3 m or 8 m): D-18 text says "1x1 (8 m)" so the label must show metres = `N * cell`.

### Smoothing pass (new)
`smoothRegion(grid, window | {circle}, {strength, passes}, rec, opts)`:
- Same 1-2-1 kernel as `smoothBrush` (`h + strength * (sum/16 - h)`), repeated `passes` times on a working copy (compute all passes into a scratch buffer, then commit once so `StrokeRecorder` records one diff).
- **Never touch road cells:** the op's compute returns `h` for any vertex where the road mask is set (use `roadVertexMask(grid, paint, graph, window)` which is the "WR-02" definition) so it neither moves road vertices nor lets the limiter move them; additionally skip vertices whose four surrounding paint pixels carry `PAINT_ROAD_FLAG` if the mask misses paint-only roads (for example demo-hills where roads are painted). Test with a painted road in `tests/terrain-brush.test.ts`.
- "Smooth area": a drag-box selection in the editor (two corners) or the existing round smooth brush applied as one pass. "Smooth whole map": window = entire grid; run `limitSlope` once at the end (the whole-map window is up to about 667 x 667 vertices on a 2 km map: fine). Diff size is up to about 450k indices; confirm `StrokeDiff` memory is acceptable and the editor does not freeze (do it in one synchronous call; measure; yield with a status message first).
- Strength 0-1 and passes 1-10 are exposed as sliders; panel buttons "Smooth area" (arms box selection) and "Smooth whole map" (immediate, confirm not needed because undoable).
- Dispatcher: new methods `smoothWindow(window, opts)` / `smoothAll(opts)` returning a `ToolResult` (dirty window = region) and pushing one undo entry; editor rebuilds only dirty chunks via `rebuild`.

### Visibility aids (editor only; no changes to `src/render`)
- **Grid overlay:** `THREE.LineSegments` of cell lines for the *visible area only* (a window around the camera target or around the cursor, for example 64 x 64 cells), rebuilt on camera move; do not build a 667 x 667 line mesh per frame. Conform to terrain height + 0.05 m. Toggle with a checkbox / key.
- **Block preview:** outline of the exact vertex window the next click changes (`blockWindow(hit, N)` pure helper), plus a DOM label of the *current* height at the anchor cell shown in the `#sel` readout (already prints `height`) or next to the outline; "step to" label optional. Colour amber if the limiter would clamp is hard to know before the op; skip.
- **Contours:** line segments at multiples of `contourIntervalM` (default 1 m) via marching squares on the grid in the visible window, computed in `src/core/terrain-overlay.ts` (pure, tested) and drawn as `LineSegments`; rebuild after height edits in the dirty region (cheap if limited to the window).
- **Zoom check hint:** when the camera distance/height implies one cell below about 8 px on screen, show a hint via `setHint`, "Zoom in to see single cells" (pure function `cellPixelSize(cameraDist, fov, viewportH, cell)` tested).
- Status/hint text via `textContent` (WR-06).

## Common Pitfalls

### Pitfall 1: Lift-off fix neuters the trick
**What goes wrong:** the cap/threshold is set so high that mid-corner lift no longer steps the tail out.
**How to avoid:** keep the existing `lift-off-60` lively assertion (peak slip above 8 at gain 5) and add the same on the shipped car; D-05 human drive decides.
**Warning signs:** `lift-off-60` peak slip drops toward the `hold-60` control (about 1.8 deg).

### Pitfall 2: Hard tests pass vacuously
**What goes wrong:** the new no-spin routines are too gentle and pass on the old code too.
**How to avoid:** run them against unmodified `vehicle.ts` first and record the failing numbers in the plan summary.

### Pitfall 3: Dossier suite slowness
**What goes wrong:** `tests/lift-off.test.ts` reruns every script per assertion.
**How to avoid:** add the `ids` filter to `runDossier`; the default vitest config has no testTimeout beyond default 5 s, so heavy cases need explicit timeouts (the gate test uses 120 s).

### Pitfall 4: Shipped-car helper drift
**What goes wrong:** `main.ts` and the headless tools build the car differently, so tests prove the wrong thing.
**How to avoid:** a single `shippedTuning()`; a test asserting main's path uses it (grep) or at least equality with `applyFeel(...FEEL_DEFAULTS)`.

### Pitfall 5: Berm breaks existing driven tests or spawn near an edge
**What goes wrong:** `?at=` drive-here near the edge, or maps whose spawn sits within the inset, collide with the wall.
**How to avoid:** inset small (about 1 m from the edge), assert default spawns of all shipped terrain maps are at least 10 m from the berm; berm only built in `createTerrainScene`, not `buildTerrainCollider`.

### Pitfall 6: Widening changes lap geometry and checkpoints
**What goes wrong:** widened band levelling shifts heights where roads meet; route validation uses `edge.widthM`.
**How to avoid:** do not touch graph widths; check `validateCourseRoutes` tests pass (`terrain-convert.test.ts` already loads routes); re-verify junction heights (node heights within 0.02 m, per migration doc) after rerun.

### Pitfall 7: Legacy tests assert old pixel counts
**How to avoid:** grep `terrain-convert.test.ts` for road radius assertions and update only for juliette/grid; feel-test expectations stay identical.

### Pitfall 8: Save guard blocks shipped maps or the hills map
**What goes wrong:** a shipped terrain map fails a hard category and the editor can never save it.
**How to avoid:** test the guard over every `public/maps/*.terrain.json`.

### Pitfall 9: Block tool repeated stepping while dragging
Covered above (once-per-stroke visited set).

### Pitfall 10: Smoothing eats road shoulders / shifts bands

### 1. Lift-off curve (sketch for vehicle.ts, replaces L704-714)
```ts
// Source: derived from src/physics/vehicle.ts L699-716 (this repo)
const lift = Math.max(0, throttleRef - frame.throttle);
throttleRef += (frame.throttle - throttleRef) * (1 - Math.exp(-DT / LIFT_OFF_REF_TAU));
const wheelDrive = Math.abs(frame.steer) * lockScale;      // real wheel angle proxy
const slipDrive = Math.abs(slipRad) / LIFT_SLIP_REF;        // slipRad computed above (L695)
const shaped = smoothstep01(clamp((Math.max(wheelDrive, slipDrive) - LIFT_T0) / (LIFT_T1 - LIFT_T0), 0, 1));
const speedFade = clamp((Math.hypot(lv.x, lv.z) - 8) / 10, 0, 1);
const liftRaw = clamp(
  LIFT_CAP * (t.drive.liftOffOversteer / LIFT_GAIN_REF) * lift * shaped * speedFade,
  0,
  LIFT_CAP,
);
liftHold = Math.max(liftRaw, liftHold * Math.exp(-DT / LIFT_OFF_HOLD_TAU));
```
