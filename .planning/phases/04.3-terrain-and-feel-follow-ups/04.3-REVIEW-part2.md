# Phase 04.3 Code Review, Part 2

**Depth:** standard. All 15 listed files were read in full, plus the collaborators needed to verify claims.

## Summary

No Critical defects found. The sim code is deterministic: grep for `Math.random`, `Date.now`, `new Date`, `performance.now`, `setTimeout` and `requestAnimationFrame` over `src/physics/` and `src/core/` finds none in executable code. The only RNG is the explicit LCG in `crest-geometry.ts:250`. Every physics path uses the imported `DT`. Saved-data parsing is robust: `parseSavedTuning`, `parseSavedFeel` and `clampNode` all fall back to defaults on non-finite or missing values and use `Object.hasOwn`/range-keyed walks, so there is no prototype-key or NaN leak.

The real defects are tuning-application gaps (live sliders that do nothing), stale per-vehicle state across `resetPose`, an inconsistency in which height brushes respect the road mask, and one smoothing-window asymmetry in road banking.

## Warnings

### WR-01: Live tuning sliders for chassis damping and wheel/chassis geometry are silent no-ops

**File:** `src/physics/vehicle.ts:327-363` (with `src/debug/tuning-panel.ts:274-316`)
**Issue:** `applyTuning` only sets the wheel suspension, friction and side-friction setters and the additional mass properties. The panel exposes `chassis.linearDamping`, `chassis.angularDamping`, `wheels.halfTrack`, `halfWheelbase`, `connectionY`, `radius`, `suspensionRestLength` and `chassis.halfExtents.*`, and wires each to `handlers.onApplyVehicle`. The panel comment says damping is "safe live" and that every wheel property goes through "Rapier's per-index wheel setters".
- Damping is applied only in `createVehicle` (lines 268-269).
- Wheel geometry is applied only in the `addWheel` loop (lines 317-319).
- The cuboid collider is never resized.

Failure scenario:
1. Drag `halfWheelbase` from 1.55 to 2.2. The physical wheels do not move.
2. `vehicle.ts` still reads `t.wheels.halfWheelbase` for the pivot front-axle cap (line 924) and the yaw-damping `demanded` yaw (line 1027). The assist maths now disagree with the real wheelbase.
3. Changing `halfExtents.z` recomputes inertia (lines 345-352) for a collider that did not change.
4. A tuner saves the "good" feel and gets a car that does not match the saved numbers after reload. At reload the construction path does honour them, so the same blob drives differently live and fresh.

**Fix:** Rapier 0.20 has the setters (`setWheelChassisConnectionPointCs`, `setWheelSuspensionRestLength`, `setWheelRadius`). Extend `applyTuning`:
```ts
body.setLinearDamping(t.chassis.linearDamping);
body.setAngularDamping(t.chassis.angularDamping);
const g = t.wheels;
const conn = [
  { x: -g.halfTrack, y: g.connectionY, z: -g.halfWheelbase },
  { x:  g.halfTrack, y: g.connectionY, z: -g.halfWheelbase },
  { x: -g.halfTrack, y: g.connectionY, z:  g.halfWheelbase },
  { x:  g.halfTrack, y: g.connectionY, z:  g.halfWheelbase },
];
for (let i = 0; i < 4; i++) {
  vc.setWheelChassisConnectionPointCs(i, conn[i]);
  vc.setWheelSuspensionRestLength(i, g.suspensionRestLength);
  vc.setWheelRadius(i, g.radius);
}
// halfExtents: keep a handle to the collider and call collider.setHalfExtents(...)
```
Alternatively remove those sliders from the panel (or mark them "reload required").

### WR-02: `resetPose` leaves roll-guard, telemetry and suspension state stale

**File:** `src/physics/vehicle.ts:367-393`, read at `840` and `481`
**Issue:** `resetPose` clears the flick, pivot, regrip, throttle-ref and falloff state, but not `telemetry`, `rollGuardWasOn`, `lastSuspensionLength` or `wheelSurfaces`. The roll guard reads `telemetry.rollDeg` (line 840), which is only refreshed at the end of `tick` (line 1045).

Failure scenario:
1. The car is rolled about 90 deg, then respawned via `resetPose`, `resetCar` or `resetVehicle`.
2. On the first tick after the reset, `rollFade` is 1, so `guardOn` is true.
3. Every wheel's friction slip is multiplied by `1 - rollGuard` (0.15 at the default 0.85) on every non-exempt surface for that tick, then restored on the next.
4. `lastSuspensionLength` from the flip also feeds the compressing-only rule in the bump stop.

The effect is deterministic, but it is a one-tick grip hole on every respawn. Ghost or medal runs that respawn at a checkpoint are exposed.

**Fix:** In `resetPose`, reset the following. Declare `telemetry` before `resetPose`, or resample after the pose is set:
```ts
rollGuardWasOn = false;
lastSuspensionLength.fill(c.suspensionRestLength); // or tuning.wheels.suspensionRestLength
telemetry = sampleVehicle({ body, controller: vc } as Vehicle);
wheelSurfaces.fill("tarmac");
```
`lastSuspensionLength` is also initialised to a hard-coded `0.45` (line 413) instead of `tuning.wheels.suspensionRestLength`.

### WR-03: Height brushes disagree on whether road-masked vertices may move

**File:** `src/core/terrain-brush.ts:284-307` (`raiseLower`), `504-526` (`flattenBrush`), `309-354` (`smoothBrush`), `539-591` (`stampTerrain`), and the relax step at `248-278`
**Issue:** `raiseBlock` (line 414) and `smoothRegion` (lines 473, 495) explicitly hold masked road vertices. The header comment at lines 389-391 says "roadMask alone only protects the limiter". `raiseLower`, `flattenBrush`, `smoothBrush` and `stampTerrain` do not consult the mask in `compute`. The 1-2-1 relax step in `runHeightOp` also rewrites moved vertices without checking it. `tool-dispatch.ts:124` passes the road mask to all of them, and `HeightOpOptions.roadMask`'s doc claims "roads keep their graph y (D-16)".

Failure scenario:
1. Raise or flatten over a road with the raise/lower or flatten brush.
2. The road vertices move by `rate * strength * falloff`. The limiter then treats the moved values as fixed sources and keeps them.
3. The painted road now has a bump, and the graph node/edge y is stale until a later `syncNodeHeights`.

If sculpting over roads is intended, the doc and D-16 wording is wrong. If not, the brushes need the same guard.

**Fix:** Either factor a shared `holdMasked(mask, x, z, h, next)` used by every `compute` (and skip masked vertices in the relax loop), or document that only `raiseBlock` and `smoothRegion` protect roads.

### WR-04: Road bank smoothing pads the start incorrectly, so the window collapses at the stroke start

**File:** `src/core/terrain-road.ts:396-409` (with `movingAverage` at `242-276`, specifically `269`)
**Issue:** `roadBankAngles` pads both ends with zero-bank samples "so the bank ramps in and out instead of the averaging window shrinking to nothing at the stroke ends". `movingAverage` computes `hw = min(windowM/2, s[i], total - s[i])`, and `s[i]` is the arclength from the start of the array. The array starts with the negative padding coordinates, but for real points `s[i] >= 0`. So `s[i]` caps the half-width near the start.
- At the first real point `hw = 0`, so no averaging happens.
- At 6 m, `hw = 6`, so the window is [0, 12] rather than [-4, 16].

The end side uses the padded `total` and is correct. Start and end ramps therefore differ, and the intended behaviour is defeated on the start side only. Banking begins slightly more abruptly at the beginning of a stroke than at its end.

**Fix:** Pass the padded origin into `movingAverage` (use `s[i] - s[0]`), or give it an explicit `pad` flag:
```ts
const hw = Math.min(windowM / 2, s[i] - s[0], s[n - 1] - s[i]);
```
For the unpadded `roadHeightProfile` call `s[0] === 0`, so behaviour there is unchanged.

### WR-05: AI cars ignore the player's drive layout despite "identical car" intent

**File:** `src/physics/ai-fleet.ts:90`
**Issue:** `createVehicle(world, currentTuning, pose)` is called without `frontDriveShare`, so it defaults to 0 (RWD). `createMapScene` passes `frontDriveShare` for the player. `main.ts:166` documents "AI cars always stay RWD" and builds an independent RWD tune for non-RWD player classes, so this is deliberate. But the `createAiFleet` header and the `setTuning` comment still promise D-02 identical car and tune. If a player on FWD/AWD races AI, the field is not symmetric. This is a doc/intent mismatch rather than a crash.

**Fix:** Add a comment on `createAiFleet` stating AI is always RWD, or add a `frontDriveShare` option and thread it through.

### IN-03: `RampSpec` and `AuthoredCrest` are only partially validated

**File:** `src/core/crest-geometry.ts:388-397`, `414-420`, `527-532`
**Issue:** `buildCrestGeometry` validates `heightM <= 0` and `radiusM <= 0` for domes only. With a ramp, `footRadiusM <= 0`, `angleDeg <= 0` or `widthM <= 0` is unchecked. Failure scenario: `angleDeg: 0` with `footRise (0) < heightM` gives `(heightM) / tan(0)` = Infinity, so `steps = Infinity`. `new Float32Array(Infinity)` then throws a `RangeError` with no crest id in the message. `NaN` values slip past `<= 0` tests as well. This is all authored data today, so there is no live hit.
**Fix:** Add `!(x > 0)`/`Number.isFinite` checks with the crest id for `heightM`, `radiusM`, `widthM`, `angleDeg` and `footRadiusM`.

### IN-04: Crest mesh colour does not follow the area's ground surface

### IN-07: `heading.ts` `headingFromRotation` forwardX has the wrong sign on the `xz` term

**File:** `src/core/heading.ts:73` (used by `ai-fleet.ts:131`)
**Issue:** Rotating local `-Z` by the quaternion gives `forwardX = -2(xz + wy)`, which agrees with `vehicle.ts` `rotateVec` and with `terrain-gate.ts:166`. `headingFromRotation` computes `2(xz - wy)`. For pure yaw (`x = z = 0`) the result is identical, so it is correct on flat ground. With simultaneous pitch and roll the `xz` product term has the wrong sign. At 10 deg of each, the error is about 0.015 in `forwardX`. This is small, and AI cars on hills or ramps get a slightly skewed heading. It is outside this review's file list but it feeds `ai-fleet`.
**Fix:** Use `-2 * (rotation.x * rotation.z + rotation.w * rotation.y)`.
