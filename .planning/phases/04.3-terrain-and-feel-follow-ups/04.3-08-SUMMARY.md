# Phase 04.3 Plan 08: Shipped-car contact loss - root caused and fixed

The single lost-contact tick on the shipped car (climb 15 m/s dir -1, tick 2894, wheel 2) was NOT a feel or tuning problem. It was a Rapier/parry heightfield ray-cast bug. Fixed with a per-vehicle local trimesh patch (decision B); the shipped-car gate case is now fatal by default.

## Root cause

Rapier 0.20.0 (and 0.21.0, checked) heightfield ray cast picks the wrong start cell when a ray starts within a few f32 ulps of a cell line, tests that cell's triangles (miss), then its cell-stepping aborts because the next-boundary toi is negative. The whole cast returns "no hit". The wheel ray (cast from the wheel hard point) occasionally lands within an ulp of a cell line, so one wheel loses contact for one tick. Independent of tuning; chaos comes only from which tick lands on a line; subdiv 2 has twice the cell lines of subdiv 1. Full evidence: `.planning/debug/wheel-ray-miss-slope-gate.md`. Flat-ground micro probe: heightfield 122/4158 z-boundary rays miss, the same triangles as a trimesh 0/4158.

This supersedes the earlier "chaotic crest event, fix needs droop/ray reach" diagnosis. The lift-off blend was never implicated (liftOff 0/5/10 identical).

## Decision B: local trimesh patch (not full trimesh, not droop change)

- Full trimesh terrain: rejected on cost (about 1.1 s build, +227 MB on a 2 km map) and it reverses 04.2-RESEARCH's heightfield-for-memory choice.
- Droop/ray-reach change: would not fix a ray that returns no hit at all, and would change feel.
- Chosen: keep the heightfield as the terrain; each raycast vehicle carries a small fixed trimesh window of the identical triangles.

### Design

- `src/physics/wheel-ray-patch.ts`: 32x32 cell window (`PATCH_CELLS`), same heights and `TERRAIN_DIAGONAL`, body-local vertices, upward normals. Re-centred when the car comes within 8 cells (`PATCH_MARGIN_CELLS`) of a window edge that is not the grid edge; window clamped to the grid; handles grids that differ (main plus gate extra terrain).
- No contacts: collision and solver groups are membership 2, empty filter. Verified: a ball falls through a patch-only world. The vehicle controller's `updateVehicle` is called with no group filter, so wheel rays do see it (probe: `wheelGroundObject` returns patch handles; a filter of all-ones groups would exclude it, so never pass one). Nearest hit is identical to the heightfield wherever the heightfield does not miss (test: <1e-3 m over 400 rays on a bumpy grid).
- Surface mapping: patch handles are added to the terrain `SurfacePaintLookup.aliasHandles` (new optional set; `vehicle.ts` checks it) and registered in the `SurfaceMap` (new `unregister`), so grip and surface match the terrain exactly.
- Determinism: rebuild decisions use only the chassis position at the fixed tick (`Vehicle.tick`, just before `updateVehicle`). No render time.
- Rebuild: two alternating body+collider slots, because a collider created this tick is only safely visible after the next step; the previous window stays until the next rebuild. Vertex and index buffers are allocated once and reused. Old slot is removed with `removeRigidBody` (frees its collider and WASM memory), also on `Vehicle.dispose`.
- Wiring: `createTerrainScene` attaches a patch to the player vehicle and exposes `createWheelRayPatch()`; `createAiFleet` takes `options.wheelRayPatch` and attaches one per AI car (main.ts passes the scene's factory). `runGateLane` attaches one (`noPatch` option for the control run).
- Not covered: the legacy `createMapScene` ground heightfield (non-terrain maps) has no patch. It has the same latent bug; add a target there if a lost tick shows up on a legacy map.

## Follow-up

`DEFAULT_COLLIDER_SUBDIV = 2` was chosen at plan 05 because subdiv 1 showed a 1-tick contact flicker. That flicker was this bug. The value is NOT changed here; it can be revisited (subdiv 1 halves the collider cost and may now pass) with a human drive.
