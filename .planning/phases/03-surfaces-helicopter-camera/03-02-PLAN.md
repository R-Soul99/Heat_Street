<objective>
Build the entire Node-testable core of the helicopter camera — heading derivation,
speed-driven framing, and occlusion mitigation decisions — as free functions with
explicit parameters, before any `THREE.PerspectiveCamera` or `THREE.Raycaster` is
touched.

Purpose: `vitest.config.ts` uses `environment: "node"` with no jsdom and no WebGL,
so this is the ONLY layer of the camera that can be automatically regression-tested
at all (03-VALIDATION.md "Test Infrastructure"). Getting the maths out of the rig and
into free functions — `src/physics/vehicle-assists.ts`'s exact precedent — is what
makes SC3/SC4/SC6's unavoidable human playtests a judgement about *feel* rather than
a hunt for a sign error.

Output: `src/render/camera/camera-math.ts`, `src/render/camera/occlusion.ts`, and the
three Wave-0 test files 03-VALIDATION.md requires.
</objective>

    - Continuity across the threshold: sweeping `groundSpeedMs` from 0 to 3 in 0.05 steps with a fixed 90-degree velocity/chassis disagreement, no consecutive pair of results differs by more than 0.08 rad — there is no snap.

    - Degenerate anti-parallel case: velocity exactly opposite chassis forward at blend weight 0.5 produces a finite number (not `NaN`), and the function documents which side it falls back to.
    - `dampFactor(lambda, dtSec)` returns 0 at `dtSec = 0`, is strictly increasing in `dtSec`, is always in [0, 1), and satisfies `dampFactor(2, 0.5)` approximately `1 - Math.exp(-1)` to within 1e-12.

  <action>
    Create `src/render/camera/camera-math.ts` with a module doc comment stating: this file
    is pure TypeScript and imports NOTHING — not `three`, not `@dimforge/rapier3d` — so it
    runs under `vitest.config.ts`'s `environment: "node"` harness with zero setup, exactly
    like `src/physics/vehicle-assists.ts`. Note explicitly that `dampFactor` is deliberately
    hand-written rather than delegated to `THREE.MathUtils.damp`: `damp()` applies the factor
    to a scalar and does not expose the factor itself, but `THREE.Quaternion.slerp` in plan
    03-04 needs the raw `t`. `THREE.MathUtils.damp` is still the required call for scalar
    damping in the rig itself — this function is the rotation-side companion, not a
    replacement.

    Export from this task:
    - `smoothstep01(t: number): number` — the classic `t*t*(3-2*t)` with the input clamped to [0,1] first.
    - `dampFactor(lambda: number, dtSec: number): number` — `1 - Math.exp(-lambda * dtSec)`, the
      frame-rate-independent form named in 03-RESEARCH.md Pattern 3. Guard `dtSec <= 0` to return 0.
    - `blendedHeadingRad(velocityXZ: { x: number; z: number }, chassisForwardXZ: { x: number; z: number }, groundSpeedMs: number, blendSpeedMs: number): number`.

    `blendedHeadingRad` must blend VECTORS and then take one `Math.atan2`, never blend two
    angles — angle blending breaks at the +/-PI wraparound, which is the project's own
    established rule (`src/render/interpolator.ts`'s slerp discipline, restated in
    03-RESEARCH.md "Don't Hand-Roll"). Algorithm: normalise both XZ inputs (a zero-length
    velocity normalises to the chassis-forward vector); compute
    `w = smoothstep01(groundSpeedMs / blendSpeedMs)`; linearly interpolate the two unit
    vectors component-wise with weight `w` toward velocity; if the blended vector's length
    falls below a small epsilon (the exactly-anti-parallel case at `w` near 0.5), fall back
    to the chassis-forward vector and say so in a comment; return
    `Math.atan2(blendedX, blendedZ)`. Guard `blendSpeedMs <= 0` by treating `w` as 1.

    Use the `Math.atan2(x, z)` argument order (X first, Z second) so the returned angle is a
    yaw about `+Y` consistent with the vehicle's `-Z`-forward convention; state this in the
    doc comment, because swapping the arguments silently mirrors the camera.
