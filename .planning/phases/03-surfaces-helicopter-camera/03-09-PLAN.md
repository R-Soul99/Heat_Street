    - `fanOffsetsRad(1)` returns `[0]` — a fan of one degenerates to the single centre ray.
    - `fanOffsetsRad(0)` returns `[0]` rather than an empty array, so `densityFrom` can never be

    - The outermost offsets do not exceed a documented half-spread (use PI/6, i.e. a 60-degree

      report density that has nothing to do with what the player can see.
    - Offsets are evenly spaced across the spread.

  <action>
    Create `src/render/camera/occlusion-controller.ts`:
    - `export interface OcclusionController { mitigation(): OcclusionMitigation; setMitigation(m: OcclusionMitigation): void; cycle(): OcclusionMitigation; update(cameraPos, targetPos, dtMs): void; dispose(): void }`
    - `export function createOcclusionController(probe: OcclusionProbe, buildingMeshes: readonly THREE.Mesh[], rig: CameraRig, tuning: CameraTuning, initial?: OcclusionMitigation): OcclusionController`

    `update(cameraPos, targetPos, dtMs)` branches on the current mitigation:

    - `"fade"`: call `probe.hits(...)`, run `classifyOcclusion(hits, targetDistance, tuning.occlusion.nearTargetMarginM)`,
      then for EVERY building mesh damp its material opacity toward
      `fadeTargetOpacity(isThisMeshAnOccluder, 1, tuning.occlusion.fadeFloorOpacity)` using
      `dampFactor(tuning.occlusion.fadeLambda, dtSec)`. Damped, never a hard cut — a pop as a
      building crosses the ray is exactly what the playtest would reject for the wrong reason.
      Set `material.depthWrite = false` on a mesh while its opacity is below 1 and restore it to
      `true` once fully opaque again, and comment why: several simultaneously-faded overlapping
      buildings sort incorrectly against each other with depth writes on, producing flicker that
      reads as a bug rather than as a mitigation. Track per-mesh current opacity in a
      pre-allocated `Float32Array` sized to `buildingMeshes.length` at construction, indexed
      positionally — never a `Map` rebuilt per frame.
    - `"steepen"`: call `probe.occludedFanRayCount(cameraPos, targetPos, fanOffsetsRad(tuning.occlusion.fanRayCount))`,
      convert with `densityFrom(...)`, convert the tuning's `basePitchDeg`/`maxPitchDeg` to radians,
      compute `steepenPitchRad(...)`, damp the applied bias toward that value with
      `dampFactor(tuning.occlusion.fadeLambda, dtSec)`, and call
      `rig.setPitchBiasRad(dampedBias - basePitchRad)` so a density of 0 yields a bias of exactly 0
      — the rig's untouched baseline pose. This is CAM-04's "then relaxing in open areas" half, and
      it is the half a naive implementation forgets: the sparse cluster and the open bands between
      zones must visibly return the camera to its normal angle.
    - `"off"`: restore every building to full opacity and `depthWrite = true`, and call
      `rig.setPitchBiasRad(0)`. This is the baseline arm of the comparison — without it the
      playtest is forced to pick a winner between two changes with nothing to compare against.
    - Switching mitigation must FULLY reset the other path's state (opacities restored when
      leaving `"fade"`, pitch bias zeroed when leaving `"steepen"`), so an A/B comparison is not
      contaminated by leftover state from the previously-selected arm.
    - `dispose()` restores every building's opacity and `depthWrite`, and zeroes the pitch bias.

    Then wire it in `src/main.ts`:
    - Construct the probe from `surfaceWorld.buildingMeshes` and the controller from it, the rig
      and `cameraTuning`. Construct them ALWAYS, not gated on `DEBUG_ENABLED` — occlusion
      mitigation is player-facing behaviour, exactly like the camera itself. Default the initial
      mitigation to `"fade"` and comment that the default is provisional pending plan 03-12's SC6
      playtest, naming this line as the one to change once the winner is chosen.
    - Gate only the A/B cycle: `if (DEBUG_ENABLED) { onDebugKey("KeyO", () => occlusion.cycle()); }`.
      This is the control that makes CAM-04's "decided by human playtest feel" a thing a human can
      actually do, in one session, without a rebuild.
    - Call `occlusion.update(camera.position, targetPosition, dtMs)` in the render callback
      immediately AFTER `activeRig.update(dtMs)` and before `renderer.render(...)`. The rig must
      run first so the camera is at this frame's pose before the probe casts from it; the pitch
      bias the controller sets takes effect on the NEXT frame, which is a one-frame lag and is
      imperceptible — document it in place so it is not mistaken for a bug, in the same spirit as
      the surface-friction one-tick lag (03-RESEARCH.md Pitfall 2).
    - Note in the key-map comment that `O` is now taken.
  </action>

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Tuning values → material opacity and camera pitch | `fadeFloorOpacity`, `basePitchDeg`, `maxPitchDeg` and `fanRayCount` originate in a parsed `localStorage` blob and drive what the player can see |
| Per-frame raycasting → frame budget | `fanRayCount` rays per frame against every building mesh, on the render thread |
| Mitigation state → shared building materials | The controller mutates materials the render scene owns |
