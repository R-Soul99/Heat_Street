# Phase 07.1: Editor UX Overhaul - Research

**Researched:** 2026-11-11
**Domain:** Dev-tooling UI (vanilla TS + DOM, Vite dev middleware, Three.js terrain editor, 2D-canvas map editor)
**Confidence:** HIGH for codebase facts (read directly); MEDIUM for the raise/lower root cause (no browser available)

## Summary

Both editors are single-file imperative pages (`map-editor/editor.ts` 1047 lines, `terrain-editor/editor.ts` 1306 lines) with a 300 px scrolling `#side` panel, DOM located by hard-coded ids via `$("id")`. They share no code today. The overhaul is therefore a UI restructure plus (a) a new shared shell module, (b) a new "fresh map" path for the map editor, (c) a new Raise/Lower split and Grid-select tool in the terrain dispatcher. No new npm packages are needed. Both pages are plain dev-server HTML files (not Vite build inputs), so a shared module is reachable by plain relative imports and a plain CSS `<link>`.

All five user complaints trace to concrete code (below). Image-import overlay, silly precision, and silent New-world failure are fully explained. Terrain raise/lower has three plausible causes; none is provable without a browser, but the strongest is "effect too small to see + no feedback", plus "silently does nothing when no area is loaded".

**Primary recommendation:** Build `tools/editor-shell/` first (pure logic files unit-testable in node, plus DOM builders), migrate map editor, then terrain editor. Keep `tool-dispatch.ts` pure and DOM-free; add `lower`, `gridSelect` tools there with tests. Do NOT use Alt for anything on raise/lower; consider moving the Lock tool's Alt+click select to Shift+click for consistency.

## 1. Map editor: current state (tools/map-editor/)

**DOM** (`index.html`): `#app` flex row = `#wrap > canvas#map` + `#side` (300 px, `overflow-y:auto`, line 11). Sidebar sections top to bottom: Tool buttons `.tool[data-tool]` (select/road/move/building, lines 36-41), `#tool-opts` (JS-filled by `setTool`), Area `<select id=area>` + Save/Save&compile/Undo/Compile&drive (44-50), View (tile size select `#tile-size`, `#show-grid`, `#show-tiles`), New world (`#nw-id #nw-w #nw-h #nw-create`, 56-63), Import image (`#im-file #im-thr #im-km #im-mpp #im-derived #im-ox #im-oy #im-width #im-hw #im-surf #im-spur #im-simp #im-smooth #im-warn #im-preview #im-go`, 64-94), `#status #hint #sel #legend #log`. Everything lives in one scroll column; the log and status are at the bottom, which is why errors are invisible.

**Tool model** (`editor.ts:85-100`): `type Tool = "select"|"road"|"move"|"building"`; module-level `let tool`; `setTool()` (419) rewrites `#tool-opts` innerHTML. Select = click-pick one road/building (mouseup branch 632-640) with pan-drag; no box select exists. Road tool: click points, `dblclick` (642) pops the duplicate point and calls `finishRoad()` (460); Enter also finishes (667). Eraser tool does not exist (only `deleteSelected` 546 via Delete/Backspace key or `#f-delete` button).

**Undo** (173-188): string-snapshot stack `undoStack: string[]` of `JSON.stringify([roads, buildings])`, cap 100, `snapshot()` must be called BEFORE every mutation. `undo()` pops and re-parses. **There is no redo.** Redo requires a second stack (push current JSON onto redo in `undo()`, clear redo in `snapshot()`). `loadArea` clears the stack (196). Keys: `Z` (not Ctrl+Z!) undoes (686); `S` saves (687).

**Persistence**: `GET /__editor/areas`, `GET|PUT /__editor/raw/<area>/<roads|buildings>`, `POST /__editor/compile/<area>`, `POST /__editor/new-world` (`vite-plugin.ts:83-151`). Areas listed = files matching `*.raw-osm.json` in `tools/map-compiler/areas/`. PUT validates `response.elements` is an array. Dirty flag `dirty` (81) set by `snapshot()`, `undo`, mouseup after node move; cleared by save/load. `beforeunload` guards.

**Data model** (`model.ts`, `world.ts`): roads and buildings are raw-OSM envelopes (`RawEnvelope`, `world.ts:33`), ways with `tags`. Road attributes = tags `highway` (HIGHWAY_CLASSES), `surface` (OSM values mapped from 6 `SURFACES`, `model.ts:18-44`), `width`, `name`, `oneway` (`editor.ts:477-544`). Building = `building=yes`, `height`. **No "disabled" concept exists anywhere**: only `filter(...)` deletion (546-552). A "disable" option for Select requires inventing a tag. Recommendation: use an OSM-style lifecycle tag that the compiler will naturally ignore only if verified; the compiler (`tools/map-compiler/graph/build-graph.ts`, not read) must be checked, since an unrecognised tag like `disabled=yes` will NOT be skipped by it. Safest, smallest option: treat "disable" as a editor-only reversible hide stored in a tag AND make `PUT` strip/`build-graph` skip it, or (simpler, recommended) implement D-07 "delete or disable" as **delete only in plan 1, with "disable" mapped to `highway`->`disused:highway` rename** (OSM convention; compiler ignores ways without a `highway` tag - VERIFY in build-graph.ts before relying on it). Flag as Open Question 1.

**Canvas**: single 2D canvas; world metres to screen via `scale/panX/panY` (102-118); `toScreen`/`toWorld` (222-226); `zoomAt()` in `world.ts` (wheel handler 648-661, exponential factor, clamps `fitScale/4..MAX_SCALE=20`); pan = left-drag in select or any non-left button (570-572, 592-596); arrow keys pan by quarter-canvas (675-681); `F` fits. Canvas size = `clientWidth/Height` on `resize` (693-698); no devicePixelRatio handling. Canvas draw is rAF-coalesced via `requestDraw()` (152). HUD (scale bar, cursor x/y, world km, tile m) is painted INTO the canvas by `drawHud()` (301-327): D-03's info bar should replace this with DOM; keep the scale bar in canvas.

**Mouse handling uses `mousedown/mousemove/mouseup` on window** (570-641), not pointer events, with `e.target === canvas` checks. New floating DOM overlays must not swallow events: mouseup on a toolbar after a canvas drag already works because listeners are on `window`, but `e.target !== canvas` gates the click branch (625), so rail/overlay clicks do not draw. Good.

### Why New world is hard / fails silently
1. `nw-create` handler (739-756): empty id -> `POST` returns 400 `{"error":"bad id or size"}` -> `api()` throws `"/__editor/new-world: 400 {…}"` -> written only to `#log` (754), which is at the very bottom of a scrolling sidebar (invisible). Never goes to `#status`.
2. Server returns the same generic `bad id or size` for bad id AND bad km range (`vite-plugin.ts:113-120`) while `blankWorld` has precise messages (`world.ts:91-99`) that the endpoint never reaches. Fix: call `blankWorld` first in a try/catch and return its message (422/400).
3. Id must be typed by hand (regex `^[a-z0-9-]+$`) with no inline validation or auto-suggestion; the `confirm("Discard unsaved edits?")` runs BEFORE validation (740).
4. A created world is NOT usable for compile: it needs two lines added by hand to `tools/map-compiler/cli.ts` (`KNOWN_AREAS`, cli.ts:102) and for synthetic routes an entry in `POST_COMPILE` (`vite-plugin.ts:28`). The instruction is dumped in `#log` only. Save works (PUT) but "Save & compile" for a new world returns "unknown area". Plan must decide: auto-register (script edit of cli.ts is fragile) OR make the compiler discover `*.config.ts` dynamically. Recommend: surface a readable info-bar note + keep the register lines in the success toast with a Copy button; track dynamic discovery as an Open Question (out of this phase unless cheap).
5. Size limits 0.5..10 km (`world.ts:55-56`) are shown only as `min/max` attrs, not enforced client-side.

### Why image import overlays (D-06 root cause)
`im-go` handler (993-1025) calls `appendImportedRoads(roads, proj, g, …)` on the CURRENT area's `roads` (1010). `appendImportedRoads` is explicitly additive (`image-import.ts:99-104`: "Additive: nothing is snapped to pre-existing roads"). The default selected area on load is `my-map` (1039), so imported roads landed in my-map. For D-06: Import must (1) compute scale from image + the dialog's Width, (2) call `blankWorld(id, widthKm, heightKm, now)` with `heightKm = scale.heightM/1000` (exactly what `image-import.e2e.test.ts:35-41` already does, then offset `{0,0}`), (3) `POST /__editor/new-world`, (4) load that area, (5) append roads. Note `MAX_WORLD_KM=10`, `MIN=0.5`: an image whose derived height is < 0.5 km or > 10 km will throw; must show that in the dialog. Needs a new combined endpoint or a client-side sequence: recommend client sequence new-world -> loadArea -> appendImportedRoads -> save, with rollback message if the middle fails (the world files exist on disk; tell the user).
Offset X/Y fields become unnecessary in the fresh-map flow (always 0,0); drop from the main UI (keep in code default). The mask overlay (`drawImportOverlay` 905-915) and preview (917-945) are useful in the dialog preview stage; keep them but they draw on the main canvas, so the Import dialog should be non-modal OR must render its own small preview canvas. Recommend: Import-dialog = modal for file + Width + threshold; after "Create from image" the map opens fresh and a side flyout offers re-trace? Simplest: modal with file, Width, Road width, Highway, Surface, Threshold, Advanced `<details>`, a live read-out, and `Preview` drawing into a small `<canvas>` thumbnail in the dialog (mask only, not graph). Keep the existing full-canvas preview out of scope.

### Real width precision (0.9345318244236143)
`editor.ts:880-883`: `const worldKm = world.widthM / 1000; impInput("im-km").value = String((worldKm*1000)/c.width <= COARSE_M_PER_PX ? worldKm : c.width/1000)`. `world.widthM` is a projected bbox float (e.g. `934.5318…`), stringified at full precision. Elsewhere `updateImportUi()` writes `toFixed(3)` (815-816, 817), so only this one initial assignment leaks. D-05 fix: format derived display values with a shared `fmt3()` (keep raw in a `number` variable, never read back from the formatted string). Also note the m/px field re-derives km on every `oninput` (loop risk: writing back 3 dp into the driving field would degrade precision; the existing code only writes the non-driving field, preserve that).

### DIAGNOSIS: why "raise/lower isn't working"
Facts verified from code: default tool is `raise` (`editor.ts:75`); radius 12 m, strength 0.5 (`tool-dispatch.ts:319-320`); `raiseLower(..., rateM=1)` adds `strength * falloff` metres at the centre per dab = **+0.5 m at the centre, less across the brush, per click**; dabs every `max(0.25, radius/4)` = 3 m of drag (413-433); the 1-2-1 relax (`relax=true`, `terrain-brush.ts:256-286`) then pulls the peak down further; default camera is ~370 m from the origin (`camera.position.set(200,250,200)`), and a 0.5 m bump with soft shading at that distance is nearly invisible. Ranked causes:
1. **(Most likely, MEDIUM) Effect is imperceptible at default settings and there is no feedback.** Status after an edit is just "Edited." (958); nothing reports height change. A user who clicks once at far zoom sees nothing. Fix: show a readout "cursor height / last change +0.45 m" in the info bar, raise default strength (or define strength as m/s of hold), and add a visible delta-height number.
2. **(Likely, MEDIUM) Nothing happens when no area is loaded**: `pointerdown` returns early on `!area` (992) with no message (`#empty` overlay says only "Pick an area or press New..."). The info bar must say "Load or create an area first" on any canvas click with no area.
3. **(Possible, LOW-MEDIUM) Road hold mask**: `roadVertexMask` holds ALL vertices flagged road in paint or within the levelled radius of any graph edge (`terrain-road.ts:518-542`) and `runHeightOp` skips held vertices (`terrain-brush.ts:212-219`). On a road-dense area (e.g. an imported or painted map) clicking near roads silently does nothing, and unlocked roads change this (rdx quick task). No "blocked by road" feedback (`NO_OP` returns `slopeClamped:false`). Fix: report "N vertices held by roads (lock the road to ... / unlock it)".
4. **(Possible, LOW) 35-degree slope limiter** (`terrain-limits.ts:8`, `limitSlope` after every op): with 3 m cells the cap is ~2.1 m height difference per cell; raising next to a steep pre-existing neighbour is clamped (`freezePreexistingSteep`) and reports only the status "Slope limit reached". Block step 1 m is safe.
5. **(Possible, LOW) Alt on Windows**: Alt+click lowers. Chrome on Windows does not normally open a menu on Alt+click, but Alt press/release alone can move focus to the browser menu bar / steal subsequent keystrokes in some configs, and the code ignores all keys while `e.altKey` (1245). Also window-manager Alt+drag moves windows in some setups. The user dislikes it regardless (D-08); removing the modifier removes this class.
6. Not causes (verified): OrbitControls LEFT is `null` so no conflict; `#empty` has `pointer-events:none`; pointer capture is set correctly; `Modifiers` plumbed correctly; tests (`tool-dispatch.test.ts:38`) prove the op works headless. => the logic is sound; the issue is perception/feedback or state (no area).
**Cannot be verified without a browser.** Plan should add a human-verify checkpoint: load an area, click Raise once at a closer zoom, confirm visible lift and the info-bar readout.

## 3. Core ops reusable for Grid select / push-pull (src/core/terrain-brush.ts)

Reusable: `runHeightOp(grid, window, compute, rec, relax, opts)` (185; internal, NOT exported): handles snapshot, road-hold (`opts.roadMask`), recorder `beforeHeightsWrite`, slope limiter with pre-existing-steep freeze. `raiseBlock` (402) = fixed step on an N x N block through `runHeightOp` with `relax=false` (sharp edges). `blockWindowAt` (376), `smoothRegion` (439) is the existing "operate on a CellWindow" op. `createStrokeRecorder`/`StrokeDiff`/`createUndoStack` give one-entry undo. `windowBetween` in `tool-dispatch.ts:441` converts two world points into a clipped vertex window.

Missing (new work, in `src/core/terrain-brush.ts` + `tool-dispatch.ts`):
- Export a **window-based** raise: `raiseWindow(grid, win: CellWindow, deltaM: number, rec, opts)` (`raiseBlock` minus the block-window computation; `raiseBlock` can delegate to it). Absolute-from-base variant for push/pull: during a Ctrl+drag, each move must set `h = base + delta` from a Float32 snapshot taken at stroke start (NOT incremental `h + step`), otherwise slope-limit clamping makes the drag non-linear/ratcheting. The `compute(x,z,h)` callback in `runHeightOp` can ignore `h`; but the limiter then needs the original state: recorder `before` values serve as the base (recorder merges earliest-before).
- A **selection state** in the dispatcher: `gridSelect` tool, `selection: CellWindow | null`, `setSelection/clearSelection/getSelection`, `raiseSelection(sign, stepM)` (one undo entry per button press), `pushPull(dyPx -> metres)` stroke mode. Reuse `windowBetween` and the smoothBox box-preview plumbing for the drag-rectangle. Selection must persist after pointerup (unlike smoothBox which commits on up), so Grid select is NOT the smoothBox path; it is a pure UI selection until ▲/▼ or Ctrl+drag.
- `Modifiers` gains `ctrl: boolean` (and drop use of alt for raise). `strokeEvent` must pass `e.ctrlKey` and, for push/pull, the pointer's screen dy (the dispatcher is world-space only; give it a `pointerMoveDelta(dyMetres)` or pass metres computed in the editor = `-dyPx * metresPerPixel` where metresPerPixel = a user-set sensitivity, e.g. 0.05 m/px with Shift fine).
- Split Raise/Lower: add `"lower"` to `Tool` (line 48), `TOOL_KEYS` entry, call `raiseLower(..., tool==="lower"?-1:1, ...)` at line 384; remove `s.alt` from raise/block (block lower also needs a distinct "Block lower" or a direction toggle: D-08 only mentions raise/lower; recommend Block gets a Raise/Lower segmented control in its flyout instead of Alt). Lock tool's Alt+click-select (516, 501-505 tests) should move to Shift+click for consistency (or leave; low priority, flag to user).
- Height read-out helper (`sampleTerrainHeight` exists, `terrain-grid.ts`) for the info bar.

## 4. Shared shell design (D-02)

**Serving**: no multi-page config. `vite.config.ts` only registers the two dev middleware plugins (`mapEditorApi`, `terrainEditorApi`, `apply:"serve"`). Both pages are reached at `/tools/map-editor/index.html` and `/tools/terrain-editor/index.html` on the dev server; neither is a build input and `vite build` ignores them. A shared module only needs relative imports (`../editor-shell/…`) and `<link rel="stylesheet" href="../editor-shell/shell.css">` (Vite dev serves it; no config change). Note: `tools/` is under `tsconfig` `include` and biome, so shell files are type-checked and linted.

**Tests**: `vitest.config.ts` has `environment: "node"` and default include (`**/*.test.ts`), so `tools/**/X.test.ts` runs. **No jsdom/happy-dom is installed** - DOM code cannot be unit-tested. Rule: every shell behaviour with logic must be a pure function in its own file (stepper math, tooltip-pref parse/serialize with injected `Storage`-like, keymap resolution, undo/redo stack, info-bar formatters), with DOM builders as thin untested wrappers verified by human checkpoints. Existing precedent: `isTextEntryFocused` has a Node fallback for exactly this (`src/debug/debug-gate.ts:59-71`).

**Common between the editors today** (duplicated): `$()` helper, `api()` fetch wrapper, `setStatus`/`log`, `dirty`+`beforeunload`+`confirm("Discard unsaved edits?")`, area `<select>` + load, `#new-form`, undo/redo buttons, button CSS (near identical `<style>` blocks), number+range linking, key handling, `.dirty` marker.

**Recommended layout** (`tools/editor-shell/`):
```
tools/editor-shell/
  shell.css            # all layout/theme: menubar, rail, flyout, infobar, toast, dialog, stepper, tooltip
  shell.ts             # createShell(opts): builds menubar/rail/flyout/infobar/zoom pad into #app, returns handle
  menubar.ts           # dropdown menus (button + role=menu), click/hover/Escape/outside-click close
  tool-rail.ts         # floating left rail, tool buttons from a descriptor array, flyout host
  infobar.ts           # setField(key,text), setStatus(text,"info"|"error"), dirty marker; pure formatters in format.ts
  dialog.ts            # openDialog({title, body, actions}) over <dialog>.showModal(); returns Promise, inline error slot
  tooltips.ts          # attachTooltip(el,text); setEnabled(); pref in localStorage via prefs.ts
  prefs.ts   (+test)   # getPref/setPref wrapping localStorage in try/catch with in-memory fallback
  stepper.ts (+test)   # createStepper({value,min,max,step,coarse,decimals,onChange}); pure stepValue()
  select.ts            # content-sized select (CSS field-sizing:content with width fallback)
  keys.ts    (+test)   # shortcut registry; pure resolveShortcut(event-like, bindings, textFocused)
  history.ts (+test)   # generic undo/redo of snapshots (map editor needs it; terrain has its own stack)
  format.ts  (+test)   # fmt3(n), fmtMetres, fmtKm
  api.ts               # shared fetch wrapper that throws Error with server's {error} message
```
**DOM/CSS patterns** (all vanilla):
- Layout: `#app{position:fixed;inset:0}`; canvas `position:absolute;inset:0`; menubar `position:absolute;top:0;height:28px`; rail `position:absolute;left:8px;top:44px` (vertical buttons); flyout `position:absolute;left:56px;top:44px` (a panel, `max-height:calc(100% - …)`, only that panel may scroll if tall); zoom/fit/pan pad bottom-right above info bar; Undo/Redo/Clear top-right; info bar `position:absolute;bottom:0;height:24px;display:flex` with `white-space:nowrap; text-overflow:ellipsis`. All overlays `pointer-events:auto` only on the controls themselves (container `pointer-events:none`) so canvas keeps events. Rail/flyout sit above the canvas stacking context (`z-index`), and the **terrain `wrap` ResizeObserver** (`editor.ts:253`) must observe the full-bleed `wrap` (no longer shrunk by a sidebar): canvas size = window size.
- Menus: `<button aria-haspopup=menu>` + absolutely positioned `<div role=menu>`; items `<button role=menuitem>`; close on outside `pointerdown`, `Escape`, item activation.
- Modal: native `<dialog>` with `showModal()` (gives focus trap, Escape cancel, backdrop `::backdrop` styling; Chrome-only target so fine). Keep an inline `<div class=dialog-error>` inside; **do not use `confirm()`** for the new flows (the existing `confirmDiscard` can stay or be replaced by the dialog; blocking `confirm()` is untestable but acceptable for "Clear all"/discard - the user asked for a confirm; prefer `<dialog>` for consistent look).
- Tooltip: single floating `div#tt` positioned from `pointerenter` (delay ~400 ms) using `data-tip` attribute; avoid `title=` (cannot be toggled). One global listener via event delegation on `[data-tip]` reads `prefs` "tooltips" (default on). Toggle lives in Help menu ("Tooltips: on/off") and persists via `prefs.ts` (`localStorage` throws in some privacy modes -> try/catch, in-memory fallback).
- Stepper: `<div class=stepper><button>-</button><input inputmode=decimal><button>+</button></div>`; big hit targets (>=32 px); `keydown` ArrowUp/Down step, Shift = coarse (e.g. 10x); `Enter` commits; clamp to min/max; display `decimals`; parse with `Number()`, reject NaN (revert); wheel stepping optional (skip). **Use `type="text" inputmode="decimal"`, not `type=number`**: native number input spin buttons are tiny, and its arrow-key behaviour conflicts with Shift stepping. Must stop propagation of the arrow keys so global handlers do not also pan the map (see pitfalls).
- Content-sized selects: `select{field-sizing:content}` (supported in Chrome 123+; verify, MEDIUM) with `width:auto` fallback; the existing CSS forces `width:100%` which is the cause of full-width selects today.

## 6. Pitfalls

1. **Keyboard vs text entry.** Two inconsistent guards: map editor checks only `INPUT`/`SELECT` tagName (`editor.ts:662-665`; blocks everything including Ctrl+S), terrain checks `INPUT[text|number]`/`TEXTAREA` (1224-1227; ignores `range`, `select`, `contenteditable`). A helper `isTextEntryFocused(el)` exists at `src/debug/debug-gate.ts:59` (INPUT any type incl. range/checkbox, TEXTAREA, contentEditable; has Node fallback + tests in `tests/debug-gate.test.ts`) but that module also reads `location`/registers debug keys at import, so **do not import debug-gate from tools**; copy/extract the 12-line function into `tools/editor-shell/keys.ts` (or move it to `src/` util and re-export from debug-gate). Treat checkbox/range/select/button focus as NOT text entry for tool hotkeys but make Arrow keys ignore when a stepper/select/range has focus; blur selects after change (terrain already does `surf.blur()` at 1069). Also bail on `e.isComposing`, `e.repeat` for toggles, and `dialog[open]` (no canvas hotkeys while a dialog is open; `<dialog>` modal traps focus but window keydown listeners still fire).
2. **New shortcuts to resolve.** Map editor `Z`/`S` bare keys must become Ctrl+Z / Ctrl+Shift+Z / Ctrl+S (browser defaults: Ctrl+S saves page, so `preventDefault` is mandatory; Ctrl+N/Ctrl+O are reserved by Chrome and CANNOT be overridden - do not bind New to Ctrl+N; use plain keys or menu only). Avoid Ctrl+W/T/R/Tab. Use `e.code` (layout-independent, terrain does) but display labels from a map. `[` `]` conflict: terrain uses them for stamp rotation (1269); D-09 wants them for "active value" - make them context-sensitive: stamp tool keeps rotation, all else adjusts the primary value (radius). Arrow keys: map editor pans with them (675); D-09 wants arrows adjust value when a value control is focused or a tool value is "active" - decide: arrows pan the map unless a stepper has focus; `[` `]` always adjust the tool's primary value. Document in Help menu.
3. **Ctrl+drag on Windows/Chrome**: Ctrl+left-click is a normal click on Windows (it is "secondary click" only on macOS - acceptable, desktop Windows is the target; note it). Ctrl+wheel is already special-cased (browser zoom blocked via capture handler, `editor.ts:136-153`); Ctrl+left-drag on the canvas does not conflict with OrbitControls (LEFT null). Check `e.ctrlKey` at `pointerdown` and latch the mode for the stroke (do not re-read per move, the user may release Ctrl mid-drag). Also `e.metaKey` for mac parity. Prevent text selection / image drag during drag (`user-select:none` on overlay + `e.preventDefault()` on pointerdown) and use pointer capture (terrain already does; map editor uses window mouse listeners so it tolerates leaving the canvas).
4. **Alt**: remove from raise/lower/block entirely (D-08). Line 1245 `if (mod || e.altKey) return` then can stay. Avoid any new Alt binding.
5. **Pointer capture & overlays**: the rail/flyout float over the canvas; the terrain `pointerleave` handler (1008) hides the cursor ring when the pointer enters an overlay (correct). `setPointerCapture` must be released on `pointercancel`/dialog open. Opening a `<dialog>` mid-stroke must cancel the stroke.
6. **Losing unsaved work**: both `New` and `Import` must call the discard-confirm first and ONLY AFTER validation passes (map editor currently confirms before validating). `loadArea` on map editor clears `undoStack` so undo can't recover after New/Import; the terrain `createArea` also prompts `confirm` for overwrite when the name exists (`editor.ts:411-412`) - in the new popup show "already exists" as an inline error instead of overwrite (D-06 lists "already exists" as a validation error). Map-editor server already refuses overwrite (`WorldExistsError` -> 409).
7. **Save guards**: terrain `save()` (`editor.ts:~430-480`) refuses saves for blocking road-graph failures (`saveBlockMessage`) and stale unlocked roads (`staleRoadBlockMessage`) and server re-checks (`vite-plugin.ts` -> `assertSaveableGraph`, `assertGradedRoads`); messages currently go to status + `#log`. In the new shell they must surface in the info bar as errors (D-03) and the unsaved marker must not clear on failure. A newly created area is `dirty=true` and unsaved on disk; the Grid-select raise on roads must respect the same mask (use `heightOpOptions(area)` - `tool-dispatch.ts:134`).
8. **Info-bar content** needs data the terrain editor already computes: cursor hit (`lastHit`/`updateCursor`), area id/size from `area.grid` (`cols*cellSizeM`), cell size, road count `area.graph.edges.length`. Map editor: world `widthM/heightM`, `tileM`, `roads.response.elements.length`, `buildings…`. Cursor-coordinate updates on every mousemove must not trigger a full redraw just for text (write DOM textContent only).
9. **Canvas resize**: map editor `resize()` sets `canvas.width=clientWidth` once on window resize; with a full-bleed canvas fine. Do not scale by devicePixelRatio (would break `toWorld`).
10. **HTML-injection**: map editor builds panels with `innerHTML` from tag values (e.g. `value="${t.name ?? ""}"`, 505) - an OSM name containing a quote breaks the field (existing bug). Terrain editor deliberately avoids innerHTML for status text (WR-06). Shell must set text via `textContent`; fix the map-editor selection panel when restructured.
11. **Select tool box semantics (D-07)** need geometry predicates: road inside a box = ALL vertices inside (or any?) - decide and document: recommend "any vertex inside" for delete, with a Shift-modifier for fully-inside; buildings = centroid inside. Existing helpers: `pointInPolygon`, `distanceToWay` (`model.ts`). Pure function `waysInBox(env, proj, box, mode)` with tests. Deleting a way whose nodes are shared by other ways is fine (nodes are per-way arrays, no node table) but leaves dangling junction ids only in other ways (harmless).
12. **"Disable"**: see section 1; unresolved until the compiler's tag handling is checked.
13. **Eraser** tool must snapshot once per drag (not per hit) -> one undo entry; reuse `pickRoad`/`pickBuilding` with tolerance `max(3, 8/scale)`.
14. **Windows/Vite**: Vite dev middleware writes via `writeFile` to `tools/map-compiler/areas/`; new-world creates `.config.ts` files, which the Vite watcher may pick up (no import graph effect). `execFile(process.execPath, args)` compile path already works on Windows.

## Code Examples

Pure stepper maths (testable in node):
```ts
export function stepValue(v: number, dir: 1 | -1, o: {step: number; coarse: number; min: number; max: number; decimals: number}, shift: boolean): number {
  const raw = v + dir * o.step * (shift ? o.coarse : 1);
  const clamped = Math.min(o.max, Math.max(o.min, raw));
  const f = 10 ** o.decimals;
  return Math.round(clamped * f) / f;
}
```
