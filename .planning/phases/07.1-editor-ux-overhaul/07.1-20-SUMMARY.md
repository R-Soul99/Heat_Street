# Phase 07.1 Plan 20: Map editor blank map, start screen and terrain handoff Summary

Blank maps are now plainly visible with an "Empty map" hint, a dev-server reload reopens the current map instead of the start screen, and Open in terrain editor only navigates once /__terrain/areas lists the map, with every failure shown in a dialog.

## Root causes (reproduced on a second dev server, port 5181, headless Chrome via CDP)

**H1 page reload from endpoint writes: REJECTED as stated; related mechanism found.**
- With the map editor page open (window marker set), POST /__editor/new-world and POST /__editor/to-terrain (which rewrites authored-maps.json, both generated registries, public/maps/*) left the marker intact: no page reload. Neither editor page nor vite.config.ts imports the generated registries or public/maps files, so Vite has nothing to reload.
- The Vite log did show one real restart: `[vite] src/core/terrain-brush.ts changed, restarting server... server restarted.` That file is in vite.config.ts's import graph (config -> terrain-editor/vite-plugin -> ... -> src/core), so ANY edit to such a source file (here by a parallel executor) restarts the server, and Vite's client then reloads the page, dropping in-page state. A reload in the middle of a session sends the user back to the start screen because main() always called openStartScreen(). That is the only reproduced route to "start screen comes back". It cannot be removed with `server.watch.ignored` (these are source files) and lazy imports do not help (esbuild still follows dynamic imports into the config dependency set), so the fix is the resume marker (below), not a vite config change.

**H2 blank map looks black: CONFIRMED (low contrast), canvas-size theory only a latent risk.**
- Computed: worldFromBbox for a 0.5 km blank map = 500.0 x 500.0 m; fitView at 1280x720 gives scale 1.28 (640 px square, fine). With a 0x0 canvas fitView returns scale 1e-6 (invisible), and resize() never refit afterwards, so a late layout would leave an unusable view. Headless run at 1254x568 did fit correctly.
- Screenshot of a new blank map: world fill #14161a on background #0b0c0f with a #667 border and 5-12 % grid is near-black; no text said the map was empty.

**H3 empty map conversion: CONFIRMED (compile fails), and a second failure for sparse maps.**
- POST /__editor/to-terrain/<blank> returned ok:false: `compile-map: unhandled error - buildRoadDistanceField: graph has no road segments to measure against` [exit 1]. No public/maps output is written. checkRoads() reports nothing for zero roads, so there was no early warning.
- Same endpoint with one 200 m road: compile OK, then the post-compile route authoring step (author-newton-routes.ts, run for every legacy authored map) fails with `Cannot read properties of undefined (reading 'x')` (degenerate ring points). With a "+" of two roads: `courses[0].checkpoint count must be 5-8`. So small or sparse road networks cannot be converted today. Conversion itself (convert-authored.ts) does not use routes; the route step is out of this plan's files, so it is reported, not changed (see Deferred). The dialog now includes the compiler's last log line so this is visible.

**popp-roads (read only):** /__editor/status = registered, format terrain, hasTerrain true, hasCompiled true; /__terrain/areas lists it; GET /maps/popp-roads.terrain.json 200 (88479 B) and .bin 200 (458871 B); parseTerrainSidecar parses it. So the data is fine; any earlier failure was in the navigation/reload path, which is now guarded. End-to-end in headless Chrome: open popp-roads, reload page -> reopens popp-roads (no start screen), Open in terrain editor -> existing-terrain dialog -> Open existing terrain map -> lands on /tools/terrain-editor/index.html?area=popp-roads.

## What changed

- `handoff.ts`: `resumeMarker`, `shouldResume` (validates shape, `^[a-z0-9-]{1,64}$`, 30 s TTL; T-07.1-20-01), `waitUntil` (injected sleep, throwing check = false), `terrainListed` (exact match). 8 tests in `handoff.test.ts` (plus the fitView 0.5 km case).
- `editor.ts`: marker written before new-world, save, compile, to-terrain and after every loadArea; main() reopens the marker's map instead of the start screen (marker consumed once); blank map drawn with #1c2026 fill, #8ab 2 px border, centred "Empty map W x H km. Press R to draw a road." hint; loadArea calls resize() first, resize() refits while still on the fit view.
- `openInTerrainEditor`: single `window.location.href` site, reached only after `waitUntil(... "/__terrain/areas" ...)` (20 x 500 ms, T-07.1-20-03); every failure path opens a "Could not open in terrain editor" dialog; zero-road guard "Draw a road first"; interrupted conversion reports "Conversion finished; use Open in terrain editor to continue." after a reload.

## Deviations from Plan

- vite.config.ts and tools/map-editor/vite-plugin.ts unchanged (no root cause on endpoint writes; see H1). Plan permitted "none needed with reason".
- Did not edit the compile pipeline for empty or sparse maps (out of files_modified); the guard dialog covers the empty case, sparse-map route failure is surfaced in the error dialog.
- Tasks 2 tests were written together with the implementation (single commit) rather than as a separate failing-first commit.

## Deferred Issues

- Route authoring (`author-newton-routes.ts`, run by compileArea for every legacy authored map) fails for small/sparse networks (single road: undefined .x; fewer than 5 checkpoint nodes: parseCourseData). Converting such a map to terrain therefore fails at the compile step even though convert-authored does not need routes. Suggested follow-up: make the route step non-fatal in to-terrain.
- Vite restarts on edits to src files in the config graph; the resume marker only masks the symptom.
