## Summary

This is a pure presentation/layout refactor of one shared shell (~1,000 lines across `tools/editor-shell/`) plus two callers. No new packages. The shell is plain TS + DOM and CSS, and vitest runs in the `node` environment with no jsdom/happy-dom installed [VERIFIED: vitest.config.ts, package.json grep]. Therefore only pure helpers are unit-testable; DOM/CSS behaviour must be verified manually or by structural review. The established pattern (`dock.ts`, `stepper.ts`, `tip-place.ts` pure + tested) should be extended with new pure helpers: tool grouping, scrub-to-steps maths, tooltip phase timing, sidebar-width/canvas-rect maths.

**Three discrepancies between the approved UI-SPEC and the actual code that the planner must handle:**

1. **The map editor already uses `layout: "dock"`**, not "classic" (`tools/map-editor/editor.ts:1693`, comment "GD-LAYOUT"). Both editors render `.shell-toolbar-bottom` + `.shell-topbar` (empty in the map editor, hidden by `:empty`). The UI-SPEC's "Tool rail (map editor, classic) ... vertical rail" and "classic infobar 24px" describe a layout neither editor uses now. UI-SPEC Open Item 1 ("map editor keeps a vertical rail") would in fact be a layout switch that contradicts D-03. Recommendation: both editors keep the horizontal bottom toolbar with dividers (consistent with D-03 and "unify across editors"); treat `classic` (`.shell-rail`, `.shell-flyout` fixed at left:64) as dead code to delete or leave untouched. [VERIFIED: grep of `layout:` in both editors]
2. **Canvas elements differ**: terrain's `.shell-canvas` is the `<div id="wrap">` containing `<canvas id="view">`, `#road-problems`, and `#empty`; the map editor's `.shell-canvas` is the `<canvas id="map">` itself. Offsetting `.shell-canvas` by the sidebar width works for both, and moves `#road-problems` (absolute, left:8 inside wrap) with it automatically.
3. **`#to-terrain-btn` (map editor)** is appended to `#app` at `left:8px; top:36px` (`tools/map-editor/index.html:22`), which will sit under/over the new sidebar. It needs a new home (offset by sidebar width, or move into the File menu only / sidebar footer). Its comment "Top-left is free" becomes false.

**Primary recommendation:** Build the sidebar as the new owner of `shell.flyout` (keep the property name as an alias to the sidebar body so both editors' `buildFlyout`/`setTool` need only trivial changes), delete `placeFlyout`/`flyoutAnchor`/top-row logic, drive canvas offset from a single CSS custom property (`--sidebar-w`) with a fixed (not content-driven) width, rewrite `createStepper` internals only (signature unchanged), and put every new piece of logic that can be pure into a tested `.ts` file.

### Target structure

### Pattern 1: Fixed sidebar width, exposed as a CSS variable (recommended over content-driven)
UI-SPEC says `width: max-content`, clamped 200-280px. **A content-driven width changes the canvas width on every tool switch**, which (a) triggers a resize of the WebGL/2D canvas and (b) in the map editor does NOT trigger a re-measure because it only listens to `window` `resize` (`tools/map-editor/editor.ts:1338`; `resize()` reads `canvas.clientWidth`). Recommended: pick one fixed width, e.g. `--sidebar-w: 240px` (inside the 200-280 spec range, UI-SPEC's own "avoid canvas jitter" goal), so canvas geometry is stable and unit-testable. Also still add a `ResizeObserver(canvas)` to the map editor (cheap, mirrors terrain's `new ResizeObserver(resize).observe(wrap)` at `terrain-editor/editor.ts:428`). Flag to planner/user: this deviates slightly from "sized to content" in D-06; the min-200/max-280 clamp already makes it near-fixed. Content wider than the bar wraps/scrolls (`overflow-y: auto`, `overflow-wrap`).

### Pattern 2: Shell stays editor-agnostic via `ShellTool.pin`
Raise/Lower pair is terrain-specific but shell must not know tool ids. Replace `dock?: "top"` with a generic marker (e.g. `placement?: "sidebar-pair"`) or reuse `dock:"top"` semantics ("pinned to the sidebar header"). Smallest diff: keep `dock: "top"` on Raise/Lower in `RAIL_TOOLS`, and have `createToolRail` render `dock:"top"` tools as the sidebar pair (arrow-only glyph buttons, `aria-label` = label). `splitDockTools` + its test stay valid and reused; only `flyoutAnchor` (and its tests) become obsolete.

### Pattern 3: Pure helpers, node-testable (extend `dock.ts`/`stepper.ts`/`tip-place.ts` pattern)
- `groupTools(tools)` -> `{group, tools}[]` preserving order, consecutive same-group runs (new file `tool-groups.ts` or in `dock.ts`).
- `scrubSteps(dxPx, carry, pxPerStep)` -> `{steps:int, carry}` in `stepper.ts` (UI-SPEC: "pixels -> integer steps, remainder carried", 8 px/step, <3 px = click-to-focus).
- `wheelDir(deltaY)` -> `1|-1` (wheel up = increase; handle `deltaY === 0`, trackpad tiny deltas).
- `tipPhase(elapsedMs)` -> `"hidden"|"short"|"long"|"faded"` (700 / +1500 / 3000 ms) so timing is testable without a DOM.
- `displayLabel(tool)` for the >12-char shortLabel rule.

### Anti-patterns
- Do not use `title=` for tooltips (existing rule: cannot be toggled).
- Do not write HTML via `innerHTML`; all text via `textContent` (existing WR-06 rule).
- Do not let the stepper push undo history (UI-SPEC: "steppers do not push history themselves").
- Do not measure the canvas from `window`/`#app` origin.

## Common Pitfalls

### Pitfall 1: Pointer offset by sidebar width
**What goes wrong:** brush/pick lands sidebar-width left of the cursor. **Why:** math using window coordinates. **Avoid/verify:** all pickers already use `canvas.getBoundingClientRect()` (table above); fix map `drawHud`. **Warning sign:** scale bar drawn ~240px right of the toolbar in map editor.

### Pitfall 2: Canvas not resized when layout changes
Map editor's `resize()` only runs on `window.resize`; `canvas.width = clientWidth` happens once. If the sidebar is shown/hidden or width changes after load, the backing store goes stale (blurry/offset). Add `ResizeObserver` on the canvas.

### Pitfall 3: Old CSS selectors still styling new controls
`dialog button`, `.shell-history button`, `.shell-viewpad button` and the shared selector at shell.css:61-75 give 3px radius/`#000` border/`--panel-2` bg and `dialog button{padding:6px 14px}` to any `button` inside a dialog, which would bloat the 16px arrows in New-popup steppers. Scope the new arrow styles with higher specificity (`.value-box .vb-arrow`).

### Pitfall 4: `field-sizing: content` support
`select{field-sizing:content}` already used; Chromium 123+. Input `field-sizing: content` works on inputs in Chromium too; provide `min-width:4ch;max-width:10ch` and `size`/`ch` fallback. Desktop Chromium is the dev target; acceptable. [ASSUMED: Firefox lacks `field-sizing` at time of research; the editors are dev-only tools so low risk.]

### Pitfall 5: Wheel zoom and page scroll
Wheel `preventDefault` needs `{passive:false}`; Chrome treats document-level wheel listeners as passive by default but element-level is fine. Hover-only wheel can hijack sidebar scrolling (Open Question 2).

### Pitfall 6: Drag-scrub vs focus/click
Pointer-down on the input normally focuses it and starts text selection. Need `preventDefault` on pointerdown after capture only once movement exceeds 3 px, else focus on pointerup (UI-SPEC "press without movement focuses input"). Letter hotkeys are suspended only while an input is focused (`isTextEntryFocused`): a scrub must not leave the input focused, or `[ ]`/letter tool keys stop working. Blur after scrub.

### Pitfall 7: Hold-repeat timers leaking
Existing `hold()` clears on pointerup/leave/cancel; when moving the ▲▼ into one box with pointer capture or `setPointerCapture` for scrub, `pointerleave` semantics change. Keep arrows' hold logic separate from scrub logic (arrows are separate buttons, not part of the scrub surface).

### Pitfall 8: Tooltip fade state machine
A hidden tooltip being re-shown on the same target after the 3 s fade (pointerover bubbles from children: value box has 4 `data-tip` children; moving between them fires `pointerover` for a different `closest("[data-tip]")`). Track `consumedTarget` and compare to the new `closest` target; moving between box parts is a *new* target, so tooltips legitimately re-arm. Acceptable; document it.

### Pitfall 9: Editor `index.html` inline CSS
Both HTML files carry inline styles that assume the old geometry (`#to-terrain-btn left:8px`, `#legend top:248px`, `#road-problems left:8px`). Terrain `index.html` has uncommitted user edits: read only; make additional changes minimal and coordinate (the user's working-tree changes there must be preserved; prefer doing layout in `shell.css` so `index.html` needs no edit). Same for `save-guard.ts` and `tests/road-save-guard.test.ts` - unrelated to this phase; do not touch.

### Pitfall 10: Tool-order vs hotkeys
Verify hotkey dispatch uses key->id maps, not array index, before reordering `RAIL_TOOLS` and the map tools list.

## Code Examples

### Scrub maths (pure, testable)
```ts
// stepper.ts - new, node-testable (pattern follows existing stepValue)
export function scrubSteps(
  dxPx: number,
  carry: number,
  pxPerStep = 8,
): { steps: number; carry: number } {
  const total = carry + dxPx;
  const steps = Math.trunc(total / pxPerStep);
  return { steps, carry: total - steps * pxPerStep };
}
// apply: for (let i = 0; i < Math.abs(steps); i++) v = stepValue(v, steps > 0 ? 1 : -1, spec, shift)
```

```ts
let down: { x: number; carry: number; moved: boolean } | null = null;
box.addEventListener("pointerdown", (e) => {
  if ((e.target as HTMLElement).closest(".vb-arrow")) return;
  down = { x: e.clientX, carry: 0, moved: false };
  box.setPointerCapture(e.pointerId);
});
box.addEventListener("pointermove", (e) => {
  if (!down) return;
  if (!down.moved && Math.abs(e.clientX - down.x) < 3) return;
  if (!down.moved) { down.moved = true; e.preventDefault(); input.blur(); box.classList.add("scrubbing"); }
  const r = scrubSteps(e.clientX - down.x, down.carry, 8);
  down.x = e.clientX; down.carry = r.carry;
  // apply r.steps via stepValue (shift = coarse), then apply(v, true)
});
const end = (e: PointerEvent): void => {
  if (down && !down.moved) input.focus();   // press without drag -> type
  down = null; box.classList.remove("scrubbing");
};
box.addEventListener("pointerup", end);
box.addEventListener("pointercancel", end);
box.addEventListener("wheel", (e) => { e.preventDefault(); /* dir = e.deltaY < 0 ? 1 : -1 */ }, { passive: false });
```
