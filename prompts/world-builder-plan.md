# Heat Street: World Builder Plan

**Goal:** author large, non-real-world maps by drawing a road layout as a black-and-white image, importing it at a chosen scale in km, splitting it into tiles, and streaming those tiles in and out at runtime so only the area near the player is in memory.

**Why:** real-world (OSM) maps are being dropped, mainly to avoid the OpenStreetMap credit. Areas are currently capped at 2000 m (`MAX_AREA_SIZE_M`, `src/core/terrain-limits.ts`), and one area is one world (one heightfield collider, one road graph, one paint map). Bigger worlds need several areas joined together.

This builds on `prompts/map-authoring-plan.md` (the existing raw-OSM envelope, the compiler and the map editor in `tools/map-editor`). Read that first.

## Decisions already made
- **Roads come from a B&W image.** Black = road centreline, white = nothing. Stroke thickness in pixels is ignored, because it would inflate when the map is scaled up.
- **Width is set in metres after import**, as a default for all roads plus a per-road override. Width varies by splitting a road at a node, not by tapering.
- **Heights start at a configurable base height**, not 0, so terrain can be sculpted up or down from a mid level.
- **Master plan first, then split.** The master plan owns layout. Tiles own terrain detail (sculpting).
- **Tiles are ordinary areas** (same format the terrain editor already saves), placed in a shared coordinate space by a small `world.json` manifest.

## Constraints to respect
- Stack and layering rules in `CLAUDE.md`. `src/physics` must not import `three`, touch the DOM or fetch. Editor tools live outside `src/`.
- Fixed-timestep physics: streaming must not change simulation results. Colliders must be loaded before the player can reach them.
- Rapier and Three are f32. Large worlds will jitter far from the origin (floating origin is a known later option, Phase 6).
- Do not reshape terrain or maps to hide handling problems (see memory: fix the car, not the terrain).

## Phase 1: Metre-native map editor
The editor currently works in lat/lon through a fake bbox (`tools/map-editor/model.ts`, `makeProjector`).
1. Add a world-space mode in metres (x east, y north) with a world size set in km.
2. Draw a scale bar, adaptive grid lines and a tile grid overlay (tile size selectable, default 1000 m).
3. Smooth zoom and pan that stays usable on a 10 km canvas.
4. Existing maps still load (project their lat/lon into the metre space).
5. Export still writes the raw-OSM envelope with a synthetic bbox, as the synthetic generators do, so the compiler is unchanged.

**Done when:** a blank 6 km world can be created, drawn on, saved and compiled, and an existing map still opens.

## Phase 2: Image import
New pure module (no DOM) plus a small UI in the editor.
1. Load a PNG/JPG, threshold to black and white (adjustable threshold).
2. Scale dialog: real width in km (or metres per pixel), aspect ratio locked, with a warning when metres-per-pixel is too coarse (aim for 1 to 2 m per pixel).
3. Skeletonise strokes to a one-pixel centreline (ignore stroke width entirely).
4. Trace the skeleton into polylines. Pixel junctions become nodes. Default: every crossing is a junction (a way to unmerge in the editor).
5. Simplify then smooth, tuned in pixels so scaled-up stair-steps vanish. Prune short spurs below a length threshold.
6. Assign the dialog's default width to every road, then drop the result into the editor as ordinary editable roads.
7. Unit-test the pure parts: threshold, skeleton, trace, simplify, junction detection, scale. Use small synthetic images (a loop, a T, a crossing, a diagonal).

**Done when:** a test image (loop with a few junctions) imports at 4 km and gives a clean, drivable road graph with no stair-steps and no stray spurs.

## Phase 3: Width editing and overlap checks
1. Per-road width field and a "set width for selection" action (the editor already supports per-way tags).
2. Draw roads at true metre width on the canvas.
3. Flag road pairs that overlap when widths are applied.
4. Check how the compiler handles junctions between roads of different widths, and fix or document the result.

**Done when:** mixed-width junctions compile and drive, and overlaps are visible on the canvas.

## Phase 4: Base height and base relief
1. Add a base height setting to world settings and to `createEmptyTerrainArea` (currently always fills 0).
2. Check the `.terrain.bin` 16-bit height step against the relief range we want, and record the usable range.
3. Add a coarse world-level relief layer (roughly 50 m cells), editable on the master canvas, default flat at base height.
4. Tile heights are generated by sampling this field, so neighbouring tile borders match by construction.

**Done when:** a world generated at base height 100 m sculpts up and down in the terrain editor, and a border between two generated tiles has identical heights on both sides.

## Phase 5: Tile split and manifest
1. Split tool: cut every road at tile borders, put a node on each side of each cut, and write one raw-OSM file per tile.
2. Write `world.json`: tile list, area IDs, world offsets, tile size, cell size, base height.
3. Tiles share a cell size. Border rows are identical in neighbours (overlap by one row, or lock the border row).
4. Terrain editor: lock or fade border rows while sculpting so seams stay matched.
5. Re-splitting regenerates roads and graphs only. It never overwrites sculpted heights, and warns when a moved road no longer matches the sculpted terrain.
6. Raise or remove the 2000 m area cap only if a tile needs it (1 km tiles do not).

**Done when:** a 6 km world splits into tiles, every tile opens in the terrain editor, and neighbouring borders match in height, paint and road positions.

## Phase 6: Runtime tile streaming
1. Two-tile proof: load two adjacent tiles from the manifest at once and drive a car across the seam. This surfaces seam, surface-lookup and wheel-ray problems before any streaming is written.
2. Route height, surface and wheel-ray lookups through a "which tile is this point in" step.
3. Streamer: load tiles inside a load radius, unload beyond a larger radius (hysteresis), build colliders and meshes spread over frames (`src/core/frame-budget.ts`).
4. Load radius sized against top speed so colliders always exist before the car reaches them.
5. Pursuit pathfinding only uses roads in loaded tiles at first; stitched cross-tile graphs come later if needed.
6. Routes, checkpoints and medals use world coordinates.
7. Floating origin, only if jitter shows up at the world sizes we use.

**Done when:** a car drives the full length of a multi-tile world with only the nearby tiles loaded, no visible or physical seam, and unchanged lap times with the streamer on or off for a fixed input tape.

## Things to verify early
- Where the OSM credit is rendered, and suppress it for non-OSM maps (arena-test's graph still carries an `© Op...` attribution block).
- Frame budget for a 3x3 loaded tile set (`docs/frame-budget.md`).
- Rapier heightfield collider build time at 1 km tiles, subdiv 2.
- Paint map memory per tile (0.5 m per pixel; 1 km is 2000x2000 px, about 16 MB per tile).

## Order and checkpoints
Phases 1 to 3 are editor-only and safe to ship on their own. Phase 4 and 5 change data, so commit after each. Phase 6 is the riskiest runtime work, so do the two-tile proof first and decide whether to continue before writing the streamer.

## Open questions
- Tile size: 1 km (suggested) or 2 km?
- Should the world relief layer be painted by hand, or generated (noise) with hand edits?
- Do we want a second image channel later (for example colour for surface type)? Not in scope for v1.
